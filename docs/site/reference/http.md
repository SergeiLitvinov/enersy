# HTTP-контракты

API доступен через nginx на `http://localhost`. Это описание существующих маршрутов; формальный OpenAPI-контракт ещё предстоит внедрить.

## Сессии и приватные проекты

API черновых версий паспортов проекта: [проектный каталог](../development/project-catalog). Он отделён от общего справочника; UI создания/версий/клонирования подключён. Привязка экземпляра реализована отдельным полем, выбор подключён в UI.

Приватный `POST /api/projects/{project}/schemes/{scheme}/components` принимает необязательный `projectPassportVersionId` строкой BIGINT. Одновременный `equipmentModelId` запрещён. Сервер копирует значения конкретной версии того же проекта и типа, затем применяет явно переданные `params` без defaults. Неверные ключи/значения/единицы — 400, недоступная версия — 404. Ответ и приватный снимок возвращают ссылку строкой либо `null`; новая версия каталога не обновляет экземпляр. Создание ещё не идемпотентно: после потери ответа сначала перечитайте схему. Требуется миграция `20261021001`, применённая на основном Docker-стенде после резервной копии.

Защищённые маршруты используют cookie-сессию, точный Origin для записей и ответы no-store. ID и ревизии в проектном JSON — строки. Подробные тела, ограничения, статусы и правила конфликтов приведены в [контракте сессий и проектов](../development/sessions). Каталог и схемы без проекта остаются общими; вход не присваивает им приватные права.

## Вычислительный сервис

### Архив успешных расчётов приватного проекта (2026-10-19)

`POST /api/projects/{projectId}/schemes/{schemeId}/archive-calculation?modelGroup=three-phase&method=newton-raphson` выполняет синхронный расчёт и сохраняет успешный ответ **до** отправки клиенту. Требования такие же, как у приватного `calculate`: доверенная сессия, Origin, роль owner/admin/editor, пустое тело и `If-Match` с прочитанной ревизией топологии. При успехе исходный ответ Julia возвращается без перекодирования; заголовок `X-Enersy-Archive-Id` указывает архив. Старый `calculate` и общий legacy-редактор не архивируют автоматически. Приватный редактор использует этот маршрут для запуска расчёта; список и открытие архива доступны из навигатора проекта.

Worker получает согласованный вход из одной repeatable-read транзакции, без cookie/сессии/ID аккаунта. Перед сохранением текущие права, сессия, аккаунт и принадлежность схемы проекту проверяются повторно; транзакционные блокировки согласованы с изменением участников. Изменение схемы за время вычисления не подменяет уже захваченный вход: сохраняются исходные параметры и исходная ревизия. Ревизия топологии не является полной версией всех параметров; точный вход идентифицируется SHA-256.

Для чтения достаточно текущей роли viewer/editor/admin/owner того же проекта:

| Запрос | Ответ |
| --- | --- |
| `GET /api/projects/{p}/calculation-archives?limit=20&beforeId={id}` | Страница метаданных, `items` и необязательный `nextBeforeId`; порядок ID убывает, limit 1…100 |
| `GET /api/projects/{p}/calculation-archives/{id}` | ID, исходные ID/имя схемы, автор, ревизия топологии, метод/группа, время сохранения, SHA-256 и размеры входа/результата |
| `GET /api/projects/{p}/calculation-archives/{id}/input` | Точные JSON-байты запроса, отправленного worker |
| `GET /api/projects/{p}/calculation-archives/{id}/result` | Точные JSON-байты ответа worker |
| `GET /api/projects/{p}/calculation-archives/{id}/provenance` | Сохранённые источники параметров и версии проектных паспортов; 404, если в старой записи этих данных нет |

BIGINT-идентификаторы и ревизии в метаданных — десятичные строки. Ответы `no-store`; `/input` и `/result` имеют ETag с соответствующей SHA-256. Перед чтением тела проверяются обе контрольные суммы. Чужой проект/архив, удалённый участник или отозванная сессия не получают содержимое (404 после проверки формата сессии; отсутствующая сессия — 401). Архив общий для участников проекта; личные журналы редактора остаются отдельными данными аккаунта.

Хранятся точные вход и результат, включая поля базиса, возможностей, solver и версии, которые вернул worker. Это ещё не полный пакет воспроизводимого исследования: закреплённые ModelBinding/каталог, снимок исходников/зависимостей движка, очередь, idempotency и повтор запуска будут развиваться в RUN-01/02. Повтор POST создаёт новый расчёт; после потери подтверждения сначала проверьте список, не повторяйте автоматически.

Каждое тело ограничено 8 МиБ; на проект — 100 записей или 64 МиБ суммарных тел. Квота проверяется под общей для проекта блокировкой: превышение — 409 `calculation_archive_quota`, без выдачи ложного подтверждения архивирования. Ошибка записи — 503. Неполный/неуспешный ответ 2xx не сохраняется как успешный (502); реальные ошибки worker передаются без создания записи. SQL UPDATE архива запрещён. Удаление схемы после сохранения не уничтожает архив; удаление самого проекта удаляет его архивы. Политика управления/очистки архива ещё не подключена; UI списка/открытия описан в руководстве редактора.

`branches` — необязательный для старых workers массив результатов линии, двухобмоточного трансформатора и внутреннего сопротивления источника. Поля: `component_id`, `code`, `from_bus`, `to_bus`, положительный `ratio`, `p_from_mw`, `q_from_mvar`, `p_to_mw`, `q_to_mvar`, `losses_p_mw`, `losses_q_mvar`, `i_from_ka`, `i_to_ka`. Мощности положительны при входе в элемент с соответствующего конца. `losses_*` — подписанная сумма мощностей обоих концов с учётом поперечных проводимостей, а не только последовательного сопротивления. Реактивная сумма может быть отрицательна. Токи — модули действующих значений, кА.

Для линии/трансформатора начало соответствует T1, конец T2. Для источника начало — внутренний узел ЭДС, конец — внешний T1. Клиент проверяет принадлежность узлов результату, отсутствие соединения разных островов, уникальность владельцев, соответствие `topology`/`sources` при их наличии и равенство сумм мощностей с допуском `1e-7 + 1e-9 × max(|Sнач|, |Sкон|, |ΔS|)` отдельно для P и Q. Это проверка целостности ответа, а не независимая проверка физических уравнений.

`shunts` содержит `component_id`, `code: "capacitor" | "reactor"`, `bus`, `q_nom_mvar`, `p_mw`, `q_mvar`. `q_nom_mvar` — положительный паспортный модуль; `q_mvar` — потребление при фактическом напряжении (отрицательное для конденсатора). Отсутствующие коллекции не заменяются нулевыми результатами; пустой массив означает отсутствие соответствующих элементов в модели.

Успешный ответ дополнен `topology`: `schema_version: 1`, `node_numbering: "min-component-terminal"`, `terminals` и `internal_nodes`. Терминал содержит `component_id`, `component_type`, физический порядковый `terminal`, `bus_id` и `omitted_reason`. У полностью неподключённого выключателя/разъединителя `bus_id: null`, `omitted_reason: "unused_switch"`; у участвующего терминала — номер узла и `omitted_reason: null`. Ноль вместо отсутствующего узла не используется.

`internal_nodes` содержит `{component_id, bus_id, role: "source_emf"}` для внутренних узлов источников. Они согласованы с `sources[].internal_bus`, а внешний T1 — с `sources[].terminal_bus`. Карта использует глобальные номера результата после объединения островов. Клиент проверяет уникальность терминалов, принадлежность узлов результату, полноту покрытия и отсутствие пересечения физических и внутренних узлов. Для старого сервиса отсутствие `topology` допустимо и явно показывается в интерфейсе.

Номера физических узлов упорядочены по минимальной паре `(ID оборудования, номер терминала)` и не зависят от направления/порядка проводов. Это индексы снимка, а не постоянные ID: изменение состава схемы может их поменять. Результаты старых версий могли иметь иной порядок.

Прямой Julia API на порту 8001 принимает `POST /calculate` с `components`, `connections`, `modelGroup`, `method` и необязательными настройками. `GET /capabilities` возвращает реестр. Пакет импортируется без запуска сервера.

Ошибки Julia содержат `success: false`, текст `error` для совместимости и объект `error_detail` с `code`, `message` и контекстом. Go сохраняет HTTP-статус worker и тело диагностики. Перенаправления worker (3xx) отклоняются с 502 `Unexpected compute redirect`: Go не следует абсолютному или относительному `Location`, не пересылает туда расчётные входы и не подтверждает архивирование такого ответа. Неверный запрос, неподдержанный метод, несходимость и недоступность сервиса различаются. Точный контракт полей и статусов смотрите в [исходниках](/generated/code/).

Точные JSON-тела архива и исследования выдаются без изменения байтов с `Content-Type: application/json` и `X-Content-Type-Options: nosniff`. Некорректное JSON-тело не выдаётся как успешный ответ: сервер возвращает 500 `Response integrity failure`. Ошибка доставки уже начатого ответа регистрируется без повторной записи тела или подмены подтверждения операции.

### Мощности источника на ЭДС и выводах

У новых результатов `sources` дополнен полями `terminal_p_mw`, `terminal_q_mvar`, `losses_p_mw`, `losses_q_mvar`. Прежние `p_mw`/`q_mvar` остаются выдачей внутренней ЭДС. Терминальные мощности положительны при выдаче во внешнюю сеть: это отрицательные `p_to_mw`/`q_to_mvar` ветви `generator`. Потери совпадают с её `losses_*`; мощность ЭДС равна сумме терминальной мощности и потерь отдельно по P/Q. Клиент принимает весь набор из четырёх конечных чисел либо его полное отсутствие для старых архивов; проверяет соответствие ветви и баланса с абсолютным допуском 10⁻⁷ МВт/Мвар плюс относительным 10⁻⁹. Это не добавляет терминальные Q-ограничения и не меняет знак старых полей.

### Диагностика шага Newton

В `solver` возвращаются `step_policy: "armijo-infinity-positive-voltage-v1"`, `armijo_coefficient: 0.0001`, `max_backtracks_per_step: 24`, суммарные `line_search_trials`/`damped_steps` и `min_step_length`. Счётчики охватывают все Q-проходы и острова; `island_results` содержит локальные значения. При отсутствии принятого шага минимальная длина равна 1. Исчерпание поиска — `SOLVER/line_search_failed` (HTTP 500), а не успешная сходимость. `root_selection: "initial-state-dependent-no-stability-certification"` означает, что выбор физически нужного корня и проверка устойчивости не выполнены. В старых архивах этих полей может не быть.

Для прокси вычислений: истечение срока ожидания (в том числе при чтении тела ответа) — 504; недоступный worker — 503; обрыв/неполный ответ или превышение 8 MiB — 502. Отмена контекста клиента прекращает чтение и закрывает HTTP-соединение; если ответ ещё можно записать, обработчик возвращает 408. При реальном отключении клиента доставка этого статуса не гарантируется. Это отмена транспорта, не подтверждение остановки численного worker (RUN-задачи остаются открытыми). Статусы 4xx/5xx Julia и её структурированная диагностика передаются без подмены на 200.

### JSON на входе вычислительного worker {#worker-json-contract}

`POST /calculate` и `POST /solve` используют JSON.jl 1.12.2. Тело должно содержать ровно одно полное JSON-значение: хвостовые данные и повторяющиеся ключи отклоняются с HTTP 400, `error_detail.code: invalid_json`. NaN/Infinity не разрешены. Корневые массив/null проходят синтаксический разбор, затем отклоняются DTO как `type_error`, если маршрут требует объект. Поля ответа со значением null и пустые массивы сохраняются; нечисловой Float64 в ответе даёт структурированную 500 `serialization_failure`.

Julia DTO сохраняет целочисленные значения до проверки диапазона Int64, без промежуточного Float64: ID `9007199254740993` не округляется. Boolean не становится числом; выход за диапазон Int64 отклоняется. Это правило разбора worker; формат строковых ID приватного проектного API остаётся описанным выше.

Смена JSON-кодека влияет на новые ответы, но не пересериализует сохранённые архивы. Архивные `/input` и `/result` продолжают возвращать первоначальные байты и соответствующие SHA-256/ETag. [Проверка миграции](../development/documentation.md#json-codec-migration).

## Пример линейной системы

```json
{"A": [[2, 3], [1, 4]], "b": [5, 7]}
```

Для `POST /julia/solve` решение равно `[-0.2, 1.8]`. Этот аналитический пример проверяет транспорт и линейную алгебру; электрической топологии в нём нет.

## Создание оборудования

`POST /api/ees/components` принимает `schemeId`, `typeId`, `x`, `y`, `rotation`, `name`, необязательные `equipmentModelId` (число или `null`) и `params` (словарь строк). Сервер копирует выбранный паспорт, применяет явно переданные переопределения и сохраняет объект с параметрами одной транзакцией. Шаблонные значения без паспорта автоматически не подставляются.

Ответ содержит `id`, `success`, `equipmentModelId` и фактически сохранённые `params`. Модель чужого типа отклоняется, отсутствующая схема/модель даёт 404, некорректные поля — 400, запрос больше 1 MiB — 413. Ошибка записи не оставляет частичный объект. Потеря сетевого подтверждения после commit требует проверки схемы перед повторной отправкой.

`GET /api/ees/schemes/{id}` возвращает паспорт и сохранённые параметры каждого объекта, а также ID соединений. Копия параметров независима от последующих правок каталога.

## Соединения и диагностика сохранённых данных

`POST /api/ees/connections` принимает `schemeId`, `from`, `to`, `fromPort`, `toPort`. Оба объекта должны принадлежать указанной схеме; имена портов проверяются по `component_type_ports`, физические домены должны совпадать. Координаты не участвуют в проверке. Кольца и параллельные ветви разрешены. Наличие порта не доказывает поддержку математической модели элемента.

Успех возвращает `id` и `success: true`. Неизвестный ID — 404; чужая схема, неизвестный/несовместимый порт и соединение порта с самим собой — 422; некорректный JSON/поля — 400; тело больше 64 KiB — 413; другой HTTP-метод — 405 с `Allow: POST`.

Миграция `20260930002` добавляет составные внешние ключи и проверку портов на записи. `NOT VALID` сохраняет старые записи для проверки, одновременно защищая новые. Представление `invalid_scheme_connections` показывает причины: `scheme_mismatch`, `unknown_port`, `domain_mismatch`, `identical_port`. Аудит доступен без изменения данных:

```sql
SELECT id, scheme_id, reasons FROM invalid_scheme_connections ORDER BY scheme_id, id;
```

`GET /api/ees/schemes/{id}` передаёт причины в `connections[].validationErrors`. Редактор показывает предупреждение и позволяет выбрать проблемную связь, даже если её порт нельзя нарисовать. Автоматического удаления нет. Реестр legacy-портов ещё требует замены единым версионированным контрактом терминалов; фазовая совместимость будущих моделей не заявляется реализованной.

## Описания математических реализаций

С 2026-10-21 описание нагрузки имеет ID `enersy.ac.load-static` и охватывает PQ и явно выбранный ZIP; прежний ID `enersy.ac.load-pq` относился только к PQ. Это публичное описание текущего кода, не сохранённая привязка модели исследования. Снимки старых результатов не переписываются.

В `POST /calculate` у нагрузки необязательный `zip_enabled` (логическое строковое значение; по умолчанию false) включает ZIP. При true обязательны `voltage_nom` (линейное RMS kV > 0) и шесть безразмерных долей `zip_p_z`, `zip_p_i`, `zip_p_p`, `zip_q_z`, `zip_q_i`, `zip_q_p`. Каждая доля в [0,1], каждая тройка суммируется в 1 с абсолютным допуском 1e-12; автоматической нормализации нет. Заданные доли без включённого ZIP отклоняются. Формулы и область применимости — [численная проверка](../development/numerical-validation.md#zip-нагрузки-2026-10-21).

Ответ дополнен `loads[]`: `component_id`, глобальный `bus`, `profile` (`pq`/`zip`), `voltage_kv`, фактические `p_mw`/`q_mvar` и номинальные `p_nom_mw`/`q_nom_mvar`. `voltage_nom_kv` — опорное напряжение ZIP, null для PQ; в ранних ответах ZIP это поле отсутствовало. Здесь положительная мощность означает потребление; исторические `balance.load_p_mw`/`load_q_mvar` сохраняют знак инъекции (обычное потребление отрицательно). Баланс использует фактические значения. Новые поля не обязательны в старых архивах. Клиент проверяет конечность чисел, уникальность ID, покрытие терминалов нагрузок, совпадение напряжения с узлом и постоянство мощностей PQ; таблица показывает отсутствие Uном явно.

Текущий ответ v3 содержит шесть описаний: источник, π-линия, двухобмоточный трансформатор, нагрузка PQ/ZIP, ёмкостный и индуктивный AC-шунты. В ребре допускается необязательное `symbol: "inductor" | "capacitor"` только для `impedance`/`admittance`, с разными координатами концов. Это безопасная подсказка схемы замещения, не УГО оборудования и не исполняемый SVG. Без неё клиент сохраняет прежние условные блоки. Для реактора символ катушки подписан `jX_L`; связь с фактическим `Y = −jB` и случай q_nom=0 описаны в уравнениях. В v3 добавлен `kind: "transformer"` для идеальной трансформации, без `symbol`, с разными координатами концов. Состав физической топологии и численные модели этим не меняются.

`GET /api/ees/model-definitions` проксирует публичный `GET /model-definitions` работающего Julia-worker. Другие методы отклоняются с 405. Запрос не принимает проект/оборудование и не передаёт query/cookie пользователя worker. Контракт `schema_version: 1`: версия ядра, статус режима `three-phase/newton-raphson`, SHA-256 комплекта исходников, список файлов и описания источника за импедансом, π-линии и PQ-нагрузки. Численные значения не рассчитываются. Ограничения идентичности и структура описаны в [контракте видов](../development/diagram-views.md#описания-реализаций-из-worker-2026-10-18). Ошибки/лимиты/отмена запроса обрабатываются общим транспортом Go → Julia.

Контракт описаний v2 дополняет каждую модель списком `parameters` с единицами, типом, обязательностью, пояснением и строковым `default_value` либо null. Клиент поддерживает v1 без списка и v2/v3 с обязательным списком; неизвестная версия отклоняется. Новый тип ребра `transformer` разрешён только в v3. Эти метаданные не выполняют расчёт, не проверяют проект и не записывают значения в оборудование. Подробности: [входы модели v2](../development/diagram-views.md#контракт-входов-модели-v2-2026-10-18), [трансформатор и v3](../development/diagram-views.md#двухобмоточный-трансформатор-и-контракт-v3-2026-10-21).
