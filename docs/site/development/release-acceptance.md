# Приёмка чистой Docker-поставки

`scripts/build/Test-CleanRelease.ps1` проверяет основной вариант поставки как единый стенд: PostgreSQL, API Go, worker Julia, frontend, внешний nginx и веб-документация. Он использует штатные Dockerfile и nginx-конфигурации проекта. Это дополнительный release-gate BASE-07; языковые тесты, проверки приватных проектов и численная матрица сохраняются отдельно.

## Запуск

Из корня проекта в PowerShell 7, с работающим Docker/Compose и доступом к закреплённым registry:

```powershell
./scripts/build/Test-CleanRelease.ps1
```

По умолчанию запускается `build --pull --no-cache`. Установка зависимостей заново проверяет lock-файлы; имеющиеся базовые слои Docker могут переиспользоваться. Кеши npm/pnpm/Go/Julia с компьютера разработчика в сборку не подключаются. Для диагностического прогона можно задать `-UseCache`; квитанция явно отмечает этот режим, и такой прогон не выдаётся за сборку без кеша инструкций.

Go, Julia, Node и компиляторы на компьютере оператора не требуются. PowerShell нужен только этому инструменту разработки; обычный запуск приложения остаётся `docker compose up --build`. Сейчас gate допускает только Linux amd64 containers. Проверка на Docker Desktop/Windows не доказывает запуск на самостоятельном Linux host, ARM64, macOS или native Windows; для другой платформы требуются собственные runtime/notice-входы и проверки.

## Изоляция и проверяемый сценарий

Каждый запуск получает новое имя `enersy-release-<UUID>`, собственную внутреннюю сеть и PostgreSQL в tmpfs. До сборки проверяется разрешённая конфигурация: host-портов и постоянных томов приложения нет, общие имена контейнеров/образов и host networking запрещены. Входы тестового клиента и nginx подключаются только для чтения; запись разрешена в собственный каталог отчёта. Проверены девять отрицательных вариантов конфигурации: чужой project, порт, фиксированный контейнер, постоянный DB-том, writable input, внешняя сеть, общий build image, host network и подменённый источник bind.

Все четыре сборки завершаются до запуска холодного HTTP-расчёта. Worker ограничен двумя CPU и 2 GiB, остальные сервисы также имеют лимиты. Тест не увеличивает бюджет решателя. HTTP-клиент последовательно выдерживает минимум 50 мс между запросами, учитывая действующий nginx rate limit; это функциональная приёмка, не нагрузочный профиль.

Проверяются:

1. Готовность шести сервисов, чистая история миграций и точное совпадение seed-каталога с поставляемым эталоном.
2. HTML frontend, загрузка его entry JS, выдача собственного MIT-текста и API через обе nginx-конфигурации. Это проверка HTTP/артефактов; визуальная и интерактивная приёмка браузером выполняется отдельно.
3. Собранное руководство и его MIT-текст.
4. Создание через внешний proxy пяти объектов и четырёх соединений, чтение сохранённого графа и реальный расчёт Go → Julia.
5. Сравнение с существующим независимым PYPOWER-эталоном `compiled_transformer` из `backend-julia/test/reference/ac-networks-v1.json`: генератор, сопротивление источника, сеть 110/10 кВ, двухобмоточный трансформатор с намагничиванием и нагрузка. Допуски прежние: напряжение/мощность узла 1e-8 p.u., угол 1e-8 рад, потоки ветвей 1e-6 МВт/Мвар. Намагничивание приводится к той же физической границе, что в существующей интеграционной проверке; единицы и эталон не подгоняются.
6. Удаление синтетической схемы и отсутствие созданных аутентифицированных аккаунтов/участников. Приватные роли этим сценарием не проверяются.

В `finally` удаляются только собственный Compose-стенд и его автоматически именованные build images; рабочий проект и его тома не используются. При ошибке сохраняются ограниченные журналы контейнеров. Два первых локальных прогона 2026-10-26 помечены failed: сначала слишком быстрый клиент получил nginx 503 по rate limit; затем отправленный им `{}` получил предусмотренный API отказ 400 без `operatingLimits`. Оба отказа произошли до решателя. Исправлены частота и контракт тестовых запросов; эталон и допуски не менялись. Клиент отдельно проверяет отказ malformed-body и передаёт явный `operatingLimits: []` для этого сценария без режимных ограничений.

## Отчёты и CI

Файлы создаются в `.cache/release-check/<UTC>-<UUID>/`: `release.json`, `http-physical.json`, логи этапов, аудит БД/каталога и сведения об образах. Квитанция фиксирует платформу Docker, IDs образов, режим кеша, SHA-256 выбранных входов, исходный независимый эталон/допуски, исход и результат cleanup. Это не полная аттестация всего дерева исходников; изменение выбранного входа во время проверки завершает прогон ошибкой.

Job `clean-release` на `ubuntu-24.04` запускает тот же скрипт и сохраняет каталог как artifact `clean-release-acceptance`, включая неуспешные запуски. Добавление job и локальная проверка YAML не означают подтверждённый удалённый CI. Статус passed относится только к перечисленным шагам, выбранному стеку и платформе; большие схемы, native Rust/WASM, переходные процессы и машины требуют своих приёмочных наборов.
