# Сходимость и режимные ограничения

Статус 2026-10-24: в общем ядре Julia/native реализована оценка явно заданных границ напряжения на терминалах. Форма редактора передаёт их через Go; приватный расчёт сохраняет границы в точном входе архива. Результат и открытие архива проверяют подтверждение исходных границ. [Версии Study](./studies.md) уже сохраняют документ и снимок через API, но окно границ к ним ещё не подключено: его настройки пока не восстанавливаются между перезагрузками. Другие виды режимных ограничений также остаются в CORE-06. Это первый слой оценки, а не полная проверка допустимости режима.

## Данные исследования

Границы принадлежат исследованию и не меняют паспорт, модель оборудования или уравнения Ньютона. Номинальное напряжение не задаёт автоматически допустимый диапазон. В программном API:

```julia
limits = [TerminalVoltageLimit(2, 1, 9.5, 10.5)]
result = calculate(components, connections; operating_limits=limits)
```

В обычное тело прямого `POST /calculate` worker можно добавить:

```json
{"operatingLimits":[{"component_id":2,"terminal":1,"min_kv":9.5,"max_kv":10.5}]}
```

Это дополнение к components/connections, не самостоятельный запрос. Используется линейное действующее напряжение в кВ; фазное напряжение и p.u. этим контрактом не принимаются. Обе границы обязательны, конечны, положительны и `min_kv <= max_kv`. ID оборудования и номер терминала — положительные целые. Строки, bool, неизвестные поля и повтор одного терминала отклоняются с 400. Терминал задаётся номером из `topology.terminals`, а не номером расчётного узла или координатой рисунка. Неизвестная ссылка отклоняется до решения. Исключённый неиспользуемый терминал аппарата возвращает 422 `omitted_limit_terminal`; он не получает фиктивное нулевое напряжение.

## Редактор и Go API

Сначала выполните расчёт без границ и закройте результат. Нажмите «Границы», добавьте строку, выберите оборудование и терминал из фактической карты расчёта, введите минимум и максимум в кВ и примените к следующему запуску. Исходные поля границ пусты: номинал не подставляется. Повторный расчёт покажет оценку и отдельную таблицу. Настройки действуют в открытом редакторе до смены схемы или перезагрузки. Кнопка «Очистить» меняет черновик окна; сброс применяется только после подтверждения формы. Отмена окна не меняет действующие границы.

Если состав или связи схемы изменены, старые границы сохраняются для просмотра, но запуск блокируется. Нужно явно очистить их, выполнить новый базовый расчёт и задать границы по новой карте. Перемещение и поворот рисунка не меняют контекст границ; сравниваются ID/типы оборудования и концы связей, не координаты. Ни номер расчётного узла, ни индекс строки не используются для переноса границы на оборудование. При смене схемы настройки не переносятся в другой контекст.

Оба Go-маршрута `POST /api/projects/{project}/schemes/{scheme}/calculate` и `archive-calculation`, а также legacy `POST /api/ees/calculate/{scheme}` принимают необязательное тело с единственным полем `operatingLimits`, как в примере выше. modelGroup/method/computeBackend/maxTimeMs остаются query-параметрами. Предел тела — 128 KiB (413 при превышении), до 1000 границ (400 при превышении). Непустое `{}`, null, неизвестные поля, дубликаты терминала и нечисловые значения отклоняются. Пустое тело сохраняет прежние байты снимка. Явный пустой массив допустим и требует подтверждения `not_declared`.

Go читает оборудование из разрешённой схемы, а не из тела клиента. Ссылка на компонент вне этого снимка возвращает 400 без запроса его данных; соответствие физическому терминалу проверяет Julia до решения. Приватные маршруты сохраняют Origin, cookie, права записи, If-Match топологии и повторную проверку доступа перед выдачей/архивированием. Бюджет времени и движок сохраняются вместе с границами. SHA-256 относится к полным точным байтам сериализованного сервером снимка, не к исходным байтам тела клиента.

Если worker вернул номинальный успех без оценки, с изменёнными границами, несогласованным статусом/измерением/картой терминалов, Go возвращает 502 до архивирования. Статус `violated` при корректной оценке остаётся успешным численным результатом и может быть сохранён. Клиент сверяет немедленный ответ и повторно открытый архив с исходными границами. Старому архиву без оценки не приписывается допустимость; отсутствие новых настроек не требует вымышленного бюджета или новых полей от старого результата.

## Результат

Поле `operating_assessment` имеет `schema_version=1`, `policy=explicit-terminal-voltage-v1`, `checks` и один из статусов:

| Статус | Значение |
| --- | --- |
| `not_declared` | Нет явно заданных границ; допустимость не проверена |
| `within_declared_bounds` | Все перечисленные напряжения находятся в своих границах |
| `violated` | Хотя бы одна заданная граница нарушена |

Каждая проверка сохраняет component_id, terminal, глобальный bus_id, `quantity=line_to_line_rms_voltage`, `unit=kV`, точные min/max/measured и `below_min`, `above_max` либо `within_bounds`. Проверка выполняется после объединения островов и до публикации, с сохранением общего бюджета времени. При отсутствии ограничений дополнительные индексы всей сети не строятся.

Сравнение выполняется по неокруглённому Float64, границы включены; скрытой надбавки к диапазону нет. Пользователь задаёт инженерный диапазон явно. Округление таблицы не меняет статус и исходные данные. `success=true` по-прежнему означает успешное численное решение; нарушение границы не превращается в несходимость и не скрывает вычисленный режим. Клиент проверяет сводный статус по строкам, значения по узлам, единицы, уникальность целей и карту терминалов, если она присутствует.

`stability_assessed=false` всегда явно указан: эта оценка не подтверждает устойчивость, единственность корня, допустимость токов, нагрева, терминальных P/Q или соответствие нормативной методике. NUM-NR-START-01 остаётся открытым. Расширение величин и нормативных профилей требует своих моделей, данных и эталонов.

## Проверки

Аналитический эталон: источник E=1 кВ с R=1 Ом питает нагрузку P=0,2 МВт, Q=0. Из `P=V(E−V)/R` получаем верхний корень `V=(1+sqrt(1−4·0,2))/2 ≈ 0,72360679775 кВ`. Допуск сравнения — 1e−10 кВ. Границы [0,7; 0,8], [0,8; 0,9] и [0,5; 0,6] соответственно дают норму, нижнее и верхнее нарушение; узловой результат совпадает с расчётом без ограничений.

47 новых проверок Julia охватывают этот эталон, равенство границе, перестановку/перемещение оборудования, два острова, неизвестные/исключённые терминалы, дубликаты и HTTP-контракт. Полный набор Julia прошёл. Настоящий HTTP Julia и Rust-Якобиана возвращает одинаковую оценку; полный native-набор содержит 235 утверждений. Frontend проверяет подменённый статус, величины, единицы, цели и отображение отсутствующих данных; полный прогон — 476 успешно, одна HTTP-проверка пропущена в окружении. Проверки выполнены в Docker; удалённый CI этим не подтверждается.

Первоначальная браузерная проверка подтвердила отображение отсутствующих границ. После подключения формы добавлены проверки её валидации и явного сброса изменённого контекста, неизменности запроса, передачи тела и сверки исходных границ архива. Полный frontend-набор: 483 успешно, одна opt-in HTTP-проверка пропущена. TypeScript, lint и сборка прошли. Полный Go-набор с одноразовой PostgreSQL и go vet прошёл; race локально не запускался из-за отсутствия cgo toolchain в образе. Само численное ядро на этом этапе не менялось.

Настоящий Go→Rust HTTP→PostgreSQL проверил архив с нижним нарушением на нагрузке: точные вход и результат сохранились после изменения исходной схемы. Отдельный явно обозначенный несовместимый HTTP worker, возвращающий прежний физический результат без оценки, получил 502 и не создал архив; failure fixture с 504 также не создал архив. Эти fixtures проверяют границу транспорта/хранения, не заменяют физические эталоны. Удалённый CI и браузерное открытие приватного архива этим набором не подтверждаются.

В браузере выполнен сценарий обычного редактора через настоящий Go API: базовый расчёт → выбор нагрузки #2, терминал 1 → границы [10,1; 11] кВ → расчёт с Rust-Якобианом. Результат за две итерации показал 9,974826 кВ и «Ниже минимума». Форма проверена визуально в светлой и тёмной темах. Добавление нового объекта сохранило старую границу, но заблокировало запуск с сообщением о пересмотре; очистка черновика и отмена окна не сняли блокировку и не сбросили действующую границу. Проверка шла на одноразовой базе без пользовательских данных.

```powershell
docker run --rm --network none -v C:/project/enersy/backend-julia:/app:ro enersy-julia-compute julia --project=. test/runtests.jl
docker run --rm --network none -v C:/project/enersy/backend-julia:/app:ro enersy-numerics-ffi-check julia --project=. test/rust_ffi.jl
```

Пути следует заменить на свой checkout. Для неизменяемых образов перед проверкой пересобрать julia-compute и профиль numerics-ffi-check. [Управление расчётом](./execution-control.md), [численная проверка](./numerical-validation.md).
