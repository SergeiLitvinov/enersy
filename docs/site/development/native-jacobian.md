# Экспериментальная граница Julia↔Rust

Статус 2026-10-23: C ABI v1 и Julia-адаптер проверены в Docker, подключены к полному Newton и опциональному HTTP-worker. Обычная поставка по умолчанию использует Julia; редактор выбирает движок из списка подключённого worker. Сам [Rust-план Якобиана](./compute-backends.md#rust-jacobian-prototype) остаётся безопасным Rust; операции с сырыми указателями изолированы в отдельном ABI-модуле за feature `c-abi`.

## Контракт и владение

Индексы и CSC-смещения C ABI — с нуля, тип `uint64_t`; числа — Float64, p.u./радианы. Версия проверяется до создания плана. Заголовок фиксирует layout и коды ошибок, а C11/Rust/Julia-проверки контролируют размеры структур и смещения полей. Пока проверен Linux 64-bit в Docker. Само безопасное ядро не имеет этого ограничения, но ABI v1 отклоняет 32-битную сборку и требует `panic=unwind`.

Rust возвращает числовой process-local handle, а не адрес своего объекта. План владеет структурой; входные буферы не удерживаются. Копирование шаблона и численных значений идёт в буферы вызывающей стороны. Нативные вызовы получают Arc-lease: удаление handle не уничтожает план под уже выполняющимся вызовом. Неизвестный/повторно закрытый handle отклоняется. Счётчик live plans считает записи handle, а не RSS или ещё выполняющиеся Arc-leases.

Граница проверяет null для непустых буферов, выравнивание, переполнение длины/диапазона и перекрытие выходов со входами. Пустые буферы могут иметь null; выход инициализируется перед созданием Rust-ссылки. Проверки не доказывают, что произвольный указатель указывает на выделенную память: C-клиент обязан предоставить живые доступные буферы, запретить конкурентную запись и не выгружать библиотеку во время вызовов. Перехват Rust-паники не изолирует segfault/OOM; лимиты и изоляция принадлежат процессу worker. Это интерфейс доверенного кода, не загрузчик пользовательских моделей.

## Julia-адаптер

`with_library` открывает только явно заданную оператором доверенную библиотеку. `with_plan` создаёт и закрывает план в `finally`, включая исключение callback. Обе области принадлежат задаче Julia, которая их создала; передача плана другой задаче отклоняется. Каждый HTTP-запрос опционального worker создаёт собственные области библиотеки и плана внутри своей задачи.

Перед каждым `assemble` проверяются структура Y, нумерация и состав PV/PQ. Смена классификации или топологии требует нового `with_plan`, даже при том же количестве узлов. Численные проводимости могут обновляться в прежней структуре. Входные Y/state/setup нельзя конкурентно изменять. Внутри области вызовы могут повторяться:

```julia
RustJacobianAdapter.with_library("/opt/enersy/libenersy_numerics.so") do library
    RustJacobianAdapter.with_plan(library, Y, setup) do plan
        J = RustJacobianAdapter.assemble(plan, Y, v, theta, calculated_p, calculated_q, setup)
        # J owns Julia arrays and remains usable after both scopes close.
    end
end
```

Адаптер удерживает Julia-буферы через `GC.@preserve`. Для ясного владения он разделяет комплексные проводимости на G/B и возвращает CSC с собственными Julia-массивами. Это включает копирования и проверки; интерфейс не объявляется zero-copy. В Rust ABI также преобразуются ZIP-записи и проверяются входы. Закрытые области и устаревший план выдают явную ошибку вместо обращения к освобождённой памяти.

## Подтверждённые проверки

Локально прошли 10 Rust-тестов с `c-abi`, debug/release и clippy с запретом предупреждений. Проверены отказ версии, layout, aliasing, неверные диапазоны, повторное освобождение, Arc-lease после удаления handle и перехват unwind. C11-проверка заголовка также прошла.

81 утверждение Julia проверяет ABI 999 как отрицательный loader fixture, выгрузку такой библиотеки, 50 исключений callback без оставшихся handle, использование матрицы после закрытия/GC, неверную задачу, изменение структуры/PV↔PQ, неконечные числа и восстановление после отказа. Проверены пустые буферы одноузловой системы, PV/PQ, несимметричная комплексная Y, отсутствующая диагональ и несколько ZIP-записей. [Тесты адаптера](/generated/code/backend-julia__test__rust_ffi_jl). Те же три семейства, размеры 1k/10k/100k, seed=20261021, неплоское состояние, смешанные PV/PQ и ZIP-производные. Девять прогретых повторений на вариант, по три прогрева; отдельный контейнер на случай, 2 CPU / 2 ГиБ, Julia/BLAS по одному потоку, Julia 1.10.12, CPU-архитектура `znver3`. Полные матрицы сравниваются после закрытия плана и библиотеки. Во всех девяти случаях разница нулевая на этом стенде; заданный допуск — 10⁻¹¹ плюс 10⁻¹²·max|JJulia|.

| Сеть 100k | Julia, мс | Адаптер, мс | Вызов Rust*, мс |
| --- | ---: | ---: | ---: |
| Радиальная | 93,977 | 8,143 | 4,502 |
| Кольцо | 75,195 | 8,879 | 4,802 |
| Сетка | 78,242 | 11,588 | 7,091 |

Адаптер включает проверку setup/структуры, преобразование Complex/ZIP, выделение выходов, C ABI и собственные CSC-копии. \* Внутренний таймер охватывает C-вызов вместе с проверками Rust, преобразованием ZIP, инициализацией выхода и обновлением ядра. Медианы стадий не складываются; отчёт сохраняет парные времена каждого вызова. Загрузка библиотеки, создание плана и первый JIT-вызов записаны отдельно от прогретых обновлений; закрытие областей в таймер update не входит. Пик cgroup включает обе реализации, JIT и все пробы случая — не память одного update.

Это проверка производных в заданной точке. Полный Newton, смена Q-режимов внутри расчёта, отмена и общая длительность HTTP-задачи здесь не измерены. На том же прогоне для 1k mesh адаптер занял 0,191 мс против Julia 0,690 мс, однако это не гарантия ускорения на любых схемах. Старый файловый Rust-стенд имеет другие накладные расходы и не используется для вычитания «стоимости FFI».

## Полное решение Newton с Rust-Якобианом

Обновление 2026-10-23: `RustJacobianAdapter.solve_newton` подключает Rust-сборку к настоящему Newton; `solve_q_limits` создаёт отдельный план на каждый проход активного PV/PQ-состава. План освобождается также при ошибке сходимости или цикле Q-ограничений. Формулы мощностей, поиск Armijo и UMFPACK остаются Julia. Это экспериментальный программный вход; отдельный HTTP-worker и проектный API с явным выбором backend описаны ниже. Обычная поставка по умолчанию использует Julia.

В Docker прошли 178 проверок адаптера: прежние 81 и 97 новых проверок полных решений. Новые проверки включают аналитический корень двухузловой резистивной цепи, независимые PYPOWER-эталоны физических сетей, PV→PQ и PQ→PV, совпадение активных составов и ошибок, отсутствие оставшихся handle после отказа и повторный запуск. Полный обычный Julia-набор также прошёл. Это не подтверждает полный набор всех будущих моделей или отмену native-вызова.

## Опциональный HTTP-worker

Обновление 2026-10-23: добавлен отдельный Compose-профиль `native-compute` с сервисом `julia-rust-compute`. По умолчанию основное приложение продолжает использовать обычный Julia-worker. Native-сервис не публикует host-порт и не подключается к БД; лимиты — 2 CPU / 2 ГиБ. Его readiness доступен через `/ready` и перечисляет `compute_backends`.

```powershell
docker compose build julia-compute
docker compose --profile native-compute build julia-rust-compute
docker compose --profile native-compute up -d julia-rust-compute
```

Worker принимает `computeBackend: "julia-rust-jacobian"` или `"julia"` в JSON `/calculate`. Если поле отсутствует, выбирается Julia. Неизвестный или не установленный движок даёт `422 / compute_backend_unavailable`, неверный тип — 400. Путь к библиотеке, модуль или код через запрос не принимаются. Библиотеку задаёт оператор при старте; проверяются ABI и SHA-256, изменение байтов после старта отклоняется. Область загрузки и native-планы создаются внутри задачи каждого запроса; разделяемого Julia-плана нет. Отсутствуют автоматический fallback и горячая подмена библиотеки.

В проектном Go API параметр передаётся явно в query `computeBackend=julia-rust-jacobian` у `/api/projects/{project}/schemes/{scheme}/calculate` и `archive-calculation`. Права, `Origin` и ревизия схемы проверяются прежним способом. Параметр попадает в точные байты снимка запроса и его SHA-256. Для подключения Go к native-worker оператор задаёт `JULIA_BASE_URL=http://julia-rust-compute:8001` при пересоздании Go-сервиса; сам профиль адрес работающего API не переключает. Выбор движка доступен в панели расчёта редактора; список читается через Go `/api/ees/compute-backends` из readiness подключённого worker. Клиент отклоняет результат, который не подтверждает выбранный ID.

Результат содержит `solver.compute_backend`: ID, версию ABI, версию Julia, версию и SHA-256 Julia-кода, SHA-256 native-библиотеки и адаптера, названия сборщика Якобиана и линейного решателя. Это описание реализации, а не доказательство физической применимости. У обычного Julia-результата записываются ID/версия Julia-движка и runtime. Архив сохраняет исходное тело ответа вместе с этими данными.

Локально прошли 34 проверки настоящего HTTP для выбора/отказов, совместимости с Julia по умолчанию и восьми отдельных запросов с чередованием backend. Вместе с предыдущими численными и ABI-проверками — 212 проверок адаптера. Также прошли обычный Julia-набор и Go vet/unit tests; PostgreSQL-сценарии этих unit tests без настроенного стенда пропускаются.

Отдельно пройден реальный Go→native HTTP→PostgreSQL round trip на одноразовом стенде: выбранный backend сохранился в запросе, хеш библиотеки — в ответе, архив прочитан побайтно без изменений; последующая правка схемы не меняет сохранённый результат. Проверены баланс P/Q и паспортное происхождение исходных данных. Это owner-сценарий; полный аудит межпользовательской изоляции не подменяется этой проверкой.

```powershell
docker compose --profile numerics-ffi-check run --rm --build numerics-ffi-check
# Go-модули должны уже находиться в локальном .cache/go-mod.
docker compose -f tests/integration/native-compose.yml run --rm archive-check
docker compose -f tests/integration/native-compose.yml down
```

Одноразовый стенд не имеет host-портов, использует PostgreSQL в tmpfs и отдельную внутреннюю сеть. Обычная база приложения не используется. Профиль пока экспериментальный: управление отменой native-вызовов, ресурсные отказы и расширение эталонов остаются в PERF-04.

Проверка UI 2026-10-23: 465 frontend-тестов прошли, один отдельный HTTP-сценарий пропущен без стенда; typecheck/lint/build и Go vet/unit tests прошли. В браузере на одноразовом Docker-стенде выполнен расчёт с Rust, просмотрены версии и SHA-256, затем worker заменён обычным Julia: обновление списка сохраняет недоступный Rust и блокирует запуск. После явного выбора Julia расчёт завершён. Основная база не использовалась. Порядок работы — [руководство](../guide/calculation.md).
