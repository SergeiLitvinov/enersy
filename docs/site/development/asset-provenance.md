## DXF и паспортные данные

`STO.dxf`, `dxf-sto-symbols/`, `dxf-sto-symbols-v2/` и `dxf-symbols/` — пользовательские материалы вне текущей Docker-поставки. Они исключены из корневого build context; это техническое исключение не является разрешением на распространение. Удалять их как мусор или включать в выпуск без отдельной проверки происхождения нельзя.

Снимок seed-каталога и его контрольные суммы описаны в [сверке каталога](./catalog-audit.md). Совпадение 604 строк с эталоном подтверждает целостность seed-данных, но не их заводское происхождение, точность или право на распространение. Для паспортных значений ещё нужен реестр первоисточников по моделям: изготовитель, документ/редакция, страницы, единицы, дата сверки и статус проверки. Непроверенное значение не становится инженерно подтверждённым из-за наличия в SQL.

## Автоматический инвентарь npm/pnpm {#node-license-inventory}

Сборки frontend и сайта выполняют `scripts/security/collect-node-licenses.mjs` после установки по lock-файлу. Инвентарь читает манифесты и корневые LICENSE/COPYING/NOTICE/COPYRIGHT/ThirdPartyNotice-файлы установленных пакетов. Код пакетов при этом не импортируется. Обрабатываются scoped-пакеты, вложенные версии npm, хранилище pnpm и символьные ссылки. Повторный путь к одной установке не удваивает её; одинаковые тексты уведомлений хранятся по SHA-256. Попытка читать ссылку вне `node_modules`, повреждённый манифест или пустой инвентарь завершается ошибкой.

Отчёт содержит SHA-256 lock-файла, точные имена/версии, заявленную лицензию, SHA-256 манифестов и тексты найденных уведомлений. Если текста или лицензионных метаданных нет, пакет остаётся в отчёте с `incompleteEvidence: true`: недостающий текст не придумывается по имени SPDX. Пути установки и произвольные файлы проекта в отчёт не включаются.

Некоторые пакеты помещают полный текст лицензии в README. Такие источники включаются только после отдельной проверки и регистрации в `scripts/security/node-notice-sources.json`: точные имя/версия, SHA-256 манифеста, имя и SHA-256 файла. Сборщик сохраняет весь файл, помечая `noticeFiles[].kind = "reviewed-embedded"`; изменение манифеста или текста у той же версии завершает сборку ошибкой. Запись не переносится автоматически на следующую версию пакета. Ссылка на лицензию или слово MIT в README сами по себе не снимают отметку неполноты. Проверка не скачивает и не исполняет код пакетов.

На Docker `linux/amd64` 2026-10-25 получены:

| Установка | Пакетов | Неполные сведения | Отчёт |
| --- | --- | --- | --- |
| Frontend, npm | 235 | 8 | [JSON в приложении](http://localhost/licenses/npm-frontend.json) |
| Сайт, pnpm | 147 | 10 | [JSON сайта](/licenses/npm-documentation.json) |

В первоначальном инвентаре было по 10 неполных записей. Для `esrecurse@4.3.0` проверен полный BSD-2-Clause текст в README (SHA-256 `a7007c78c9d9da690ef6cdb0e7a3427d05832edb00abd1f5a9882700d73be4ad`), для `imurmurhash@0.1.4` — полный MIT-текст (SHA-256 `4491517f7deb68d0b2a3bb590e785e276a60f12448447a9650d0bd50161a101c`). Они сохранены без пересоставления текста и без изменения зависимости. Остались 18 неполных записей в двух установках: у всех есть поле заявленной лицензии, но полного уведомления пока нет в собранном отчёте. Среди них платформенные бинарные пакеты esbuild/Rollup и некоторые dev-пакеты; это не доказательство отсутствия уведомлений в другом месте пакета или в исходном проекте. Получение недостающих текстов, проверка их происхождения и сопоставление с фактически поставляемым кодом ещё нужны.

Семь проверок сборщика прошли: scoped/вложенные версии, pnpm и дубликаты, сохранение неполных сведений, отказ копирования постороннего файла, сохранение Unicode/BOM/CRLF с совпадающим байтовым хешем уведомления, точная привязка встроенного текста и отказ при изменении/подмене источника. Проверены также запрет повторного использования для новой версии и ссылка на README другого пакета. CI повторяет проверки и сохраняет frontend-инвентарь отдельным артефактом; инвентарь сайта входит в артефакт документации. Удалённый запуск CI этим локальным прогоном не подтверждён.

Для произвольной уже установленной копии:

```sh
node scripts/security/collect-node-licenses.mjs frontend frontend/package-lock.json .cache/frontend-licenses.json
node scripts/security/collect-node-licenses.mjs . pnpm-lock.yaml .cache/documentation-licenses.json
```

Для контейнерной поставки достаточно обычной сборки frontend и сайта — инвентарь создаётся автоматически и копируется в статические файлы. Он охватывает установленные пакеты текущей платформы, включая dev-зависимости; отсутствующие optional-пакеты других платформ в него не входят. Это не список модулей итогового браузерного bundle, не полный SBOM приложения и не заключение о лицензионной совместимости. Зависимости Go/Rust/Julia, бинарные библиотеки и пакеты ОС требуют отдельных инвентарей и проверки уведомлений.

## Автоматический инвентарь Go {#go-license-inventory}

Сборка API выполняет `scripts/security/collect-go-licenses.go` после компиляции. Источник списка модулей — встроенные метаданные **готового бинарника**, а не все записи `go.sum` или весь кэш SDK. Кэш проверяется штатным `go mod verify`, затем для каждого выбранного модуля версия и checksum сверяются с `go list -m -json -mod=readonly`. Замены `replace`, несовпавшие сведения и источник вне модульного кэша завершают сборку ошибкой. Вызовы Go выполняются с `GOTOOLCHAIN=local`, `GOWORK=off`, `GOPROXY=off`, `GOSUMDB=off`: инвентарь не подкачивает зависимости и не запускает их код.

Отчёт содержит SHA-256 бинарника, `go.mod` и `go.sum`, имя основного модуля, точную версию SDK, версии/checksum связанных модулей и полные тексты найденных корневых LICENSE/COPYING/NOTICE/COPYRIGHT/PATENTS/ThirdPartyNotices с SHA-256. Тексты дедуплицированы по байтовому хешу. Unicode, BOM и окончания строк сохраняются; абсолютные пути установки в отчёт не записываются. Произвольный код с похожими именами (`notice.go`, `notice_example_test.go`) и JSON-метаданные лицензий не считаются текстом уведомления. Пустой, слишком большой, не-UTF-8 файл или ссылка вне каталога модуля отклоняются. Отсутствующий файл остаётся `missingNotice: true`, а не дополняется придуманным текстом. Манифесты повторно сверяются после сбора.

Проверено 2026-10-25 на Docker `linux/amd64`: в API выбраны семь внешних модулей — migrate/v4 4.18.2, pq 1.10.9, errwrap 1.1.0, go-multierror 1.1.1, atomic 1.7.0, x/crypto 0.58.0 и x/sys 0.49.0. У всех найдены корневые уведомления. Дополнительно сохранены LICENSE/PATENTS Go 1.26.10; всего семь различных текстов. Все опубликованные в JSON тексты проверены повторным SHA-256. Бинарник API до и после добавления инвентаря совпадает: `1e8ecc2c5bf533ac14760e269d8752eb6aa01e5c231c96d59eac84c9300f01fc`. Эта проверка относится к упаковке уведомлений; физические формулы и расчётные модели не менялись.

В конечном образе файл находится в `/usr/share/licenses/enersy/go-modules.json`, рядом с собственной MIT-лицензией. Для сборки/проверки не нужен Go на host:

```sh
docker compose -f tests/integration/go-compose.yml run --rm --no-deps go-license-check
docker compose build go-api
docker compose run --rm --no-deps --entrypoint cat go-api /usr/share/licenses/enersy/go-modules.json
```

В CI добавлены проверки сборщика, сборка конечного API и экспорт отчёта как артефакта `go-module-notices`; удалённый запуск локальной проверкой не подтверждён.

### Вложенные уведомления Go SDK {#go-sdk-source-notices}

С 2026-10-26 отчёт имеет `formatVersion: 2`. Дополнительный раздел `sdkSource` рекурсивно сохраняет файлы уведомлений из `GOROOT/src`, включая `src/vendor`, `src/cmd/vendor`, вложенные сторонние каталоги и `crypto/internal/boring`. Каждый файл имеет путь относительно SDK и SHA-256; полный текст находится в общем словаре `notices`. Область явно записана как `all-go-sdk-src-notice-files`: туда входят инструменты сборки и тестовые данные. Это консервативный комплект уведомлений SDK, а не утверждение, что каждый перечисленный компонент включён в сервер. Корневые уведомления внешних модулей по-прежнему отбираются по метаданным бинарника.

Обход не следует по ссылкам на каталоги: такая ссылка, выход за корень, отсутствие `src`, пустой, повреждённый или слишком большой текст завершают сбор ошибкой. Ссылка на обычный файл внутри SDK допустима, исходный относительный путь сохраняется. Корневое уведомление Go не назначается автоматически вложенным компонентам. Встроенные в исходники copyright-комментарии этим обходом не извлекаются.

Проверены, в частности, сохранение BOM/Unicode/CRLF и вложенных путей, дедупликация, отказы при повреждении и ссылках на внешние файлы/каталоги, а также наличие реальных вложенных уведомлений SDK. Отдельный конечный образ `enersy-go-notice-check:20261026` собран обычным `backend-go/Dockerfile`; его API-бинарник побайтово совпал с текущим образом API: `cd90125b1870bf982ae8c66edc4941e0f5d6855da494cee2b6f42d0d46add281`. Рабочий API этой проверкой не перезапускался. Новый комплект будет включаться в последующие обычные сборки автоматически.

Локальные результаты: `.cache/go-sdk-notices/go-modules.json`, независимые суммы `sdk-source-sha256.txt` и итог `verification.json`. Это артефакты проверки, а не исходные файлы поставки. Исходная проверка 2026-10-25 выше относится к прежнему бинарнику и корневому комплекту; её хеш не используется как подтверждение текущего образа.

Лицензирование отдельных исходных файлов, уведомления вне SDK src/root, совместимость условий, пакеты ОС и другие варианты бинарника требуют дальнейшей проверки. Сам факт наличия LICENSE не подтверждает лицензионную совместимость всего выпуска и не закрывает BASE-08.

## Автоматический инвентарь Rust {#rust-license-inventory}

Native-worker и проверочный WASM-образ собирают уведомления через `scripts/build/prepare-rust-notices.sh` и `scripts/security/collect-rust-licenses.mjs`. После компиляции Cargo формирует `metadata --locked --offline` и дерево `vendor --locked --offline --versioned-dirs`. Сборщик обходит разрешённый граф от корневого crate, а не все случайные файлы кэша. У каждого внешнего crate сохраняются точная версия, источник crates.io, package checksum, SHA-256 vendored-манифеста, исходное выражение лицензии и тексты уведомлений. Манифесты и файлы уведомлений сверяются с `.cargo-checksum.json`; изменение или отсутствие ожидаемой суммы завершает сборку ошибкой. Это контроль целостности в доверенной сборке, а не защита от администратора, изменившего все входы и инструментарий.

Сохраняются корневые LICENSE/COPYING/NOTICE/COPYRIGHT/PATENTS/ThirdPartyNotices и явно заданный Cargo `license_file`, включая допустимый вложенный файл. Неизвестные Git/локальные зависимости требуют отдельной проверки происхождения; ссылки за пределы своего crate, подмена каталога другим источником и неполный граф отклоняются. Отсутствующий текст остаётся `incompleteEvidence: true`. Код crates сборщик не импортирует и не исполняет. Начальная подготовка зависимостей и обычная компиляция Cargo остаются отдельными этапами Docker-сборки.

Для кода стандартной библиотеки копируется предоставленный SDK Rust 1.99.1 комплект `COPYRIGHT-library.html` и `licenses/*.txt`: 13 файлов с исходной структурой относительных ссылок. Ссылки на локальные тексты проверяются, пустые/не-UTF-8 файлы и текст свыше 4 MiB отклоняются без усечения. Все тексты, включая Unicode/BOM/окончания строк и HTML, сохраняются по SHA-256. Отчёт содержит хеши Cargo.toml/Cargo.lock/metadata, фактические release/host компилятора и SHA-256/размер/target собранного `.so` или `.wasm`. Абсолютные пути сборки и сырые Cargo IDs в него не включаются. Уведомления стандартной библиотеки дополнительно поставляются обычными файлами в `/usr/share/licenses/enersy/rust-stdlib/`.

WASM Dockerfile теперь использует корневой build context для собственного LICENSE и инструментов сбора; копируются только явно перечисленные источники. Граф Cargo включает host build/proc-macro и платформенные зависимости; это не доказательство их включения в конечный бинарник. Ноль неполных записей означает наличие собранных текстов/метаданных, а не полный юридический аудит. Полнота атрибуции отдельных исходных файлов, совместимость условий, другие native-библиотеки, ОС и будущие варианты поставки остаются отдельными проверками. Сборка WASM-прототипа не подтверждает его подключение к интерфейсу или ускорение расчёта.

## Автоматический инвентарь Julia {#julia-license-inventory}

Основной Docker-образ генерирует `/usr/share/licenses/enersy/julia-modules.json` через `scripts/security/collect_julia_licenses.jl` без сети. Сборщик проверяет фактические версию и commit Julia, платформу, идентичность пакетов и Git tree SHA зарегистрированных исходников относительно Manifest. Хеши Project.toml и Manifest.toml до и после сбора должны совпасть. Неизвестные локальные/Git-зависимости требуют отдельного разбора происхождения. Собственный код остаётся под MIT; сторонние тексты сохраняют свои условия.

Уведомления пакетов, runtime и Compiler сохраняются полностью, с SHA-256 и дедупликацией. Поддерживаются Unicode, BOM и исходные окончания строк; выход за разрешённые каталоги, пустой/повреждённый UTF-8 или текст свыше 4 MiB завершает проверку ошибкой. Отсутствующий отдельный текст явно отмечается `incompleteEvidence`, а общая лицензия Julia не назначается автоматически всем библиотекам.

В официальном образе Julia 1.13.2 LICENSE.md ссылается на отсутствующий THIRDPARTY.md. В поставку добавлен оригинал из commit `45b6d15e34bbd2003a31acce0b1847b63dad029c`: проверяются Git blob `7e3e5c604c13890df513e69e7858e88ac1e0f4b4` и SHA-256 `7028c525d1a25e31c6c684ade567b3f6f1e408636c65c2d787fc8304e69df777`. Это указатель upstream на сторонние компоненты, содержащий в том числе изменяемые ссылки; он не заменяет тексты лицензий конкретной поставки.

### Обновление источников уведомлений

`scripts/security/julia-notice-sources.json` закрепляет проверенный runtime commit и источник THIRDPARTY. При обновлении SDK сначала пересматривают эту запись, затем собирают промежуточный `notice-input-runtime`: он позволяет исследовать новый SDK до обновления индекса. Конечный образ всегда выполняет проверку уведомлений.

```sh
docker build --target notice-input-runtime -f backend-julia/Dockerfile -t enersy-julia-notice-input .
python -B scripts/security/update-julia-notices.py --image enersy-julia-notice-input
docker compose build julia-compute
```

Обновляющий инструмент использует Python 3.11+ только для разработки; запуск приложения не требует Python на компьютере пользователя. Тестовый Compose-профиль закрепляет Python 3.12.13. Для офлайн-анализа можно передать ранее полученный снимок через `--facts FILE`. Инструмент читает SDK через Docker, выбирает архивы из его метаданных, проверяет SHA-256 загрузок, извлекает только обычные UTF-8 файлы `share/licenses/` и сравнивает хеши библиотек потоком. Архивный код не запускается, бинарники не устанавливаются, ссылки и опасные пути отклоняются. Имеющийся проверенный текст с другим содержимым не перезаписывается автоматически.

Небольшие оригинальные уведомления и индекс хранятся в `scripts/security/julia-notices/` и копируются в образ. Архивы остаются в исключённом `.cache/julia-license-artifacts/`; пользовательские материалы и резервные копии в сборку не включаются. Обновлённые метаданные, происхождение и открытые расхождения проверяются перед принятием нового индекса.
