## Фазы журнала v2 — 2026-10-18 {#editor-journal-phases-2026-10-18}

`formatVersion: 2` устраняет ограничение v1 для команд, ожидающих подготовки в очереди. Каждый элемент `graph` содержит обязательные `phase`, `intent`, `reason`. Намерения оборудования в `components` сохраняют прежнюю структуру и историческую базу. Типы и runtime-декодер находятся в `frontend/src/api/editor-draft-phases.ts`; Go проверяет те же правила в `editor_draft_payload.go`.

| Фаза структурной записи | Что известно | Правило ревизии связи |
| --- | --- | --- |
| `unprepared` | Исходное намерение, но нет сохранённых данных подготовки транспортом | `expectedTopologyRevision` отсутствует; даже null или «0 по умолчанию» запрещены |
| `prepared` | Транспорт зафиксировал точные данные перед сетевой мутацией | Для создания/удаления связи обязательна каноническая строка signed BIGINT, включая явно выбранный «0» |

Для создания оборудования обе фазы содержат тип/паспорт, название, координаты, поворот и параметры запроса; CAS топологии у этой команды отсутствует. UUID создания связи уникален во всём журнале, независимо от фазы. Неизвестные фазы/поля, лишний CAS у unprepared, пропущенный CAS у prepared, дубли UUID, неподдержанная версия и превышение общих лимитов отклоняются. `unprepared` **не доказывает, что мутация не выполнялась**: это также возможно при старом транспорте или отсутствии сохранённого подтверждения подготовки. `prepared` не означает отправку или commit. Подтверждённые/явно разрешённые записи снимаются из очереди, а не получают фиктивный статус успеха в журнале.

`captureEditorJournal` теперь возвращает v2. Внутри preflight callback первой команды можно получить весь журнал: первая запись уже prepared, а следующая, ещё ожидающая той же FIFO, остаётся unprepared. Снимок не ждёт выбора её CAS и не выбрасывает намерение. Для старой неполной записи создания оборудования, где не зафиксированы поворот/параметры, экспорт по-прежнему откажет вместо подстановки значений. Текущий hook записывает эти поля явно.

`parseStoredEditorDraftPayload` и `encodeStoredEditorDraftPayload` поддерживают обе версии; HTTP-клиент читает и сохраняет их. Прежние `parseEditorDraftPayload`/`encodeEditorDraftPayload` остаются декодером/кодировщиком именно v1. При восстановлении v1 его структурные записи интерпретируются как prepared, сохраняя исходные данные и CAS. Восстановленные v2 unprepared остаются заблокированными для расчёта/повтора: нельзя загрузить новую топологию и незаметно назначить её ревизию старой команде. После явной сверки можно принять серверный граф и сформировать отдельное новое намерение. Prepared-связь повторяется прежним явным механизмом с исходными UUID/body/If-Match.

Миграция `20261018001_editor_draft_phases` расширяет ограничение JSONB-конверта до v1/v2. Прежняя миграция `20261010006` не менялась. Аккаунт/scheme/workspace, ревизии журналов, лимиты размера/квоты и tombstone сохраняют прежний контракт. Up меняет только CHECK; down предварительно отказывает, если сохранились payload v2, без их удаления или переинтерпретации. Это не штатный способ отката пользовательских данных. Основная пользовательская БД на этом этапе не обновлялась; миграция применена на отдельном тестовом стенде.

Проверено в Docker: Go vet/полный race-набор с PostgreSQL, миграции пустой/legacy-БД и отдельный переход старого ограничения → новое. Полное содержимое строк v1 (payload, ревизии и временные метки) сравнивается до/после обновления; отказ downgrade проверяется с сохранением строк v1/v2. Общие JSON-фикстуры v1/v2 приняты Go и TypeScript. Frontend typecheck/lint/205 тестов/build прошли, включая смешанную очередь перед отправкой и запрет повтора unprepared после восстановления. Настоящий HTTP-клиент сохранил/прочитал обе фазы, подтвердил неизменность физической схемы и повтор prepared-связи без дубликата; прежний `Test-AuthSessions.ps1` также прошёл на новой схеме БД. HTTP-обёртка моделирует потерю ответа после commit, а не разрыв TCP; cookie-контексты стенда не являются браузерной приёмкой. Новый удалённый CI-запуск не подтверждён.

Следующий этап — уведомления об изменениях журнала, менеджер сохранения с CAS и обработкой потерянных подтверждений, отдельный UUID рабочего контекста и UI явного восстановления. Сам формат v2 ещё не включает автосохранение и не гарантирует сохранность при закрытии вкладки. Сценарии reload, клонирования, смены аккаунта, срок хранения и очистка истории остаются в USER-02.

## Снимок и восстановление очередей — 2026-10-18 {#editor-queue-journal-2026-10-18}

`frontend/src/features/projects/editor-journal.ts` связывает wire-формат с очередями. `captureEditorJournal(queue, schemeId)` синхронно получает глубокие копии всех неподтверждённых намерений выбранной схемы, включая операции в работе. Только подтверждение, явное принятие серверной версии или завершённый проверенный повтор снимают соответствующие записи. Подтверждённый предшественник обновляет исходную базу оставшихся намерений оборудования; простая перезагрузка схемы её не заменяет. Выборочное разрешение не удаляет чужие или ещё не рассмотренные намерения.

Приватный `SchemeTransport` перед отправкой структурной команды вызывает необязательный `GraphDispatchCapture`. Для создания оборудования передаются точные тип/паспорт, положение/поворот и параметры запроса; для создания связи — UUID, концы/порты и выбранный исходный CAS; для удаления связи — ID и исходный CAS. Каждая попытка привязана к своей записи очереди: два неподтверждённых удаления одного ID сохраняют разные ревизии. Callback может быть асинхронным: транспорт ждёт его завершения до сетевой мутации. Очередь проверяет соответствие исходному намерению, копирует данные и запрещает изменение завершённой попытки. Мутация пользовательского объекта параметров или копии, выданной callback, не меняет уже подготовленную команду.

Hook редактора передаёт callback для создания оборудования/связи и удаления связи; общий legacy API остаётся совместимым, но не выдаёт доказательства приватного CAS. Снимок очереди с такой неподготовленной командой явно отклоняется. Никакие записи журнала на сервер из hook пока автоматически не отправляются.

`restoreProjectEditorJournal(options, payload)` сначала проверяет весь payload, затем создаёт новую `ComponentWrites` и новый транспорт для указанного проекта/схемы. Promise, разрешения прежних диалогов сверки, выделение и оптимистическое состояние вида не восстанавливаются. Все импортированные намерения становятся спорными; пустая причина заменяется сообщением о необходимости сверки. Само восстановление не читает и не меняет сервер. Следующая явная загрузка проверяет доступ и даёт фактическое состояние, сохраняя историческую базу намерений. Вызывающий код обязан брать payload из запроса текущего аккаунта и родительского scope; функция не подтверждает личность и не является импортёром произвольного файла.

Восстановленные попытки создания связи сохраняют исходные UUID, данные и топологическую ревизию в новом транспорте. Только явный проверенный повтор из диалога сверки может отправить их; новая ревизия после загрузки не подставляется вместо исходной. После подтверждения команды всё равно требуется новый полный граф, и только затем снимается запись/барьер расчёта. Создание оборудования и удаления не получают автоматического повторного выполнения.

**Ограничение перед подключением автосохранения:** wire-формат v1 требует CAS для структурной связи, но у команды, ещё ожидающей своей очереди в транспорте, CAS пока не выбран. `captureEditorJournal` в этом случае возвращает ошибку целиком, без частичного сохранения или подстановки ревизии. То же относится к отказу до подготовки команды. Нельзя просто включить сохранение всего журнала внутри preflight callback: за текущей командой могут ждать ещё неподготовленные. Следующий этап должен явно представить фазу до отправки в версионированном формате, сохранив все намерения; после этого нужны уведомления об изменениях, менеджер сохранения/CAS, отдельный UUID контекста, UI выбора восстановления и приёмка reload/клонированных вкладок. Текущая реализация ещё не обеспечивает сохранность при закрытии браузера.

Проверено: Docker typecheck/lint, 200 frontend-тестов и production build; 11 новых регрессий снимков/восстановления, ожидание подготовки, копирование параметров, исторические базы, отдельные CAS одинакового ID, выборочное снятие и запрет неподготовленного экспорта. Настоящий `Test-EditorDraftClient.ps1` дополнительно проверил очередь потерянного создания связи → сохранение журнала → чтение другой сессией → новый контекст/сверка → явный повтор. Оба POST связи имели одинаковые body/UUID/If-Match; сервер сохранил одну связь и неизменный граф после повтора. Потеря подтверждения моделируется отбрасыванием ответа уже после настоящего commit, без разрыва TCP. Данные теста очищены; UI восстановления/автосохранения и новая браузерная приёмка пока отсутствуют. CI-сценарий расширен, удалённый запуск не подтверждён. Численные методы не менялись; USER-02 остаётся открытым.

## Клиент хранилища журналов — 2026-10-18 {#editor-draft-client-2026-10-18}

`frontend/src/api/editor-draft-payload.ts` описывает wire-формат v1 отдельно от renderer и очередей. `parseEditorDraftPayload(unknown)` возвращает независимую глубокую копию; `encodeEditorDraftPayload(unknown)` проверяет данные и предел 256 КиБ перед отправкой. ID оборудования — положительные строки PostgreSQL INTEGER, ID проекта и ревизии — строки signed BIGINT; преобразования через `Number` нет. Все варианты намерений требуют собственные поля: в частности, исходный UUID и `expectedTopologyRevision` связи, поворот и параметры нового оборудования. Кодек не дополняет отсутствующую ревизию текущей и не выводит параметры из каталога.

Проверяются известная версия/поля, обязательные массивы, уникальность оборудования и UUID команд, пределы количества намерений, координат, строк и UTF-8 значений параметров. Непарные UTF-16 суррогаты и NUL отклоняются. Параметр с именем `__proto__` сохраняется как собственное поле и не меняет прототип объекта. Превышение лимитов возвращает ошибку без обрезания журнала. Это структурная проверка исторических намерений; наличие оборудования, портов и действующих прав при восстановлении проверяется отдельно. Кодек принимает уже разобранный объект, не является импортёром произвольного JSON-файла.

`frontend/src/api/editor-drafts-api.ts` предоставляет операции:

| Функция | Результат и условия |
| --- | --- |
| `listEditorDrafts(scope, signal)` | Не более 32 уникальных карточек workspace/revision/updatedAt; payload в списке отклоняется |
| `readEditorDraft(scope, workspaceId, signal)` | Карточка и проверенный payload; UUID ответа и сильный ETag должны совпадать |
| `saveEditorDraft(scope, workspaceId, expected, payload, signal)` | PUT с исходным If-Match; только явное `expected="0"` создаёт новый журнал |
| `deleteEditorDraft(scope, workspaceId, expected, signal)` | DELETE существующего журнала, без тела; нулевая ревизия недопустима |

`scope` содержит projectId/schemeId. Cookie передаётся same-origin, запросы используют no-store, AbortSignal и запрещают перенаправления. Успешная запись подтверждается только точной следующей ревизией и совпадающим ETag. Истечение диапазона BIGINT отклоняется до отправки. Ответ читается потоком с пределом 2 МиБ, включая HTML-экранирование Go; проверяются Content-Type и UTF-8. Отмена после заголовков/во время чтения освобождает поток и не публикует прежний результат. Запреты доступа, конфликт и квота возвращаются как `EditorDraftError`, совместимый с `SessionError`, без отражения приватного тела ошибки в интерфейсе.

Клиент выполняет один запрос без автоматического повтора, удаления или перехода на общий CRUD. После потери подтверждения PUT вызывающий код должен сначала перечитать журнал и решить конфликт явно. Смена аккаунта/контекста требует отмены принадлежащего ему signal; API не является менеджером жизненного цикла сессий.

Проверено в Docker: typecheck/lint, все 189 frontend-тестов и production build; Go-проверки `TestEditorDraftSharedWireFixture` и `TestEditorDraftPayload`. Общий файл `tests/fixtures/editor-draft-v1.json` проверяется обоими языками и содержит все варианты намерений, Unicode, специальный ключ параметра и ревизии выше 2^53. Mock fetch проверяет отказ/конфликт, потерю ответа, отмену и лимит потока. Отдельный настоящий HTTP-сценарий самого TypeScript-клиента подтвердил два аккаунта/три сессии, точный payload, потерю ответа после commit без повтора PUT, перечитывание подтверждённого журнала, конфликт старой версии, неизменность физической схемы, tombstone и сохранение второй сессии после выхода первой. Тестовые проекты и аккаунты удалены. Браузерная приёмка UI пока не проводилась.

Повторить настоящий клиентский сценарий можно в отдельном стенде, из корня репозитория:

```powershell
docker compose -f tests/integration/revision-compose.yml up -d --wait postgres go-api
docker compose -f tests/integration/revision-compose.yml --profile draft-client build editor-draft-client-check
./tests/integration/Test-EditorDraftClient.ps1
docker compose -f tests/integration/revision-compose.yml --profile draft-client down
```

Скрипт создаёт временные учётные записи через CLI тестового API и очищает только принадлежащие им данные; адрес сервиса и тестовая БД фиксированы. Контейнер клиента получает отдельные cookie-контексты через HTTP-обёртку стенда, это не проверка браузерного cookie jar. Обёртка намеренно отбрасывает успешный ответ PUT уже после настоящего commit; физический разрыв TCP этим тестом не моделируется. Один HTTP-тест пропускается в обычном frontend-наборе и запускается отдельно профилем `draft-client`; этот шаг добавлен в Docker job CI. Новый удалённый CI-запуск не подтверждён.

Очереди редактора пока не вызывают этот API. Следующий этап — сохранять исходные базы и CAS транспортных попыток, сериализовать обе очереди, подключить отдельный UUID каждого рабочего контекста и явное восстановление после reload. Клонирование вкладки, автосохранение, экспорт/импорт файла и lifecycle/очистка истории остаются в USER-02; эпик открыт.

## Хранилище приватных журналов редактора — 2026-10-10 {#editor-draft-storage-2026-10-10}

Серверное хранилище добавлено миграцией `20261010006_editor_drafts`. Это основа USER-02 для будущего сохранения намерений после перезагрузки, **не подключённое автосохранение UI**. Существующие очереди редактора пока остаются в памяти. Текущий протокол хранит исходное состояние и команды, но не применяет их к физической схеме, не повторяет расчёт и не подтверждает выполнение исходной команды.

Область журнала: аккаунт действующей сессии + фактически принадлежащая проекту схема + UUID рабочего контекста. UUID не даёт права доступа. Участник, включая owner/admin общего проекта, читает только собственные журналы; два аккаунта могут использовать одинаковый UUID независимо. Разные сессии одного аккаунта могут явно открыть один журнал, тогда их правки защищаются отдельным CAS. Будущий UI должен создавать независимые UUID для отдельных контекстов вкладок и предложить явный выбор восстановления, а не назначать один глобальный активный черновик.

| Маршрут относительно `/api/projects/{projectId}/schemes/{schemeId}/drafts` | Контракт |
| --- | --- |
| `GET` | `{items:[{workspaceId,revision,updatedAt}]}` собственных активных журналов этой схемы; без payload |
| `GET /{workspaceId}` | Та же карточка с payload, ETag ревизии |
| `PUT /{workspaceId}` | Полный payload формата v1, обязательный If-Match; `"0"` только для создания; 200 с workspaceId/revision/updatedAt и ETag |
| `DELETE /{workspaceId}` | Обязательная текущая ревизия; удаляет payload, возвращает новую revision/ETag и сохраняет метку удаления UUID |

Чтение доступно owner/admin/editor/viewer при текущем праве на схему; сохранение — owner/admin/editor. Viewer может удалить только собственный ранее созданный журнал. После удаления членства даже собственный сохранённый payload недоступен через проектный путь. Отзыв/истечение сессии, отключение аккаунта, чужой проект или схема дают общий 404; отсутствующая/некорректная cookie — 401. Применяются точный Origin и no-store. Отсутствующая ревизия — 428, неверная форма — 400, конфликт — 412 `editor_draft_revision_conflict`. UUID — каноническая строка lowercase; ID и ревизии внутри payload — десятичные строки без округления.

Минимальный payload:

```json
{"formatVersion":1,"components":[],"graph":[]}
```

`components` содержит `{componentId,base,intents,reason}`. Base сохраняет id/typeId/type/equipmentModelId/revision/name/x/y/rotation/params. Intents: `pose` с частичными values x/y/rotation/name, `parameter` с key/value или `delete`. `graph` содержит `{intent,reason}`: `create-component` с typeId/name/x/y/rotation/params и необязательным equipmentModelId; `create-connection` с commandId/from/to/fromPort/toPort/expectedTopologyRevision; `delete-connection` с id/expectedTopologyRevision. Для создания связи обязательно сохраняется исходный UUID и исходная топологическая ревизия. Наличие записи в журнале не доказывает существование связи сейчас. Потерянное подтверждение сохранения самого журнала требует чтения и сравнения, а не слепого повтора с новой ревизией.

Сервер проверяет версии/виды намерений, известные поля с точным регистром, уникальность componentId и commandId, форму ID/ревизий, конечную геометрию и ограниченные строки. Допускаются параметры с пустыми значениями и исторические ссылки на уже отсутствующие объекты: будущая сверка должна прочитать текущий защищённый граф и проверить реальный объект/тип/паспорт до любой записи. Журнал не является физической верификацией параметров, единиц, портов или математической модели. Дополнительный JSON, повторяющиеся ключи, чрезмерная вложенность, неверный UTF-8 и непарные UTF-16 escapes отклоняются без замены значения.

Фиксированные пилотные пределы: 256 KiB HTTP-payload, до 128 компонентных и 128 структурных записей, до 64 намерений на объект, причина до 1024 символов. PostgreSQL дополнительно ограничивает размер JSONB-представления 512 KiB. На аккаунт разрешено 32 активных журнала и 256 строк с учётом меток удаления. Создание сверх предела даёт 409 `editor_draft_quota`; существующие журналы можно обновлять и удалять. Квота сериализуется account-wide advisory lock, включая разные схемы; права повторно проверяются после ожидания. Метка удаления запрещает повторное создание прежнего UUID и стирает payload; ревизия не обнуляется. Очистка меток/удалённых членств, настройка квот, срок хранения и UI управления журналами ещё не реализованы: достижение общего предела требует будущего административного сценария, а не удаления истории вслепую.

Проверено: полный Docker Go vet/race с настоящей PostgreSQL; миграции пустой и legacy-БД; приватность между разрешёнными участниками, одинаковый UUID разных аккаунтов, отдельная сессия после отзыва другой, истечение/отключение, конфликт конкурентных PUT, ожидание блокировки и удаление редактора, concurrent quota разных схем, tombstone и SQL-ограничения конверта. `Test-AuthSessions.ps1` проверяет настоящие Docker HTTP login/CRUD: два аккаунта/три сессии, полный payload, исходный UUID, CAS, неизменность физического графа, удаление и отзыв доступа. Проверка включена в существующий CI-сценарий; удалённый запуск нового расширения ещё не подтверждён. Фикстуры сценарий удаляет сам. UI автосохранения, экспорт/импорт обеих очередей, обработка клонированных вкладок и ручное восстановление после reload остаются следующими задачами; USER-02 не завершён.

## Адресная проверка выбранного проекта — 2026-10-10 {#адресная-проверка-выбранного-проекта-2026-10-10}

`GET /api/projects/{projectId}` возвращает id/name/role/createdAt доступного проекта без обхода страниц. ID — каноническая положительная строка signed BIGINT; путь и JSON не округляются в JavaScript. Один SQL-запрос проверяет действующую сессию, отключение аккаунта и owner/членство. Неверная сессия даёт 401; отсутствующий или чужой проект — одинаковый 404 без имени/роли. Метод только GET, ответы no-store. Авторизация следующих мутаций остаётся независимой: карточка проекта не предоставляет право записи.

При focus UI сначала проверяет сессию. Для прежнего аккаунта/sessionId параллельно читает первую страницу и выбранный проект по ID. Прежние ID/роль сохраняют тот же mount редактора независимо от страницы; изменение имени обновляет карточку. Другая сессия не читает прошлый выбранный ID. 404 выбранного проекта сбрасывает редактор, сохраняя доступный список; другие ошибки скрывают прежний контекст. Это заменяет ограничение проверки только первой страницы из предыдущего этапа.

Глобальные горячие клавиши редактора проверяют его DOM-контекст: скрытый, inert, закрывающийся или размонтированный редактор не запускает Delete/Backspace и не перехватывает фокус. Поля ввода, модальные окна и элементы другого рабочего пространства также исключены; проверка покрыта DOM-регрессиями. Уже отправленные запросы по-прежнему независимо проверяются сервером.

Проверено: Docker Go vet/полный race-набор с PostgreSQL, Docker typecheck/lint/175 frontend-тест/build, настоящий HTTP (свой проект 200/no-store, неизвестный 404). Регрессии охватывают все роли, удалённое членство, чужой/неканонический ID, отдельную действующую сессию после отзыва другой, отключённый аккаунт, отмену и ID выше 2^53. Браузер подтвердил отзыв активного приватного редактора: следующий расчётный запрос убрал граф и вернул вход. Сохранение редактора вне первой страницы проверено регрессией UI, а не отдельным браузерным сценарием. USER-01/02/03 остаются открытыми.

## Серверная основа — 2026-10-10

Миграция `20261010001_auth_sessions` и `backend-go/sessions.go` добавляют хранилище отзываемых сессий. Вход/чтение/выход, проекты, участники и создание/чтение проектных схем подключены к HTTP (разделы ниже). Старые схемы без проекта остаются общими; каталог и вычислительные задания **ещё не разделены пользовательскими правами**. USER-01/02/03 остаются открытыми. Демонстрационная таблица `users(name)` сохранена, её Alice/Bob не становятся учётными записями.

`auth_accounts` хранит отдельный ID, отображаемое имя, дату создания и признак отключения. Отображаемое имя не является логином и может повторяться. Локальные учётные данные хранятся отдельно в `auth_local_credentials`; регистрационного HTTP-маршрута и привязки к внешнему провайдеру пока нет. Миграция не создаёт тестовых аккаунтов и не назначает владельцев старым схемам.

`auth_sessions` хранит ID сессии, ссылку на аккаунт, SHA-256 хеш 32 случайных байт, срок действия и дату отзыва. Исходный секрет — канонический Base64URL без padding, 43 символа — возвращается только при выпуске и не сохраняется в БД. ID аккаунта/сессии не является секретом и не даёт доступ. Генерация использует `crypto/rand`; SHA-256 здесь применяется к случайному токену, это не алгоритм хранения пароля. Срок в Go-контракте — от секунды до 30 суток; времена проверки берутся из PostgreSQL, а не часов браузера.

| Операция | Поведение |
| --- | --- |
| `Issue` | Выпуск после доверенного подтверждения личности; отсутствующий/отключённый аккаунт отклоняется |
| `Authenticate` | По хешу возвращает аккаунт/сессию/срок; истечение, отзыв или отключение аккаунта блокируют результат |
| `Revoke` | Проверяет действующий токен инициатора и принадлежность целевой сессии в одном SQL; отзыв одной сессии сохраняет остальные |
| `RevokeAll` | Проверяет инициатора и отзывает только сессии его аккаунта, включая собственную |

Выпуск по переданному клиентом account ID запрещён: метод `Issue` вызывается HTTP-login только после проверки учётных данных. Неканонические и слишком длинные токены отклоняются до обращения к БД и до выделения буфера декодирования. Отсутствующий токен/аккаунт, чужая цель, истечение и отзыв возвращают общий `session unavailable`; ошибки доступности БД и отмена запроса остаются отдельными ошибками, не превращаются в успешную идентичность. Секреты не включаются в сообщения ошибок.

Повтор отзыва собственной уже отозванной цели допустим, пока инициатор использует другую действующую сессию. Отозванный инициатор больше не может выполнять команды, включая повтор `RevokeAll`. Само отключение аккаунта не переписывает даты отзыва; административные сценарии отключения/повторного включения и ротация токенов ещё не реализованы. Отзыв применяется к последующим проверкам после коммита, он не прерывает уже начавшийся запрос или вычисление. Очистка истории и ограничения числа сессий пока отсутствуют.

## Локальный вход и HTTP cookie — 2026-10-10

Миграция `20261010003_local_credentials` добавляет отдельную таблицу логинов/хешей. Логин нормализуется trim/lowercase, 3–64 ASCII символа `a-z0-9._-`, первый — буква/цифра; уникальность закреплена в БД. Отображаемое имя остаётся отдельным Unicode полем. При создании пароль должен содержать минимум 12 Unicode символов и максимум 1024 UTF-8 bytes, при проверке не обрезается и не нормализуется. Это текущая политика длины; blocklist, восстановление/смена пароля, MFA и внешние identity providers ещё не реализованы.

Хеш — Argon2id, версия 19, 64 MiB, три прохода, четыре потока, случайная соль 16 bytes, ключ 32 bytes, PHC-строка. Используется [официальный пакет Go](https://pkg.go.dev/golang.org/x/crypto/argon2) `golang.org/x/crypto v0.58.0`, совместимый с Go 1.26; память задаётся в KiB. Параметры хеша проверяются до KDF и не могут потребовать произвольную память из текста БД. Ключи сравниваются через `subtle.ConstantTimeCompare`. Неизвестный/отключённый логин выполняет тот же ограниченный KDF и получает тот же 401, что неверный пароль; это не гарантия одинакового времени HTTP. Отмена проверяется до/после KDF, сам Argon2 не прерывается посередине вычисления.

| Маршрут | Контракт |
| --- | --- |
| POST `/api/auth/login` | JSON `{login,password}`, максимум 16 KiB, неизвестные поля/лишний документ отклоняются; 200 с публичной идентичностью и cookie |
| GET `/api/auth/session` | Действующая cookie → accountId/sessionId/expiresAt, иначе 401 |
| POST `/api/auth/logout` | Отзывает текущую сессию и удаляет cookie, 204; другие сессии сохраняются |
| POST `/api/auth/logout-all` | Отзывает сессии текущего аккаунта и удаляет cookie, 204; другие аккаунты не затрагиваются |

ID в JSON — строки для сохранения BIGINT без потери точности. Исходный токен не выдаётся в JSON; срок HTTP-сессии — 24 часа. Cookie: HttpOnly, SameSite=Strict, Path=/, без Domain; по умолчанию Secure и имя `__Host-enersy_session`. Все ответы имеют `Cache-Control: no-store`. Дублирующиеся cookies отклоняются. Для POST обязателен один точный Origin; GET с чужим Origin также отклоняется. Auth CORS использует только точный origin и credentials, не общий wildcard CRUD. Frontend/API должны находиться на одном site для Strict-cookie; текущая конфигурация рассчитана на общий reverse proxy или localhost с разными портами, а не на произвольные разные сайты.

`AUTH_ORIGIN` по умолчанию пуст: auth-маршруты возвращают 503, пока оператор не укажет точный origin без path/query/credentials/wildcard. `AUTH_COOKIE_SECURE` по умолчанию true; только явное `false` выбирает локальную HTTP cookie `enersy_session`. В тестовом Compose задано `AUTH_ORIGIN=http://localhost:4174`, `AUTH_COOKIE_SECURE=false`; это не конфигурация HTTPS-поставки. Корневой Compose передаёт эти настройки из окружения. Текущий API и CRUD не становятся изолированными только от включения login.

Одновременно разрешены два входа с KDF; лишний получает 429/Retry-After вместо неограниченного расхода памяти. Это ограничение параллелизма, не полная защита от перебора: временные/per-account/IP лимиты, число сессий и распределённый admission остаются задачами. Ошибка БД не превращается в неверный пароль: возвращается общий 503 без SQL/секретов.

### Создание аккаунта оператором

HTTP-регистрации и паролей по умолчанию нет. Оператор контейнера может создать аккаунт через `./server -provision-account`: JSON со stdin, без секретов в argv/env. Аккаунт и учётные данные записываются одной транзакцией; конфликт нормализованного логина откатывает создание аккаунта. Ответ содержит только строковый accountId.

Пример PowerShell для уже запущенного обновлённого контейнера (меняет БД):

```powershell
$operatorPassword = Read-Host 'Пароль нового аккаунта' -AsSecureString
$operatorPayload = @{
  displayName = 'Имя пользователя'
  login = 'operator'
  password = [Net.NetworkCredential]::new('', $operatorPassword).Password
}
try {
  $operatorPayload | ConvertTo-Json -Compress |
    docker compose exec -T go-api ./server -provision-account
} finally {
  $operatorPayload.password = $null
  $operatorPassword.Dispose()
}
```

`TestAuthHTTPPostgres` использует реальную PostgreSQL и HTTPS-сервер с отдельными cookie jars: правильный/неверный/неизвестный логин, соль, rollback дубля, cookie policy, три независимые сессии двух пользователей, logout/logout-all, Origin/CORS, тип/размер/форма запроса, admission, отключение и отмена. Docker Go vet/race прошли. `tests/integration/Test-AuthSessions.ps1` прошёл на настоящем контейнерном API: создание двух временных аккаунтов через stdin, три HTTP cookie-сессии, запрет чужого Origin, раздельный/общий выход и неверный пароль. Аккаунты/сессии после проверки удалены, в БД осталось 0/0; сценарий подключён к CI, удалённый запуск ещё не подтверждён. Настоящий Go/PostgreSQL/Julia эталон режима также прошёл в прежних допусках.

Login UI, браузерная приёмка, управление чужими сессиями оператором, привязка legacy-схем и применение guard к CRUD/каталогу/командам/Run остаются открытыми. Рабочий API/пользовательская БД этим этапом не развёртывались; локальная web-документация обновляется отдельно.

## Создание и приватный список проектов — 2026-10-10

`POST /api/projects` принимает JSON `{ "name": "Проект" }` и возвращает `201` с `{ "id": "123" }`. Владелец определяется действующей cookie-сессией в том же SQL, что создаёт проект. Передать владельца через тело запроса нельзя: неизвестные поля отклоняются. Требуются разрешённый Origin и JSON; предел тела — 16 KiB, имени после trim — 1–200 символов.

`GET /api/projects` возвращает `{ "items": [], "nextAfterId": "123" }`: элементы содержат строковые `id`, `name`, `role` и `createdAt`. Видны только собственные проекты и проекты с действующим членством. `limit` по умолчанию 50, допустимы 1–100; `afterId` — неотрицательный BIGINT, курсор по возрастающему ID. ## Синхронный расчёт проекта — 2026-10-10

`POST /api/projects/{projectId}/schemes/{schemeId}/calculate?modelGroup=...&method=...` принимает пустое тело и обязательный `If-Match` топологической ревизии. Оба параметра расчёта задаются явно, по одному значению; неизвестные параметры запрещены. Owner/admin/editor могут запускать расчёт, viewer — нет. Отсутствующая cookie даёт 401, недоступная фактическая схема/проект — 404; отсутствующая ревизия — 428, устаревшая — 412.

Авторизация и граф читаются в одной read-only REPEATABLE READ транзакции. Данные сортируются по ID, транзакция завершается до вызова worker. Перед отправкой входа и перед публикацией полного JSON-ответа права проверяются снова. Удалённый участник или отозванная сессия не получает готовый результат. Worker не получает cookie, токен или учётную запись пользователя.

Ответ сохраняет статус и исходные JSON-байты worker, включая числовую точность. Заголовки `X-Enersy-Input-SHA256`, `X-Enersy-Topology-Revision`, `X-Enersy-Project-Id`, `X-Enersy-Scheme-Id` описывают захваченный вход и доступны через CORS; действует no-store. SHA256 относится к точным байтам запроса, включая геометрию и параметры методов, и не доказывает физическую эквивалентность. Изменение параметров или геометрии может менять hash без изменения топологической ревизии. Ответ worker сохраняет прежний числовой контракт ID; новый граф API использует строковые ID.

`TestProjectCalculationPostgres` с настоящей PostgreSQL и контролируемым HTTP-worker проверяет отсутствие вызова при отказах доступа/ревизии/формы запроса, подстановку чужого projectId, неизменный захваченный вход при параллельной записи, обновление следующего входа, точный hash и ответ, отсутствие credentials у worker и отказ удалённому во время расчёта editor. Полный Docker Go vet/race прошёл. Этот тест проверяет транспорт и изоляцию; численные алгоритмы не менялись. Новый проектный маршрут проверен через настоящие Docker Go/PostgreSQL/Julia: Test-GoJuliaReference.ps1 -ProjectMode создал приватную схему трансформатора 110/10 кВ через защищённые команды и совпал с независимым эталоном. Допуски: узлы 1e-8 p.u., углы 1e-8 rad, ветви 1e-6 MW/Mvar. Проверены отказ анонимному клиенту и заголовки происхождения; временные аккаунт/проект/граф удалены. Тот же сценарий без ProjectMode подтвердил прежний маршрут. Оба варианта включены в CI; удалённый запуск новой проверки ещё не подтверждён.

Это синхронный маршрут с прежним ограничением worker 25 секунд, без сохранённого Study/Run, очереди, квот и аудита авторства. HTTP cancellation не гарантирует остановку вычислений worker. UI, постоянные снимки исследований и управление заданиями остаются открытыми; ранние разделы отражают последовательные этапы реализации. Основной API и пользовательская БД при этих проверках не развёртывались.

## Клиент команд и проектный адаптер редактора — 2026-10-10

`project-scheme-api.ts` реализует защищённые команды оборудования, связей и расчёта. Wire ID и ревизии остаются строками; ID графа ограничены текущим SQL INTEGER, ревизии — PostgreSQL BIGINT. Все запросы используют same-origin cookie, no-store и AbortSignal. Отказ, некорректное подтверждение или отмена не превращаются в успех. Для оборудования/связей проверяется ETag, для связи — исходный UUID и явный deleted, для результата — projectId/schemeId/topologyRevision и SHA-256 входа. `createProjectEditorTransport` связывает существующий редактор с одной приватной схемой на время одного mount. Структурные команды сериализуются общей очередью адаптера, отдельно от очередей объектов. После подтверждения создания/удаления оборудования или связи перечитывается полный граф. Состав оборудования и концы/порты связей должны точно совпасть с ожидаемым результатом команды; посторонняя структурная правка или потерянное чтение блокирует следующие структурные команды и расчёт до явной сверки. Геометрия и параметры защищаются отдельным CAS объекта. Это дополнительное полное чтение после каждой структурной команды; оптимизация для больших схем ещё не реализована.

Неопределённая команда связи сохраняет исходные UUID, payload и If-Match в памяти адаптера. После явной сверки повтор использует те же данные и может вернуть историческое deleted-подтверждение. Применять его как новую связь нельзя: существующий сценарий восстановления снова читает серверный граф. Подтверждённый первоначальный ответ также сверяется с текущим графом; старое topologyRevision из replay не подменяет текущую ревизию. Долговременное сохранение команд/черновиков остаётся открытым.
