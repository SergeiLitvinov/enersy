## Создание с единицами: форма и восстановление — 2026-11-02 {#creation-unit-recovery}

Object-based SDK `createComponent(input)` передаёт явные `params` и `parameterUnitDeclaration`, сохраняя прежний позиционный `addComponent`. Приватный транспорт копирует обе карты до ожидания очереди, фиксирует UUID/CAS и исходную декларацию до POST. GraphWrites проверяет соответствие отправляемой команды намерению, журнал v1/v2 сохраняет декларацию. При восстановлении замена единицы меняет намерение и запрещает повтор. Ответ должен подтвердить точные строки и единицы; отсутствие подтверждения не вызывает автоматического повторения. До сверки топологии hook блокирует новое добавление, включая публичный транспорт; потерянный ответ не превращается в новую команду при повторном нажатии кнопки.

Диалог добавления теперь передаёт [параметры экземпляра](../guide/editor.md#creation-parameters) этим путём. Шаблон не заполняет значения или декларацию. Числовая строка или числовое поле шаблона требует единицы, безразмерное — `1`; текстовый параметр может остаться без единицы. Проверки ввода не заменяют физическую валидацию выбранной модели. Общий справочник не получает задним числом единицы для полей без явного override; версия проектного паспорта сохраняет собственные обозначения остальных полей.

Docker typecheck/lint/build и 607 frontend-тестов прошли; два opt-in HTTP-теста обычным прогоном пропущены. Отдельно выполнен `Test-EditorDraftClient.ps1` на одноразовом стенде `enersy-create-form`: две независимые сессии владельца и посторонний аккаунт, потеря ответа после реального commit создания, сохранение actual queue в серверном журнале, чтение второй сессией и явный повтор. Подтверждены одинаковые POST body/UUID/CAS, ровно один новый объект, точные `voltage_nom="110000.0000"` / `В`, отказ постороннему 404 и снятие расчётного барьера после чтения графа. Тест удалил свои аккаунты и проекты. Unit-регрессии отдельно проверяют копирование входных карт, запрет смены единицы при повторе и историческое подтверждение уже удалённого объекта.

Браузерный навык на этом же отдельном стенде подтвердил отказ числовому `p="1.2300"` без единицы, создание после ввода `МВт`, повторное открытие сохранённой схемы с точной строкой и обозначением; затем создание из общего паспорта с override `p="2.5600"` / `МВт` и сохранением остальных строк `q="4.0"`, `voltage_nom="10.0"` без присвоения единиц. Рабочий стенд и его схемы при приёмке не менялись. Расчётный worker на тестовом стенде не запускался: численная корректность этой проверкой не заявляется. Локальные отчёты: `.cache/create-form-check.log`, `.cache/create-form-http-acceptance.log`, `.cache/creation-parameters-form.jpg`, `.cache/creation-parameters-saved.jpg`.

Остаются расширение MCP/harness, браузерная приёмка приватных паспортов с override, работа с размерами/SI/p.u. и обязательность контракта для всех внешних клиентов. CORE-01 не закрыт.

## Единицы атомарного профиля нагрузки — 2026-11-02 {#load-profile-unit-declarations}

Форма PQ/ZIP требует явной декларации единиц действующего AC-профиля перед сохранением: МВт, Мвар, кВ и `1`. Все десять значений и обозначений отправляются вместе. Сохранённые единицы показываются до выбора декларации, включая отдельные доли ZIP; при замене обозначений выводится предупреждение без изменения числовых строк. Пустые неактивные поля получают обозначение, но не числовые defaults. Подтверждение собственной записи принимается как целая пара и не вызывает ложного конфликта. Следующий локальный ввод не стирается при последующем принятии другого поля. Чужое изменение единиц после подготовки декларации блокирует её применение.

Проверена собственная анонимная схема №42 с нагрузкой №26; для физической проверки через API добавлены синтетический источник №27 и связь №48. UI не сохранял профиль до установки декларации. PQ сохранил точные строки `10.0000`, `3.0000`, `10.0000`; ZIP не подставлял шесть долей — вручную заданы обе тройки `1.0000/0.0000/0.0000` (постоянное сопротивление). HTTP-чтение подтвердило все десять единиц и неизменность строк. В обоих реальных расчётах Go→Julia ответ подтвердил профиль `legacy-ac-three-phase-rms-v1`, два компонента и 15 параметров, включая пять явно объявленных параметров источника.

Независимые эталоны для линейной RMS-ЭДС 10 кВ, фазного Z = 0,1 + j0,5 Ом и трёхфазной нагрузки 10 + j3 МВА:

| Профиль | Независимая формула | Напряжение, кВ | Ошибка U, кВ / угла, рад |
| --- | --- | --- | --- |
| PQ | V/E = a − j0,047; a = (1 + √(1 − 4·0,025 − 4·0,047²))/2 | 9,73143059984497 | 2,56·10⁻¹⁰ / 1,43·10⁻¹¹ |
| ZIP, обе части чисто Z | V = E / (1 + Z·conj(Sном)/Uном²) | 9,74585732567213 | 1,18·10⁻¹⁰ / 5,67·10⁻¹² |

Допуски заданы заранее: 10⁻⁸ кВ по модулю и 10⁻⁹ рад по углу. Это проверка цепочки сохранённого UI-профиля/единиц/API/worker для двух выбранных случаев, не новое доказательство всех ZIP-сочетаний, машин или переходных процессов.

Отдельный HTTP-клиент изменил только единицу P с МВт на W при том же `10.0000`. Попытка формы сохранить `12.0000 МВт` по старой ревизии отклонена. Сверка сохранила обе пары и заблокировала применение локального P; расчёт был недоступен. Принятие серверных полей и явное восстановление формы сняли конфликт и сбросили декларацию. После смены на W расчёт не запускался: этот шаг проверяет конфликт метаданных, не преобразование МВт↔Вт.

В отдельной анонимной схеме №43 с нагрузкой №28 повторное сохранение неизменённого PQ-профиля подтвердилось без конфликта и сохранило ревизию 21 и все десять пар. Отдельная регрессия проверяет, что маркер такого подтверждения не стирает следующий черновик при последующей сверке другого поля.

Локальные доказательства: `.cache/load-units-pq-server.json`, `.cache/load-units-physical-verification.json`, `.cache/load-units-zip-verification.json`, `.cache/load-units-ui-check.log`. Численное ядро, API и структура БД этим изменением не менялись. Приватные роли/сессии, все формы создания, обязательность внешних API и общий SI/p.u.-контракт остаются в CORE-01.

## Явные единицы обычных числовых полей — 2026-11-02 {#ordinary-numeric-units}

Обычные строки с `type=number` в рабочем инспекторе используют атомарный PATCH значения и декларации единицы. Без декларации поле доступно только для чтения; пустое поле показывает «Не задано», а не числовой default шаблона. Кнопка «Ед.?» открывает форму сразу на выбранном ключе. Подсказка единицы остаётся подсказкой, без автоматического подтверждения старых данных. После задания единицы обычная правка числа отправляет ту же явно выбранную единицу вместе с точной строкой значения. Ошибка операции показывается рядом с полем и не стирает введённый текст; журнал сохраняет намерение для сверки.

Проверена реальная анонимная вкладка `http://localhost/`, собственная синтетическая схема №41 и единственная линия №25. Это не приватная многопользовательская приёмка; конкурирующая запись выполнена отдельным HTTP-клиентом:

| Действие | Подтверждённый результат |
| --- | --- |
| Добавление линии вручную | Пустые параметры не получили единиц из текущего шаблона; обычные числовые поля доступны только для чтения |
| Нажатие кнопки у длины | Форма выбрала `length`, единица осталась пустой при подсказке «км» |
| Ввод `5.0000 km` и отмена | Повторно открытая форма осталась пустой; отменённая пара не записалась |
| Сохранение `5.0000 km`, затем правка числа при выходе из поля | API вернул точную пару `6.2500 km`, ревизию 4; других параметров не записано |
| Ввод локального `6.5000 km`, смена серверной пары на `6.2500 m` | Устаревшая запись отклонена. В сверке база `6.2500 km`, локальное `6.5000 km`, серверное `6.2500 m`; применение локального числа и расчёт заблокированы |
| Принятие серверной пары | Поле показывает `6.2500 m`, сообщения конфликта сняты, расчёт снова доступен; отклонённая строка не записана |

Визуально проверены светлая тема и обычный viewport 1280×720; длинные обозначения в компактной кнопке сокращаются с полной подсказкой. Нативные типы boolean и прежний callback изолированных компонентов без атомарного API сохраняют прежний путь. Регрессии проверяют отсутствие записи без единицы, выбор конкретного поля, сохранение точной строки и единицы, сохранность отклонённого ввода и запрет применения после смены единицы.

Область этого этапа ограничена обычными числовыми строками рабочего редактора; [профиль нагрузки проверен отдельно](#load-profile-unit-declarations). Создание из общего каталога, внешние API и неоднозначные старые записи ещё требуют общего обязательного контракта. Сохранение `m` здесь проверяет метаданные и конфликт, а не поддержку этой единицы AC-моделью линии. Расчёты, пересчёт km↔m, приватные роли, восстановление после reload и все типы оборудования этим сценарием не подтверждены. CORE-01 остаётся открытым.

## Браузерная проверка единиц и сверки — 2026-11-02 {#unit-browser-acceptance}

На настоящем Docker API/PostgreSQL выполнен браузерный сценарий в двух вкладках анонимного редактора. Создана отдельная синтетическая схема с одной нагрузкой; использованы только её параметры. Это две вкладки одного origin, не разные авторизованные пользователи или приватные проекты.

| Сценарий | Подтверждённое поведение |
| --- | --- |
| Явное сохранение пары `0.2000 MW` | Строка сохранилась без округления, профиль нагрузки показал `MW` вместо подписи текущего шаблона `МВт` |
| Вкладка A вводит `0.3000 MW`, вкладка B сохраняет `0.2000 kW` | Сохранение A по старой ревизии отклонено; сверка показала базовую, локальную и серверную пары |
| Выбрано локальное значение с изменённой единицей | «Применить мои значения» недоступно; прежнее число не перенесено в новую единицу |
| Есть неподтверждённые правки | Кнопка «Рассчитать» теперь недоступна и объясняет причину; раньше она выглядела доступной, хотя отдельный guard обработчика запрещал запуск |
| Все тестовые намерения приняты с сервера | Предупреждение снято, блокировка кнопки по этому основанию снята; на сервере осталась только `p="0.2000"`, единица `kW`, ревизия 6, без добавления q/ZIP-полей |
| Окно сужено с 1440×1000 до 763×884 | Открытый инспектор и несохранённая пара `123.4500 MW` сохранились. Раньше обработчик resize закрывал инспектор и размонтировал форму |

При переходе в узкую раскладку автоматически скрывается каталог, инспектор сохраняется. Светлая и тёмная темы проверены визуально; после проверки возвращены исходная светлая тема и снят временный viewport override. Несохранённый демонстрационный ввод отменён. Собственная схема удалена через API с проверкой исходного имени, ID компонента и неизменности параметров; последующий GET вернул 404. Остальные схемы не удалялись. Скриншот формы включён в [руководство](../guide/editor.md#parameter-unit-input).

После исправлений прошли Docker production build, TypeScript, ESLint и 592 frontend-теста; два opt-in теста без своих сервисов пропущены. Проверен только frontend: API, численное ядро, каталог и схема БД не менялись. Расчёты и преобразование MW↔kW этим сценарием не проверялись; сохранение обозначения не означает его поддержку выбранным решателем. Локальные доказательства — `.cache/units-ui-acceptance.json`, `.cache/units-ui-server-state.json`, `.cache/units-ui-resize-{before,after}.json`, `.cache/units-ui-check.log` и `.cache/units-ui-*.jpg`.

Обнаруженная граница: журнал анонимного редактора находится в памяти и не пережил reload. Этот результат не является проверкой восстановления приватного журнала; отдельные механизмы приватных контекстов описаны ниже. Обязательные единицы новых/изменяемых параметров, неоднозначный старый каталог, прочие формы/типы оборудования, приватные вкладки и роли, отзыв доступа, большие журналы и выбор профиля Study остаются в CORE-01/USER-02.

## Смена единиц между сессиями — 2026-10-31 {#unit-session-acceptance}

Настоящий HTTP-сценарий `frontend/src/api/editor-drafts-http.test.ts` использует TypeScript-клиенты, очереди редактора и Go API с PostgreSQL. Две независимые сессии одного аккаунта разделяют проект и могут читать его приватный журнал; третий, посторонний аккаунт не получает доступа. Контексты cookie привязаны к асинхронному вызову через Node-only помощник, поэтому параллельные Promise-цепочки транспорта не подменяют друг другу сессию. Помощник не импортируется приложением.

| Сценарий | Проверенный результат |
| --- | --- |
| Вторая сессия меняет значение и единицу после чтения первой | Запись первой по старой ревизии получает 412; число, единица и положение на сервере не меняются от отклонённой операции |
| Журнал сохраняется и читается другой сессией владельца | Исходная пара и локальные намерения сохраняются точно; новое чтение схемы не подменяет историческую единицу |
| Восстановление локального значения при сменившейся серверной единице | Очередь блокирует применение до PATCH; отдельная правка положения сохраняется, принятие серверного параметра не отправляет запись |
| Подтверждение намеренной смены единицы потеряно после commit | Журнал сохраняет исходную и намеренную пары; после восстановления совпадение числа и единицы снимает намерение без повторного PATCH |
| Две сессии одновременно отправляют разные пары с одной ревизией | Один ответ 200 и один 412; обе отправки используют исходную ревизию и разные cookie-контексты; сохранена целиком пара победителя |
| Посторонний аккаунт читает журнал или пытается изменить компонент | 404; подтверждённое состояние компонента остаётся прежним |
| Первая сессия выходит | Её запросы получают 401, вторая сессия продолжает работать |

Воспроизведение — [существующий сценарий клиента журналов](#editor-draft-client-2026-10-18) и `Test-EditorDraftClient.ps1` на отдельном Compose-стенде. Проверено локально на `enersy-revision-acceptance-units`: сценарий прошёл, после его очистки accounts/sessions/projects/schemes/drafts — 0, затем тестовые контейнеры удалены. Обычный frontend-прогон пропускает этот opt-in HTTP-тест; отдельный шаг уже включён в Docker CI, но новый удалённый прогон не подтверждён.

Это приёмка двух реальных API-сессий с отдельными cookie-контекстами HTTP-клиента, не двух браузерных вкладок. Потеря подтверждения моделируется отбрасыванием успешного ответа после настоящего commit, без разрыва TCP. Разные роли участников, отзыв прав во время восстановления, большие журналы и браузерный lifecycle остаются открытыми. Численные методы и рабочая БД этим сценарием не затрагиваются.

## Фазы журнала v2 — 2026-10-18 {#editor-journal-phases-2026-10-18}

`formatVersion: 2` устраняет ограничение v1 для команд, ожидающих подготовки в очереди. Каждый элемент `graph` содержит обязательные `phase`, `intent`, `reason`. Намерения оборудования в `components` сохраняют прежнюю структуру и историческую базу. Типы и runtime-декодер находятся в `frontend/src/api/editor-draft-phases.ts`; Go проверяет те же правила в `editor_draft_payload.go`.

| Фаза структурной записи | Что известно | Правило ревизии связи |
| --- | --- | --- |
| `unprepared` | Исходное намерение, но нет сохранённых данных подготовки транспортом | `expectedTopologyRevision` отсутствует; даже null или «0 по умолчанию» запрещены |
| `prepared` | Транспорт зафиксировал точные данные перед сетевой мутацией | Для создания/удаления связи обязательна каноническая строка signed BIGINT, включая явно выбранный «0» |

Для создания оборудования обе фазы содержат тип/паспорт, название, координаты, поворот и параметры запроса; CAS топологии у этой команды отсутствует. UUID создания связи уникален во всём журнале, независимо от фазы. Неизвестные фазы/поля, лишний CAS у unprepared, пропущенный CAS у prepared, дубли UUID, неподдержанная версия и превышение общих лимитов отклоняются. `unprepared` **не доказывает, что мутация не выполнялась**: это также возможно при старом транспорте или отсутствии сохранённого подтверждения подготовки. `prepared` не означает отправку или commit. Подтверждённые/явно разрешённые записи снимаются из очереди, а не получают фиктивный статус успеха в журнале.

`captureEditorJournal` теперь возвращает v2. Внутри preflight callback первой команды можно получить весь журнал: первая запись уже prepared, а следующая, ещё ожидающая той же FIFO, остаётся unprepared. Снимок не ждёт выбора её CAS и не выбрасывает намерение. Для старой неполной записи создания оборудования, где не зафиксированы поворот/параметры, экспорт по-прежнему откажет вместо подстановки значений. Текущий hook записывает эти поля явно.

`parseStoredEditorDraftPayload` и `encodeStoredEditorDraftPayload` поддерживают обе версии; HTTP-клиент читает и сохраняет их. Прежние `parseEditorDraftPayload`/`encodeEditorDraftPayload` остаются декодером/кодировщиком именно v1. При восстановлении v1 его структурные записи интерпретируются как prepared, сохраняя исходные данные и CAS. Восстановленные v2 unprepared остаются заблокированными для расчёта/повтора: нельзя загрузить новую топологию и незаметно назначить её ревизию старой команде. После явной сверки можно принять серверный граф и сформировать отдельное новое намерение. Prepared-связь повторяется прежним явным механизмом с исходными UUID/body/If-Match.

Миграция `20261018001_editor_draft_phases` расширяет ограничение JSONB-конверта до v1/v2. Прежняя миграция `20261010006` не менялась. Аккаунт/scheme/workspace, ревизии журналов, лимиты размера/квоты и tombstone сохраняют прежний контракт. Up меняет только CHECK; down предварительно отказывает, если сохранились payload v2, без их удаления или переинтерпретации. Это не штатный способ отката пользовательских данных. Основная пользовательская БД на этом этапе не обновлялась; миграция применена на отдельном тестовом стенде.

Проверено в Docker: Go vet/полный race-набор с PostgreSQL, миграции пустой/legacy-БД и отдельный переход старого ограничения → новое. Полное содержимое строк v1 (payload, ревизии и временные метки) сравнивается до/после обновления; отказ downgrade проверяется с сохранением строк v1/v2. Общие JSON-фикстуры v1/v2 приняты Go и TypeScript. Frontend typecheck/lint/205 тестов/build прошли, включая смешанную очередь перед отправкой и запрет повтора unprepared после восстановления. Настоящий HTTP-клиент сохранил/прочитал обе фазы, подтвердил неизменность физической схемы и повтор prepared-связи без дубликата; прежний `Test-AuthSessions.ps1` также прошёл на новой схеме БД. HTTP-обёртка моделирует потерю ответа после commit, а не разрыв TCP; cookie-контексты стенда не являются браузерной приёмкой. Новый удалённый CI-запуск не подтверждён.

Сам формат v2 ещё не включает автосохранение и не гарантирует сохранность при закрытии вкладки. Сценарии reload, клонирования, смены аккаунта, срок хранения и очистка истории остаются в USER-02.

## Снимок и восстановление очередей — 2026-10-18 {#editor-queue-journal-2026-10-18}

`frontend/src/features/projects/editor-journal.ts` связывает wire-формат с очередями. `captureEditorJournal(queue, schemeId)` синхронно получает глубокие копии всех неподтверждённых намерений выбранной схемы, включая операции в работе. Только подтверждение, явное принятие серверной версии или завершённый проверенный повтор снимают соответствующие записи. Подтверждённый предшественник обновляет исходную базу оставшихся намерений оборудования; простая перезагрузка схемы её не заменяет. Выборочное разрешение не удаляет чужие или ещё не рассмотренные намерения.

Приватный `SchemeTransport` перед отправкой структурной команды вызывает необязательный `GraphDispatchCapture`. Для создания оборудования передаются точные тип/паспорт, положение/поворот и параметры запроса; для создания связи — UUID, концы/порты и выбранный исходный CAS; для удаления связи — ID и исходный CAS. Каждая попытка привязана к своей записи очереди: два неподтверждённых удаления одного ID сохраняют разные ревизии. Callback может быть асинхронным: транспорт ждёт его завершения до сетевой мутации. Очередь проверяет соответствие исходному намерению, копирует данные и запрещает изменение завершённой попытки. Мутация пользовательского объекта параметров или копии, выданной callback, не меняет уже подготовленную команду.

Hook редактора передаёт callback для создания оборудования/связи и удаления связи; общий legacy API остаётся совместимым, но не выдаёт доказательства приватного CAS. Снимок очереди с такой неподготовленной командой явно отклоняется. Никакие записи журнала на сервер из hook пока автоматически не отправляются.

`restoreProjectEditorJournal(options, payload)` сначала проверяет весь payload, затем создаёт новую `ComponentWrites` и новый транспорт для указанного проекта/схемы. Promise, разрешения прежних диалогов сверки, выделение и оптимистическое состояние вида не восстанавливаются. Все импортированные намерения становятся спорными; пустая причина заменяется сообщением о необходимости сверки. Само восстановление не читает и не меняет сервер. Следующая явная загрузка проверяет доступ и даёт фактическое состояние, сохраняя историческую базу намерений. Вызывающий код обязан брать payload из запроса текущего аккаунта и родительского scope; функция не подтверждает личность и не является импортёром произвольного файла.

Восстановленные попытки создания связи сохраняют исходные UUID, данные и топологическую ревизию в новом транспорте. Только явный проверенный повтор из диалога сверки может отправить их; новая ревизия после загрузки не подставляется вместо исходной. После подтверждения команды всё равно требуется новый полный граф, и только затем снимается запись/барьер расчёта. Создание оборудования и удаления не получают автоматического повторного выполнения.

**Ограничение перед подключением автосохранения:** wire-формат v1 требует CAS для структурной связи, но у команды, ещё ожидающей своей очереди в транспорте, CAS пока не выбран. `captureEditorJournal` в этом случае возвращает ошибку целиком, без частичного сохранения или подстановки ревизии. То же относится к отказу до подготовки команды. Нельзя просто включить сохранение всего журнала внутри preflight callback: за текущей командой могут ждать ещё неподготовленные. Следующий этап должен явно представить фазу до отправки в версионированном формате, сохранив все намерения; после этого нужны уведомления об изменениях, менеджер сохранения/CAS, отдельный UUID контекста, UI выбора восстановления и приёмка reload/клонированных вкладок. Текущая реализация ещё не обеспечивает сохранность при закрытии браузера.

Проверено: Docker typecheck/lint, 200 frontend-тестов и production build; 11 новых регрессий снимков/восстановления, ожидание подготовки, копирование параметров, исторические базы, отдельные CAS одинакового ID, выборочное снятие и запрет неподготовленного экспорта. Настоящий `Test-EditorDraftClient.ps1` дополнительно проверил очередь потерянного создания связи → сохранение журнала → чтение другой сессией → новый контекст/сверка → явный повтор. Оба POST связи имели одинаковые body/UUID/If-Match; сервер сохранил одну связь и неизменный граф после повтора. Потеря подтверждения моделируется отбрасыванием ответа уже после настоящего commit, без разрыва TCP. Данные теста очищены; UI восстановления/автосохранения и новая браузерная приёмка пока отсутствуют. CI-сценарий расширен, удалённый запуск не подтверждён. Численные методы не менялись; USER-02 остаётся открытым.

## Клиент хранилища журналов — 2026-10-18 {#editor-draft-client-2026-10-18}

`frontend/src/api/editor-draft-payload.ts` описывает wire-формат v1 отдельно от renderer и очередей. `parseEditorDraftPayload(unknown)` возвращает независимую глубокую копию; `encodeEditorDraftPayload(unknown)` проверяет данные и предел 256 КиБ перед отправкой. ID оборудования — положительные строки PostgreSQL INTEGER, ID проекта и ревизии — строки signed BIGINT; преобразования через `Number` нет. Все варианты намерений требуют собственные поля: в частности, исходный UUID и `expectedTopologyRevision` связи, поворот и параметры нового оборудования. Кодек не дополняет отсутствующую ревизию текущей и не выводит параметры из каталога.

Проверяются известная версия/поля, обязательные массивы, уникальность оборудования и UUID команд, пределы количества намерений, координат, строк и UTF-8 значений параметров. Непарные UTF-16 суррогаты и NUL отклоняются. Параметр с именем `__proto__` сохраняется как собственное поле и не меняет прототип объекта. Превышение лимитов возвращает ошибку без обрезания журнала. Это структурная проверка исторических намерений; наличие оборудования, портов и действующих прав при восстановлении проверяется отдельно. Кодек принимает уже разобранный объект, не является импортёром произвольного JSON-файла.

`frontend/src/api/editor-drafts-api.ts` предоставляет операции:

| Функция | Результат и условия |
| --- | --- |
| `listEditorDrafts(scope, signal)` | Не более 32 уникальных карточек workspace/revision/updatedAt; payload в списке отклоняется |
| `readEditorDraft(scope, workspaceId, signal)` | Карточка и проверенный payload; UUID ответа и сильный ETag должны совпадать |

`scope` содержит projectId/schemeId. Cookie передаётся same-origin, запросы используют no-store, AbortSignal и запрещают перенаправления. Успешная запись подтверждается только точной следующей ревизией и совпадающим ETag. Истечение диапазона BIGINT отклоняется до отправки. Ответ читается потоком с пределом 2 МиБ, включая HTML-экранирование Go; проверяются Content-Type и UTF-8. Отмена после заголовков/во время чтения освобождает поток и не публикует прежний результат. Запреты доступа, конфликт и квота возвращаются как `EditorDraftError`, совместимый с `SessionError`, без отражения приватного тела ошибки в интерфейсе.

## Хранилище приватных журналов редактора — 2026-10-10 {#editor-draft-storage-2026-10-10}

Серверное хранилище добавлено миграцией `20261010006_editor_drafts`. Это основа USER-02 для будущего сохранения намерений после перезагрузки, **не подключённое автосохранение UI**. Существующие очереди редактора пока остаются в памяти. Текущий протокол хранит исходное состояние и команды, но не применяет их к физической схеме, не повторяет расчёт и не подтверждает выполнение исходной команды.

Область журнала: аккаунт действующей сессии + фактически принадлежащая проекту схема + UUID рабочего контекста. UUID не даёт права доступа. Участник, включая owner/admin общего проекта, читает только собственные журналы; два аккаунта могут использовать одинаковый UUID независимо. Разные сессии одного аккаунта могут явно открыть один журнал, тогда их правки защищаются отдельным CAS. Будущий UI должен создавать независимые UUID для отдельных контекстов вкладок и предложить явный выбор восстановления, а не назначать один глобальный активный черновик.

| Маршрут относительно `/api/projects/{projectId}/schemes/{schemeId}/drafts` | Контракт |
| --- | --- |
| `GET` | `{items:[{workspaceId,revision,updatedAt}]}` собственных активных журналов этой схемы; без payload |
| `GET /{workspaceId}` | Та же карточка с payload, ETag ревизии |
| `PUT /{workspaceId}` | Полный payload формата v1, обязательный If-Match; `"0"` только для создания; 200 с workspaceId/revision/updatedAt и ETag |
| `DELETE /{workspaceId}` | Обязательная текущая ревизия; удаляет payload, возвращает новую revision/ETag и сохраняет метку удаления UUID |

Чтение доступно owner/admin/editor/viewer при текущем праве на схему; сохранение — owner/admin/editor. Viewer может удалить только собственный ранее созданный журнал. После удаления членства даже собственный сохранённый payload недоступен через проектный путь. Отзыв/истечение сессии, отключение аккаунта, чужой проект или схема дают общий 404; отсутствующая/некорректная cookie — 401. Применяются точный Origin и no-store. Отсутствующая ревизия — 428, неверная форма — 400, конфликт — 412 `editor_draft_revision_conflict`. UUID — каноническая строка lowercase; ID и ревизии внутри payload — десятичные строки без округления.

Минимальный payload:

```json
{"formatVersion":1,"components":[],"graph":[]}
```

`components` содержит `{componentId,base,intents,reason}`. Base сохраняет id/typeId/type/equipmentModelId/revision/name/x/y/rotation/params. Intents: `pose` с частичными values x/y/rotation/name, `parameter` с key/value или `delete`. `graph` содержит `{intent,reason}`: `create-component` с typeId/name/x/y/rotation/params и необязательным equipmentModelId; `create-connection` с commandId/from/to/fromPort/toPort/expectedTopologyRevision; `delete-connection` с id/expectedTopologyRevision. Для создания связи обязательно сохраняется исходный UUID и исходная топологическая ревизия. Наличие записи в журнале не доказывает существование связи сейчас. Потерянное подтверждение сохранения самого журнала требует чтения и сравнения, а не слепого повтора с новой ревизией.

Сервер проверяет версии/виды намерений, известные поля с точным регистром, уникальность componentId и commandId, форму ID/ревизий, конечную геометрию и ограниченные строки. Допускаются параметры с пустыми значениями и исторические ссылки на уже отсутствующие объекты: будущая сверка должна прочитать текущий защищённый граф и проверить реальный объект/тип/паспорт до любой записи. Журнал не является физической верификацией параметров, единиц, портов или математической модели. Дополнительный JSON, повторяющиеся ключи, чрезмерная вложенность, неверный UTF-8 и непарные UTF-16 escapes отклоняются без замены значения.

Фиксированные пилотные пределы: 256 KiB HTTP-payload, до 128 компонентных и 128 структурных записей, до 64 намерений на объект, причина до 1024 символов. PostgreSQL дополнительно ограничивает размер JSONB-представления 512 KiB. На аккаунт разрешено 32 активных журнала и 256 строк с учётом меток удаления. Создание сверх предела даёт 409 `editor_draft_quota`; существующие журналы можно обновлять и удалять. Квота сериализуется account-wide advisory lock, включая разные схемы; права повторно проверяются после ожидания. Метка удаления запрещает повторное создание прежнего UUID и стирает payload; ревизия не обнуляется. Очистка меток/удалённых членств, настройка квот, срок хранения и UI управления журналами ещё не реализованы: достижение общего предела требует будущего административного сценария, а не удаления истории вслепую.

## Адресная проверка выбранного проекта — 2026-10-10 {#адресная-проверка-выбранного-проекта-2026-10-10}

## Серверная основа — 2026-10-10

Миграция `20261010001_auth_sessions` и `backend-go/sessions.go` добавляют хранилище отзываемых сессий. Вход/чтение/выход, проекты, участники и создание/чтение проектных схем подключены к HTTP (разделы ниже). Старые схемы без проекта остаются общими; каталог и вычислительные задания **ещё не разделены пользовательскими правами**. USER-01/02/03 остаются открытыми. Демонстрационная таблица `users(name)` сохранена, её Alice/Bob не становятся учётными записями.

`auth_accounts` хранит отдельный ID, отображаемое имя, дату создания и признак отключения. Отображаемое имя не является логином и может повторяться. Локальные учётные данные хранятся отдельно в `auth_local_credentials`; регистрационного HTTP-маршрута и привязки к внешнему провайдеру пока нет. Миграция не создаёт тестовых аккаунтов и не назначает владельцев старым схемам.

`auth_sessions` хранит ID сессии, ссылку на аккаунт, SHA-256 хеш 32 случайных байт, срок действия и дату отзыва. Исходный секрет — канонический Base64URL без padding, 43 символа — возвращается только при выпуске и не сохраняется в БД. ID аккаунта/сессии не является секретом и не даёт доступ. Генерация использует `crypto/rand`; SHA-256 здесь применяется к случайному токену, это не алгоритм хранения пароля. Срок в Go-контракте — от секунды до 30 суток; времена проверки берутся из PostgreSQL, а не часов браузера.

| Операция | Поведение |
| --- | --- |
| `Issue` | Выпуск после доверенного подтверждения личности; отсутствующий/отключённый аккаунт отклоняется |
| `Authenticate` | По хешу возвращает аккаунт/сессию/срок; истечение, отзыв или отключение аккаунта блокируют результат |
| `Revoke` | Проверяет действующий токен инициатора и принадлежность целевой сессии в одном SQL; отзыв одной сессии сохраняет остальные |
| `RevokeAll` | Проверяет инициатора и отзывает только сессии его аккаунта, включая собственную |

Выпуск по переданному клиентом account ID запрещён: метод `Issue` вызывается HTTP-login только после проверки учётных данных. Неканонические и слишком длинные токены отклоняются до обращения к БД и до выделения буфера декодирования. Отсутствующий токен/аккаунт, чужая цель, истечение и отзыв возвращают общий `session unavailable`; ошибки доступности БД и отмена запроса остаются отдельными ошибками, не превращаются в успешную идентичность. Секреты не включаются в сообщения ошибок.

Повтор отзыва собственной уже отозванной цели допустим, пока инициатор использует другую действующую сессию. Отозванный инициатор больше не может выполнять команды, включая повтор `RevokeAll`. Само отключение аккаунта не переписывает даты отзыва; административные сценарии отключения/повторного включения и ротация токенов ещё не реализованы. Отзыв применяется к последующим проверкам после коммита, он не прерывает уже начавшийся запрос или вычисление. Очистка истории и ограничения числа сессий пока отсутствуют.

## Локальный вход и HTTP cookie — 2026-10-10

Миграция `20261010003_local_credentials` добавляет отдельную таблицу логинов/хешей. Логин нормализуется trim/lowercase, 3–64 ASCII символа `a-z0-9._-`, первый — буква/цифра; уникальность закреплена в БД. Отображаемое имя остаётся отдельным Unicode полем. При создании пароль должен содержать минимум 12 Unicode символов и максимум 1024 UTF-8 bytes, при проверке не обрезается и не нормализуется. Это текущая политика длины; blocklist, восстановление/смена пароля, MFA и внешние identity providers ещё не реализованы.

Хеш — Argon2id, версия 19, 64 MiB, три прохода, четыре потока, случайная соль 16 bytes, ключ 32 bytes, PHC-строка. Используется [официальный пакет Go](https://pkg.go.dev/golang.org/x/crypto/argon2) `golang.org/x/crypto v0.58.0`, совместимый с Go 1.26; память задаётся в KiB. Параметры хеша проверяются до KDF и не могут потребовать произвольную память из текста БД. Ключи сравниваются через `subtle.ConstantTimeCompare`. Неизвестный/отключённый логин выполняет тот же ограниченный KDF и получает тот же 401, что неверный пароль; это не гарантия одинакового времени HTTP. Отмена проверяется до/после KDF, сам Argon2 не прерывается посередине вычисления.

| Маршрут | Контракт |
| --- | --- |
| POST `/api/auth/login` | JSON `{login,password}`, максимум 16 KiB, неизвестные поля/лишний документ отклоняются; 200 с публичной идентичностью и cookie |
| GET `/api/auth/session` | Действующая cookie → accountId/sessionId/expiresAt, иначе 401 |
| POST `/api/auth/logout` | Отзывает текущую сессию и удаляет cookie, 204; другие сессии сохраняются |
| POST `/api/auth/logout-all` | Отзывает сессии текущего аккаунта и удаляет cookie, 204; другие аккаунты не затрагиваются |

ID в JSON — строки для сохранения BIGINT без потери точности. Исходный токен не выдаётся в JSON; срок HTTP-сессии — 24 часа. Cookie: HttpOnly, SameSite=Strict, Path=/, без Domain; по умолчанию Secure и имя `__Host-enersy_session`. Все ответы имеют `Cache-Control: no-store`. Дублирующиеся cookies отклоняются. Для POST обязателен один точный Origin; GET с чужим Origin также отклоняется. Auth CORS использует только точный origin и credentials, не общий wildcard CRUD. Frontend/API должны находиться на одном site для Strict-cookie; текущая конфигурация рассчитана на общий reverse proxy или localhost с разными портами, а не на произвольные разные сайты.

`AUTH_ORIGIN` по умолчанию пуст: auth-маршруты возвращают 503, пока оператор не укажет точный origin без path/query/credentials/wildcard. `AUTH_COOKIE_SECURE` по умолчанию true; только явное `false` выбирает локальную HTTP cookie `enersy_session`. В тестовом Compose задано `AUTH_ORIGIN=http://localhost:4174`, `AUTH_COOKIE_SECURE=false`; это не конфигурация HTTPS-поставки. Корневой Compose передаёт эти настройки из окружения. Текущий API и CRUD не становятся изолированными только от включения login.

Одновременно разрешены два входа с KDF; лишний получает 429/Retry-After вместо неограниченного расхода памяти. Это ограничение параллелизма, не полная защита от перебора: временные/per-account/IP лимиты, число сессий и распределённый admission остаются задачами. Ошибка БД не превращается в неверный пароль: возвращается общий 503 без SQL/секретов.

### Создание аккаунта оператором

HTTP-регистрации и паролей по умолчанию нет. Оператор контейнера может создать аккаунт через `./server -provision-account`: JSON со stdin, без секретов в argv/env. Аккаунт и учётные данные записываются одной транзакцией; конфликт нормализованного логина откатывает создание аккаунта. Ответ содержит только строковый accountId.

Пример PowerShell для уже запущенного обновлённого контейнера (меняет БД):

```powershell
$operatorPassword = Read-Host 'Пароль нового аккаунта' -AsSecureString
$operatorPayload = @{
  displayName = 'Имя пользователя'
  login = 'operator'
  password = [Net.NetworkCredential]::new('', $operatorPassword).Password
}
try {
  $operatorPayload | ConvertTo-Json -Compress |
    docker compose exec -T go-api ./server -provision-account
} finally {
  $operatorPayload.password = $null
  $operatorPassword.Dispose()
}
```

## Оборудование проекта и ревизии — 2026-10-10

В базовом пути `/api/projects/{projectId}/schemes/{schemeId}/components` owner/admin/editor могут создавать и менять оборудование; viewer читает граф схемы, но не выполняет записи. Создание не принимает schemeId/ownerId в теле: родитель задаётся путём, права — сессией. Идентификаторы типов и паспортов передаются каноническими положительными десятичными строками. Текущие ID схем/оборудования/типов/паспортов имеют тип PostgreSQL INTEGER; значения выше 2147483647 отклоняются до SQL. ID проектов/аккаунтов и ревизии — BIGINT. Строковый формат не означает миграцию всех таблиц на BIGINT. Тела JSON ограничены 1 MiB; неизвестные поля, дополнительный JSON и некорректные геометрия/параметры отклоняются общими валидаторами существующего API. Снимок паспорта копируется общей функцией для старого и проектного создания. Тип паспорта и все его параметры читаются одним SQL-снимком; начальные params переопределяют скопированные значения. Последующие изменения справочника не меняют параметры экземпляра. Версионирование каталога и смена привязанного паспорта существующего объекта ещё не реализованы.

PUT/PATCH/POST params/DELETE требуют `If-Match: "revision"` текущего объекта. Отсутствие — `428`, неправильная форма — `400`, конфликт — `412 component_revision_conflict`. Успешная запись возвращает строковую revision и ETag; CORS разрешает PATCH/If-Match и открывает ETag клиенту. При удалении подтверждается проверенная ревизия удалённого объекта. Исходная ревизия после создания зависит от записанных параметров и триггеров, её нельзя считать всегда равной 1. Создание нового объекта не требует ревизии другого объекта; ревизия топологии схемы и защита повторов создания пока отсутствуют.

Запись выполняется в READ COMMITTED транзакции: shared-блокировка проекта, повторная проверка активной сессии и роли после ожидания, exclusive-блокировка фактически принадлежащей схемы, затем блокировка оборудования и сравнение ревизии. Эти блокировки удерживаются до коммита/rollback; изменение участников использует exclusive-блокировку проекта. Удалённый ожидающий редактор не получает права на запись. Изменение геометрии и нескольких параметров одним PATCH атомарно; ошибка второй части откатывает первую и ревизию. Некорректная cookie даёт `401`, недоступные/отсутствующие родители или объект — `404`; ошибки БД — общий `500` без SQL. Проверка доступа относится к начавшейся операции; последующий отзыв сессии не является командой отмены уже исполняемой транзакции.

Отсутствующая cookie даёт 401, недоступная фактическая схема/проект — 404; отсутствующая ревизия — 428, устаревшая — 412.

Авторизация и граф читаются в одной read-only REPEATABLE READ транзакции. Данные сортируются по ID, транзакция завершается до вызова worker. Перед отправкой входа и перед публикацией полного JSON-ответа права проверяются снова. Удалённый участник или отозванная сессия не получает готовый результат. Worker не получает cookie, токен или учётную запись пользователя.

Ответ сохраняет статус и исходные JSON-байты worker, включая числовую точность. Заголовки `X-Enersy-Input-SHA256`, `X-Enersy-Topology-Revision`, `X-Enersy-Project-Id`, `X-Enersy-Scheme-Id` описывают захваченный вход и доступны через CORS; действует no-store. SHA256 относится к точным байтам запроса, включая геометрию и параметры методов, и не доказывает физическую эквивалентность. Изменение параметров или геометрии может менять hash без изменения топологической ревизии. Ответ worker сохраняет прежний числовой контракт ID; новый граф API использует строковые ID.

`TestProjectCalculationPostgres` с настоящей PostgreSQL и контролируемым HTTP-worker проверяет отсутствие вызова при отказах доступа/ревизии/формы запроса, подстановку чужого projectId, неизменный захваченный вход при параллельной записи, обновление следующего входа, точный hash и ответ, отсутствие credentials у worker и отказ удалённому во время расчёта editor. Полный Docker Go vet/race прошёл. Этот тест проверяет транспорт и изоляцию; численные алгоритмы не менялись. Новый проектный маршрут проверен через настоящие Docker Go/PostgreSQL/Julia: Test-GoJuliaReference.ps1 -ProjectMode создал приватную схему трансформатора 110/10 кВ через защищённые команды и совпал с независимым эталоном. Допуски: узлы 1e-8 p.u., углы 1e-8 rad, ветви 1e-6 MW/Mvar. Проверены отказ анонимному клиенту и заголовки происхождения; временные аккаунт/проект/граф удалены. ## Клиент команд и проектный адаптер редактора — 2026-10-10

`project-scheme-api.ts` реализует защищённые команды оборудования, связей и расчёта. Wire ID и ревизии остаются строками; ID графа ограничены текущим SQL INTEGER, ревизии — PostgreSQL BIGINT. Все запросы используют same-origin cookie, no-store и AbortSignal. Отказ, некорректное подтверждение или отмена не превращаются в успех. Для оборудования/связей проверяется ETag, для связи — исходный UUID и явный deleted, для результата — projectId/schemeId/topologyRevision и SHA-256 входа. Неопределённый отказ не вызывает автоматический повтор или общий legacy маршрут.

`createProjectEditorTransport` связывает существующий редактор с одной приватной схемой на время одного mount. Чтение, записи, восстановление и расчёт используют защищённый API; только каталог типов/шаблонов и генерация UUID остаются общими. Списку редактора достаточно id/name, снимку — состава графа: адаптер не придумывает legacy owner или даты.

Структурные команды сериализуются общей очередью адаптера, отдельно от очередей объектов. После подтверждения создания/удаления оборудования или связи перечитывается полный граф. Состав оборудования и концы/порты связей должны точно совпасть с ожидаемым результатом команды; посторонняя структурная правка или потерянное чтение блокирует следующие структурные команды и расчёт до явной сверки. Геометрия и параметры защищаются отдельным CAS объекта. Это дополнительное полное чтение после каждой структурной команды; оптимизация для больших схем ещё не реализована.

Неопределённая команда связи сохраняет исходные UUID, payload и If-Match в памяти адаптера. После явной сверки повтор использует те же данные и может вернуть историческое deleted-подтверждение. Применять его как новую связь нельзя: существующий сценарий восстановления снова читает серверный граф. Подтверждённый первоначальный ответ также сверяется с текущим графом; старое topologyRevision из replay не подменяет текущую ревизию. Долговременное сохранение команд/черновиков остаётся открытым.

Writable-контекст проверяется в адаптере, а сервер независимо проверяет фактические права. AbortSignal завершает lifetime, а 401/404 вызывает обработчик сброса контекста. Владелец UI обязан создать отдельную ComponentWrites и keyed editor по аккаунту/проекту/схеме, отменить запросы при закрытии и подключить сброс приватных данных; эти связи с экраном ещё не реализованы. ### Исправленный журнал правок оборудования

В приватном редакторе раньше перед перезагрузкой сохранялись только команды
создания оборудования. Теперь `ComponentWrites` привязывает синхронное хранилище
намерений параметров, положения и удаления объекта. Снимок с исходной ревизией,
точными строками, единицами и базисами записывается **до** сетевой мутации.
Если хранилище недоступно, новый запрос не отправляется. При подтверждении
журнал обновляется, сохраняя более новые намерения очереди. Сбой очистки после
подтверждённой записи показывается отдельно; повторного запроса не возникает.

`component-intent-journal.ts` использует sessionStorage текущей вкладки и ключ
account/session/project/scheme. Запись проверяется чтением, ограничена 256 КиБ
контракта (260 КиБ с оболочкой), максимум 32 контекста на вкладку. Cookie и пароль
не сохраняются. При выходе и смене аккаунта/сессии чужие ключи удаляются.
Завершившийся старый контекст не может заново записать журнал после abort.
Это локальное свидетельство намерения, а не право доступа и не подтверждение commit.

После перезагрузки восстановленная очередь заблокирована до явной сверки с
настоящим сервером. Автоматического PATCH/DELETE нет. В журнал входят намерения,
уже переданные очереди: текст формы нагрузки до «Применить профиль» и другие
ещё не зарегистрированные поля этим механизмом не сохраняются. Команды связей
и остальные изменения топологии пока требуют отдельной долговечной интеграции.
Серверный API журналов при этом сохраняет свой отдельный контракт.

Найдена и исправлена несовместимость исторического исходного состояния без
названия: пустая строка сохраняется точно; `null`, пропущенное имя, пробелы вместо
имени и некорректный текст не превращаются в неё. Для создания нового оборудования
и явного переименования пустое имя по-прежнему недопустимо. Проверка координат
отделена от требования нового имени без изменения численных границ.

## Смена базиса внутри очереди одной вкладки {#queued-basis-acceptance}

Найдена ошибка локальной FIFO: после подтверждения изменения исходного базиса
очередь переносила его в исходное состояние следующего уже ожидавшего коэффициента
и отправляла тот с новой ревизией объекта. Серверный CAS принимал запрос, поскольку
эта ревизия действительно актуальна; исходный контекст ввода терялся до отправки.
Регрессия до исправления завершилась 1 fail / 670 pass и показала выполнение
второго callback вместо остановки.

`ComponentDrafts.acknowledgeBatch` теперь применяет все намерения одного успешного
запроса к подтверждённому состоянию целиком. Перед переносом базы сравниваются
единицы и Sб/Uб оставшихся параметров. При изменении контекста сохраняется полный
исторический baseline, а оставшиеся намерения получают причину для сверки.
Следующая отправка блокируется существующим guard очереди. Первая подтверждённая
запись остаётся успешной; расчёт блокируется до явного решения. Формат журнала
v1/v2, API и схема БД не менялись.

Перед регистрацией параметрической правки дополнительно сравнивается наблюдаемое
представление объекта с последним подтверждённым. Это блокирует старый callback,
вызванный уже после предыдущего подтверждения: его baseline берётся из реально
наблюдавшегося старого объекта и не подменяется текущим состоянием очереди.
При неизменных единицах/базисах более новая ревизия собственных числовых правок
сама по себе не запрещает продолжение FIFO.

Проверка оставшихся контекстов выполняется только если сам подтверждённый запрос
изменил единицу или базис. Обычные числовые правки не требуют полного просмотра
ожидающей очереди для этого guard; отдельная масштабная приёмка остаётся открытой.

Проверены смена единицы, Sб, Uб и явная очистка базиса; атомарная группа P/Q не
создаёт смешанного baseline. Быстрые правки числа при неизменном контексте и
независимое перемещение продолжают использовать последовательные ревизии.
React hook дополнительно проверяет, что API не получает второй PATCH и расчёт
не запускается; интерфейс сохраняет успешную первую запись и спорный старый ввод.
Docker typecheck/lint и 681 frontend-тест прошли; 3 opt-in теста обычным прогоном
пропущены.

Отдельный `queued-basis.http.test.ts` прошёл с настоящими Go API/PostgreSQL
одноразового `enersy-study-ui`. Существующим аккаунтом владельца прочитана
синтетическая нагрузка №1; P `0.025000 p.u.`, Sб/Uб=60/10. Первый PATCH меняет
только Sб на 70 МВА. Ответ уже получен от настоящего API, но его передача очереди
удерживается тестовым барьером, пока второй коэффициент `0.030000` ожидает.
Контрольное чтение подтверждает commit первого PATCH. После снятия барьера
второй запрос не отправляется: в проверяемой гонке ровно один PATCH.

Сериализация/восстановление настоящего журнала сохраняет исходные 60/10, показывает
серверные 70/10 и `unit_changed`; попытка применения отклонена до HTTP. Явное
принятие серверного поля снимает намерение без повторного PATCH. После этого
вызван старый callback с исходным объектом 60/10: он также остановлен до HTTP,
а сохранённый baseline остался 60/10. Отдельная cleanup-
запись возвращает исходный базис; ревизии не откатываются. Чтение БД подтвердило
P `0.025000` с 60/10, Q `0` и Uном `1.0000` с 10/10, отсутствие добавленных ZIP-полей
