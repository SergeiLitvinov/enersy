## Согласованное чтение схемы — 2026-10-08

`GET /api/ees/schemes/{id}` читает метаданные, оборудование с параметрами/строковыми ревизиями и связи с диагностикой в одной read-only транзакции PostgreSQL `REPEATABLE READ`. Снимок фиксируется первым SELECT; конкурентная запись может завершиться, но не подменяет последующие части текущего ответа. Транзакция завершается до отправки HTTP 200. Все SQL-чтения получают контекст запроса; ошибка, отмена или отсутствие схемы освобождают транзакцию. Ошибки SQL этого маршрута больше не возвращают внутренний текст БД клиенту. Формат успешного JSON сохранён.

Дефект DB-01 воспроизведён на обработчике до исправления: GET вернул старые имя/параметр 110 kV, но уже новый пустой список связей после чужого атомарного коммита. `TestSchemeSnapshotConcurrentCommitPostgres` использует только отдельную тестовую схему и SQL-барьер: fixture-view задерживает SELECT оборудования на advisory lock, при этом FK писателя остаются привязаны к физической таблице. Тест наблюдает реальное ожидание в `pg_locks`, коммитит новое имя, положение, параметр 220 kV и удаление связи, затем разрешает чтение. Исправленный GET возвращает все старые данные/ревизию/связь, а свежий GET — все новые данные и отсутствие связи. Барьера/изменения таблиц нет в production-коде; проверки не зависят от случайного попадания sleep между HTTP-запросами.

### Контракт и восстановление в редакторе

Текущий редактор с ключом команды использует отдельный `POST /api/ees/connection-commands`. Этот маршрут требует валидный `Idempotency-Key`; отсутствие или неверный ключ отклоняются до создания. Старый CRUD-сервер не имеет такого маршрута и отвечает 404. Клиент не делает fallback на `/connections`, чтобы старый обработчик не проигнорировал ключ и не создал дубликат. Подтверждение новой команды и её повтора содержит канонический `commandId`; клиент отклоняет даже HTTP 200, если ключ в ответе отсутствует или отличается. Запросы без ключа по-прежнему используют прежний CRUD-маршрут.

`GraphWrites.retryConnection` подключён к `useSchemeData` и `GraphRecoveryDialog`. После сверки можно выбрать одно создание связи с ключом и отдельно подтвердить повтор. Используется исходное намерение и тот же UUID. Повтор входит в барьер расчёта; намерение снимается только после корректного подтверждения и свежего чтения серверной топологии. Ошибка отправки или чтения сохраняет ту же запись журнала. Новые правки оборудования/графа и смена рабочего контекста требуют новой сверки. Подтверждение старой команды не восстанавливает уже удалённую связь.

Frontend typecheck/lint/132 теста/build прошли. Регрессии проверяют защищённый транспорт, исходный payload, отдельное подтверждение в диалоге, ожидание свежего чтения и сохранение ошибки при его отказе. В браузере на отдельном Compose-стенде с временной PostgreSQL прокси `tests/integration/nginx-lost-command-ack.conf` скрывал `commandId` после сохранения команды upstream. Редактор блокировал расчёт; после восстановления обычного прокси явный повтор оставил одну связь и одну команду в БД, перечитал схему и снял блокировку. Это потеря идентичности подтверждения в HTTP 200, а не полный сетевой обрыв после коммита. Рабочее развёртывание остаётся прежним.

`POST /api/ees/connections` поддерживает необязательный `Idempotency-Key`: один UUID команды. Неверный/пустой/повторяющийся заголовок отклоняется с 400. Без заголовка сохраняется прежний контракт, без защиты повтора. Редактор создаёт случайный UUID перед отправкой каждой новой команды и сохраняет его вместе с её данными в журнале неподтверждённого создания. Автоматического повтора нет; явный повтор создания связи описан выше.

Миграция `20261008001_connection_commands` добавляет `connection_commands`. Ключ хранится в области схемы; нормализованный DTO (имена портов в нижнем регистре) хешируется SHA-256. Транзакционная advisory-блокировка сериализует одну команду до чтения журнала, включая случай отсутствующей строки. Точный ключ и схема проверяются отдельно: коллизия хеша блокировки лишь задерживает независимые команды. Связь и подтверждение сохраняются одной транзакцией; ошибка подтверждения откатывает связь. С тем же ключом и теми же данными повтор возвращает первоначальные `id` и `success: true`, а также диагностический `Idempotency-Replayed: true`. Изменённые данные с прежним ключом получают 409. Новая независимая команда требует нового UUID; два разных ключа могут создать параллельные связи.

Подтверждение относится к выполнению исходной команды, а не к существованию связи сейчас. Журнал не имеет FK на связь: её последующее удаление не стирает подтверждение, и повтор не создаёт связь заново. Перед отображением результата повтора редактор заново читает топологию. Удаление самой схемы удаляет её журнал. TTL/очистка истории пока не введены; разрушительный down удаляет историю и не является штатным откатом. Область схемы не заменяет авторизацию: текущий прототип не аутентифицирует пользователей. При USER-01/02 проверка доступа к проекту должна выполняться до чтения/повтора подтверждения. Ключ команды не является паролем или правом доступа.

В Docker прошли `go vet` и полный `go test -race -v` с PostgreSQL 15: восемь конкурентных первых отправок создают одну связь; восемь повторов возвращают один ID; изменение payload отклоняется; регистр портов нормализуется; другая схема независима; невалидная команда не оставляет подтверждение; ошибка вставки подтверждения откатывает уже вставленную связь; удалённые объекты не восстанавливаются повтором. Миграции пустой/legacy базы и их целостность проверены общим набором. Через реальный API отдельного Compose-стенда подтверждены повтор ID=1, конфликт 409, одна сохранённая связь, повтор после перезапуска API и отсутствие связи после DELETE + повтора. Игнорирование первого ответа в Go-тесте моделирует потерю подтверждения, полный сетевой обрыв ответа после коммита ещё не проверен; браузерная проверка потери идентичности подтверждения описана выше.

## Барьер расчёта для изменений графа — 2026-10-08

### Основа явного принятия серверной топологии

`GraphWrites.review` ждёт отправленные операции исходной схемы, затем вызывает переданное чтение её полного состава. Сравнение хранит отдельные копии снимка и намерений; оно привязано к конкретному журналу непрозрачным токеном. `acceptServer` позволяет явно отказаться только от выбранных рассмотренных намерений, возвращая копию прочитанного серверного состояния без HTTP-записи. Это не отменяет исходную команду и не доказывает, была ли она выполнена. Новая операция исходной схемы во время чтения или после сравнения делает его устаревшим; операции другой схемы не мешают сверке. Поддельное сравнение, другая схема, пустой/чужой выбор и повторное использование отклоняются.

API подключён к `useSchemeData` и `GraphRecoveryDialog`. Сверка привязана также к рабочему контексту и версии очереди оборудования: новая правка оборудования или переход A → B → A требует нового чтения. При принятии серверный состав обновляет вид, но конфликтные экземпляры и их журнал остаются; даже отсутствующий на сервере экземпляр с черновиком сохраняется для отдельного разрешения. Параметры, введённые в инспекторе, не получают принудительный reset. В диалоге нет автоматического выбора: требуются выбранные намерения и отдельное подтверждение принятия состава. Совпадение признаков созданного оборудования не считается доказательством идентичности или выполнения команды.

В исходном frontend `GraphWrites` регистрирует отправленные создания оборудования, создания и удаления соединений. `ComponentWrites.settleForCalculation` ждёт как версионную очередь оборудования, так и эти изменения выбранной схемы; повторяет ожидание, если во время него появилась новая запись. HTTP-запрос расчёта отправляется только после подтверждения. API-клиент требует `success: true` для соединений и положительный безопасный целый ID созданной связи; HTTP 200 без корректного подтверждения считается отказом.

Неоднозначный отказ сохраняет копию намерения и причину по ID схемы в App-owned очереди. Повторное открытие редактора или чтение схемы не снимает блокировку автоматически; другая схема не наследует этот отказ. Журнал находится только в памяти, не изолирован по аутентифицированному субъекту. Расчёт исходной схемы блокируется до явного принятия рассмотренных намерений или подтверждённого повтора создания связи со свежим чтением состава. Перезагрузка страницы теряет журнал и не доказывает, что спорная запись отменена.

Проверки включают ожидание трёх видов отправленных операций, появление записи во время ожидания, отказ после повторного открытия, независимую схему, копию журнала и неверные HTTP-подтверждения. Это React/транспортные регрессии с управляемыми Promise; последующая браузерная проверка потери идентичности подтверждения описана выше. Барьер не охватывает будущие действия пользователя, подготовительную загрузку каталога до отправки создания или изменения других клиентов. Неизменяемый серверный снимок Run, ревизии топологии, идемпотентные команды, разрешение конфликтов и USER-01/02/03 остаются отдельными задачами. Рабочие контейнеры приложения не обновлялись.

## Основа ревизий оборудования

Миграция `20261003001` добавляет положительный `BIGINT revision` к оборудованию. Любой UPDATE записи увеличивает ревизию; изменение/добавление/удаление параметра увеличивает ревизию родителя в той же транзакции. Параметр, записанный без изменения строки, не увеличивает ревизию. Явное присваивание произвольной версии не обходит триггер. Существующие экземпляры начинают с версии 1; копирование параметров нового экземпляра может увеличить её несколько раз, поэтому API не должен предполагать начальную версию 1.

`mutateComponentRevision` — подготовленный Go-контракт транзакции: блокировка родителя `FOR UPDATE`, сравнение ожидаемой версии, изменение, чтение новой версии и commit. Неверная версия отклоняется до вызова изменения; отсутствующий объект отличим от конфликта. Параметры и положение конкурируют за одну ревизию. Любой сбой откатывает данные вместе с версией. Прямые SQL-изменения тоже наблюдаются триггерами; обслуживающие операции должны брать блокировки в том же порядке (родитель перед параметрами), иначе PostgreSQL может отклонить взаимную блокировку.

Проверено на отдельном PostgreSQL 15 в Docker без сети и пользовательских томов: один победитель двух конкурентных записей, устаревшие параметры/удаление, отсутствие частичной записи, rollback, прямой SQL и no-op параметр, отсутствие объекта. Go vet и общий набор тестов, включая запуск с race detector, прошли; совместимость пустой/обновляемой/legacy БД подтверждена существующим migration harness.

### HTTP-контракт ревизий

В исходном коде Go API ревизии подключены к публичным обработчикам оборудования. Загрузка схемы возвращает `revision` каждого компонента вместе с его параметрами в одном SQL-запросе. Создание возвращает фактическую ревизию после копирования всех параметров и commit. JSON передаёт её десятичной строкой, чтобы не терять точность PostgreSQL BIGINT в JavaScript.

PUT оборудования, POST параметра и DELETE оборудования требуют заголовок `If-Match: "<revision>"`, например `If-Match: "3"`. Допускается ровно один сильный ETag с канонической положительной десятичной ревизией. Списки, wildcard, слабые ETag, ведущие нули и выход за диапазон BIGINT отклоняются. Успех возвращает `success: true`, строковую `revision` и ETag новой версии; для DELETE возвращается проверенная последняя версия удалённого объекта. Повторная запись неизменённого параметра может сохранить ревизию.

| Ситуация | HTTP | Код ошибки |
| --- | --- | --- |
| Не передан If-Match | 428 | `component_revision_required` |
| Некорректный If-Match | 400 | `invalid_component_revision` |
| Объект изменён другим клиентом | 412 | `component_revision_conflict` |
| Объект отсутствует | 404 | `component_not_found` |
| Не удалось завершить транзакцию | 500 | `component_write_failed` |

Статус 412 соответствует невыполненному условию If-Match. Ошибки содержат `success: false`, `code`, `error`; внутренние SQL-ошибки не выдаются клиенту. Изменения положения требуют все четыре поля (`x`, `y`, `rotation`, `name`), иначе пропущенное поле могло бы незаметно стать нулём. Запрос ограничен 1 MiB; лишние поля и несколько JSON-значений отклоняются. Пустая строка параметра допустима; отсутствие значения или null отклоняется.

Проверено 2026-10-03 через публичные обработчики с PostgreSQL 15 в отдельном Docker-контейнере: два конкурентных HTTP PUT дают один успех и один 412; устаревший параметр не создаёт строку; устаревшее удаление не удаляет объект; повторное удаление даёт 404. Проверены обязательность заголовка, неверные ETag, лимит тела, неполный запрос, no-op параметр, ревизия при загрузке и после создания с параметрами, точность версии `9007199254740993`. Полный `go vet ./...` и `go test -race -v ./...` прошли, включая обновление legacy БД до миграции 20261003001.

### Атомарное применение выбранных полей

В исходном Go API `PATCH /api/ees/components/{id}` с обязательным If-Match сохраняет выбранные поля положения и параметры в одной транзакции. Пример тела:

```json
{"pose":{"x":20,"rotation":90},"params":{"voltage":"220"}}
```

`pose` допускает только `x`, `y`, `rotation`, `name`; пропущенные поля сохраняют текущие значения серверной записи под блокировкой. `params` содержит строковые значения, в том числе пустую строку; null не означает удаление параметра и отклоняется. Пустой запрос, неизвестные поля, неверные типы, координаты вне диапазона хранения, поворот вне INTEGER, неверные имена/параметры отклоняются до изменения БД. Размер тела ограничен общим лимитом 1 MiB, параметров не более 256. Тип оборудования и паспорт через PATCH не меняются. Удаление объекта выполняется отдельным DELETE, не смешивается с изменением полей.

Родитель блокируется до параметров, сравнение ревизии выполняется до записи; параметры обрабатываются в порядке ключей. Ошибка любой записи откатывает весь набор с ревизиями. В ответе возвращается фактическая итоговая ревизия: один PATCH может увеличить её несколько раз из-за триггеров, а no-op параметр не увеличивает её. Клиент не должен вычислять новую ревизию самостоятельно.

`prepareRecoveryPatch` строит частичный запрос из выбранных строк трёхстороннего сравнения и точной ревизии сравниваемой серверной записи. Незатронутые поля не входят в запрос; уже совпадающие значения не требуют повторной записи. Отсутствующий объект, другой тип/паспорт, неизвестная строка или попытка смешать удаление с PATCH отклоняются. `patchComponent` отправляет один запрос и проверяет подтверждение/структурированный отказ. **Кнопки применения и принятия серверных полей подключены в исходном редакторе; рабочий стек ещё требует согласованного обновления.**

Проверено Docker PostgreSQL 15: откат положения и первого параметра при ошибке второго, отсутствие утечки SQL-ошибки, сохранение незатронутых полей, запрет stale PATCH, сохранение no-op ревизии и конкурентные наборы с одним успехом и одним 412 без смешивания данных. Полный Go vet/test с race detector и существующие миграционные регрессии прошли. Рабочая пользовательская БД не менялась.

Docker frontend: typecheck/lint/58 тестов/build прошли. Новые проверки охватывают один PATCH с точной версией, структурированный 412, набор только выбранных полей, сохранение чужого названия/координаты вне запроса, отсутствие записи уже совпадающих значений и запрет восстановления отсутствующего/заменённого объекта или смешанного удаления. Это проверка транспорта и подготовки запроса; интерфейс применения ещё не прошёл приёмку.

### Клиент и очередь записи

В исходном frontend ревизия обязательна у загруженного/созданного оборудования. API-клиент проверяет её формат и диапазон BIGINT, не преобразует в Number и отправляет точный If-Match для PUT/параметров/DELETE. Ответ записи должен явно подтвердить успех и содержать корректную новую ревизию; отсутствующая/числовая/некорректная версия не считается подтверждением. Создание дополнительно проверяет ID, параметры и паспортную привязку.

Очередь хранит последнюю подтверждённую сервером ревизию отдельно от положения объекта. Версия выбирается при отправке очередного запроса, а не при постановке намерения в очередь. Поэтому параметр или удаление после перемещения использует новую версию, даже если React ещё не перерисовал объект. Для no-op параметра принимается возвращённая неизменённая ревизия. Конфликт или неоднозначный отказ останавливает следующие записи объекта и запуск расчёта. Структурированная ошибка сохраняет HTTP-статус/код и показывает серверную причину; автоматической повторной записи нет.

Проверено Docker frontend: typecheck, lint, 44 теста и build. Десять новых проверок охватывают точные BIGINT-токены, заголовки всех трёх операций, структурированный отказ, ошибочные подтверждения, отсутствие версии при загрузке, ответ создания, очередь move → параметр → delete, no-op параметр и остановку при конфликте. Это API/React-тесты с mock-транспортом, а не подтверждение многопользовательской изоляции или двухклиентной браузерной приёмки.

### Журнал неподтверждённых правок

`ComponentDrafts` хранит копию последнего подтверждённого состояния и упорядоченные неподтверждённые намерения по `(schemeId, componentId)`: изменённые поля положения, значение параметра или удаление. Геометрия до оптимистичного перемещения берётся из загруженного снимка. Подтверждённая операция удаляется из журнала и обновляет базу оставшихся намерений; отказ сохраняет первую причину. Неотправленное намерение устаревшего открытия отменяется, а потерянное подтверждение уже отправленной записи остаётся для проверки.

Загрузка другой схемы очищает текущую очередь и кэш подтверждённых состояний, но не журнал отказов. Новая загрузка серверных данных не переписывает исходную базу спорной правки. Неподтверждённое намерение продолжает блокировать записи объекта и расчёт его схемы, даже после повторного открытия; другая схема работает независимо. Снимки журнала копируются, чтобы код представления не изменял исходные данные. Метод явного отклонения намерения предназначен для будущего диалога после завершения очереди и повторной загрузки, а не для автоматического обхода блокировки.

Журнал находится в памяти приложения и переживает закрытие/повторное открытие редактора при сохранении его App-owned очереди. Перезагрузка страницы, закрытие браузера или перезапуск приложения пока теряют этот журнал. Это ещё не пользовательский черновик с долговременным хранением и не изоляция по аутентифицированному субъекту; после USER-01 потребуется область пользователя/проекта/рабочего контекста и очистка при выходе.

Проверено Docker frontend: typecheck/lint/49 тестов/build. Пять новых тестов журнала проверяют сохранение исходной базы после reload, отделение схем, обновление базы после подтверждения, копии снимков, несколько неподтверждённых операций FIFO, отмену stale намерения, сохранение потерянного подтверждения и явное отклонение с новой серверной базой. Обновлённая React-регрессия подтверждает, что повторное открытие само не разрешает конфликт. Проверка блокировки одного объекта выполняется по ключу журнала, без копирования всех черновиков при загрузке каждого компонента.

### Безопасное выборочное разрешение журнала

`ComponentDrafts.failed` возвращает снимок сравнения с внутренней привязкой к рассмотренным намерениям. `isCurrentReview` проверяет его перед отправкой: новый ввод или подтверждение прежней операции требуют нового сравнения. Копия снимка, созданная вне журнала, не позволяет снять намерения; изменения публичных данных снимка не меняют внутреннюю привязку к схеме и объекту.

`resolveReviewed` снимает только выбранные поля рассмотренных намерений. Рассмотренный перенос `{x, y}` после разрешения только X сохраняет Y. Новый перенос X, появившийся во время запроса, сохраняется. Нерассмотренные поля, удаление и первая причина отказа остаются в журнале. Исходные значения нерешённых полей сохраняются, даже если сервер изменил их; после частичного разрешения база сравнения содержит значения из разных ревизий, и её нельзя использовать как единый серверный снимок для записи. Повторное использование уже разрешённого снимка не снимает новые намерения.

`ComponentWrites.recover` ставит явное разрешение в ту же FIFO-очередь, что и записи объекта. Поэтому `settle` и расчёт ожидают его завершения. Для применения отправляется один PATCH с точной сравниваемой ревизией; без обработчика применения принимаются выбранные серверные значения. Уже совпадающие значения не требуют PATCH. После подтверждения очередь принимает фактическую ревизию и серверное положение; оставшиеся намерения продолжают блокировать записи и расчёт. Ошибка записи сохраняет журнал. Устаревший рабочий контекст до отправки отменяет восстановление; подтверждение уже отправленного запроса разрешает рассмотренные намерения исходной схемы. Применение ответа к интерфейсу другой вкладки или открытия должно отдельно проверяться вызывающим кодом.

### Отдельное разрешение удаления

`ComponentWrites.recoverDeletion` рассматривает только намерение удаления. «Оставить объект на сервере» принимает сравниваемое состояние без нового DELETE; остальные локальные поля остаются спорными. «Удалить по серверной версии» требует отдельного подтверждения ID и версии в диалоге и выполняет один DELETE с If-Match. Подтверждённая версия должна совпасть с проверенной версией удаления. При уже отсутствующем объекте «Подтвердить отсутствие объекта» снимает рассмотренное намерение без повторного DELETE. Ошибка чтения не считается отсутствием.

Новый ввод во время запроса и нерешённые поля не снимаются. Тип/паспорт заменённого объекта отклоняется; устаревший снимок сравнения требует повторной сверки. Очередь ждёт завершения операции перед расчётом и не отправляет обычные записи уже удалённому объекту. После подтверждения редактор удаляет только нужный объект и его инцидентные соединения; при отказе граф остаётся прежним. Восстановление отсутствующего объекта и явное отклонение оставшихся правок полей требуют отдельного сценария; пока они сохраняются в журнале и блокируют расчёт.

Проверено в Docker: typecheck/lint/83 теста/build, десять новых регрессий журнала, очереди и React. Браузерный стенд с восстанавливаемыми данными в памяти: сохранение объекта без DELETE, один условный DELETE, отсутствие без нового запроса, сохранение параметра после удаления, Escape/повторное открытие, темы и 390 px. Исправлена наследованная горизонтальная раскладка блока удаления; предупреждение и подтверждение читаются последовательно. Стенд очищен. Это не приёмка двух клиентов с реальным PostgreSQL и не развёртывание рабочего приложения.

### Проверка интерфейса сверки полей

В браузерном Docker-стенде с тестовыми ответами проверены применение только X, принятие Y без второго PATCH, сохранение параметра в журнале, отказ 412, Escape/повторное открытие, светлая/тёмная темы и 390 px с прокруткой таблицы и кнопками. Это не двухклиентная приёмка реального API/БД. Временный стенд удаляется после проверки.

В исходном редакторе неподтверждённые записи показывают постоянное сообщение и кнопку сверки каждого объекта. `RecoveryDialog` заново читает схему и сравнивает только явно затронутые локальными намерениями поля: исходное значение, последнее локальное намерение и актуальное серверное значение. Поля, которых локальная правка не касалась, не предлагаются к перезаписи. Совпадение значений означает совпадение текущих данных, а не доказательство, кто выполнил запись. Пустая строка и отсутствие параметра различаются; ключи, совпадающие с именами прототипа JavaScript, не считаются существующими значениями.

Ошибку загрузки нельзя трактовать как удаление объекта. Ответ прежнего чтения после смены объекта/закрытия окна игнорируется. Обновление сравнения повторяет только GET; закрытие через кнопку или Escape сохраняет журнал. Удалённый объект показан явно, без автоматического создания нового экземпляра. Поля выбираются явно, без выбора по умолчанию. «Применить мои значения» отправляет один частичный PATCH с точной сравниваемой ревизией; «Принять серверные» снимает выбранные локальные поля без записи. При разрешении элементы управления и закрытие заблокированы; затем сравнение обновляется, выбор сбрасывается. Отказ показывает причину и повторяет GET, сохраняя журнал. Удаление и отсутствующий объект недоступны для этих действий. База сравнения после частичного разрешения учитывает принятые значения отдельных полей, поэтому интерфейс не выдаёт её за единый исходный серверный снимок.

## Один путь запуска

В Docker/Compose источник схемы — `database/migrations/*.up.sql`. API поставляется вместе с этим каталогом и применяет миграции после подключения PostgreSQL. Новая пустая база и обновление выполняются одним путём. Compose больше не монтирует `init.sql` в `docker-entrypoint-initdb.d`; существующий том не пересоздаётся.

По умолчанию каталог ищется относительно исполняемого файла: `database/migrations`, а не относительно рабочего каталога. Для разработки и тестов можно явно задать `MIGRATIONS_SOURCE` как URL `file:///absolute/path`. Эта настройка не нужна для штатного контейнера. Не редактируйте применённые миграции: исправление оформляется следующей версией.

## Отказ и восстановление

До обновления проверяется версия `schema_migrations`. API отклоняет более новую версию, неизвестную историческую версию и `dirty`. После обновления проверяется точное достижение последней поставляемой версии. Пустой/недоступный каталог и неверный SQL также завершаются ошибкой. Ошибка не закрывает общий пул соединений внутри функции миграции; вызывающий запуск API закрывает его и оставляет сервис неготовым.

`/health` отражает работу процесса, `/ready` — доступность базы после успешного обновления. Compose проверяет `/ready`. Это не подтверждение физической достоверности расчётов.

При ошибке сохраните журнал и резервную копию. `dirty` означает, что обновление не завершилось: сначала выясните, какие изменения применились, затем подготовьте проверенное восстановление. Автоматического сброса версии, удаления данных или отката пользовательской базы нет.

## Проверяемая совместимость

`backend-go/migrations_test.go` создаёт отдельные схемы PostgreSQL и проверяет:

- установку с нуля и повторный запуск без изменения структуры/каталога;
- обновление с отмеченной версией `20260612001`;
- импорт legacy `init.sql` и `ees_schema.sql`, затем применение миграций;
- одинаковые столбцы, типы, defaults, ограничения, индексы, функции, triggers и views;
- одинаковые типы оборудования, шаблоны, паспорта, паспортные параметры и порты по естественным ключам;
- сохранение пользовательского объекта, координат, поворота и заданного параметра;

Последовательные ID могут различаться; эквивалентность каталога проверяется по ключам. Пользовательские строки и legacy демонстрационные `users` не сравниваются с заводским каталогом и не очищаются автоматически. Старый bootstrap мог повторно вставлять Alice/Bob, поскольку имя не имеет ограничения уникальности. ## Контроль содержимого миграций

API сохраняет SHA-256 в `schema_migration_integrity`. Изменённый/удалённый применённый SQL и пропущенная история блокируют обновление. Проверка выполняется под PostgreSQL advisory lock мигратора; исполняются заранее зафиксированные байты. CRLF и LF нормализуются, остальные изменения учитываются. Соединение возвращается пулу, не закрывая его.

Для старой базы первая фиксация имеет `origin=legacy-baseline` и предупреждение: прошлое содержимое невозможно подтвердить задним числом. Новые миграции получают `origin=applied`, сумма записывается до исполнения. Это контроль файлов, не защита от администратора БД.

## Резервная копия и восстановление

Из корня проекта в PowerShell:

```powershell
$backup = ./scripts/database/Backup-EnersyDatabase.ps1
./scripts/database/Restore-EnersyDatabase.ps1 -Backup $backup -Container hybrid-db -NewDatabase enersy_restored
./scripts/database/Test-DatabaseBackup.ps1
```

Backup сохраняет PostgreSQL custom dump и JSON-манифест SHA-256 в `.backups`, исключённый из Git. Бинарные данные копируются через Docker. Копия содержит данные, последовательности и историю миграций, но не роли/права сервера и внешние файловые артефакты. Храните dump и манифест вместе.

Restore проверяет hash, создаёт только новую базу и импортирует одной транзакцией. Существующая база не перезаписывается. При SQL-ошибке новая база может остаться пустой. Переключение рабочего API — отдельное действие после проверки данных и готовности.

Тест использует временный PostgreSQL без сети и рабочего тома. Сравнивает SQL до/после восстановления, кириллицу, параметры, версии/суммы и последовательности; существующая цель и повреждённый dump отклоняются. Эквивалентные casts одного CHECK нормализуются, его значения и отказ для неверного значения проверяются независимо. Контейнер останавливается в finally; evidence остаётся в `.cache`. Проверка добавлена в CI, удалённый запуск пока не подтверждён.

BASE-05 остаётся открытой для аудита legacy bootstrap-данных. `database/audit_legacy.sql` содержит только читающие запросы; дубликаты не удаляются автоматически. Новый контроль сумм пока не развёрнут в работающем API.
