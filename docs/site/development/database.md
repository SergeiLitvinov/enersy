# Установка и обновление базы

## Один путь запуска

В Docker/Compose источник схемы — `database/migrations/*.up.sql`. API поставляется вместе с этим каталогом и применяет миграции после подключения PostgreSQL. Новая пустая база и обновление выполняются одним путём. Compose больше не монтирует `init.sql` в `docker-entrypoint-initdb.d`; существующий том не пересоздаётся.

По умолчанию каталог ищется относительно исполняемого файла: `database/migrations`, а не относительно рабочего каталога. Для разработки и тестов можно явно задать `MIGRATIONS_SOURCE` как URL `file:///absolute/path`. Эта настройка не нужна для штатного контейнера. Не редактируйте применённые миграции: исправление оформляется следующей версией.

## Отказ и восстановление

До обновления проверяется версия `schema_migrations`. API отклоняет более новую версию, неизвестную историческую версию и `dirty`. После обновления проверяется точное достижение последней поставляемой версии. Пустой/недоступный каталог и неверный SQL также завершаются ошибкой. Ошибка не закрывает общий пул соединений внутри функции миграции; вызывающий запуск API закрывает его и оставляет сервис неготовым.

`/health` отражает работу процесса, `/ready` — доступность базы после успешного обновления. Compose проверяет `/ready`. Это не подтверждение физической достоверности расчётов.

При ошибке сохраните журнал и резервную копию. `dirty` означает, что обновление не завершилось: сначала выясните, какие изменения применились, затем подготовьте проверенное восстановление. Автоматического сброса версии, удаления данных или отката пользовательской базы нет.

## Проверяемая совместимость

`backend-go/migrations_test.go` создаёт отдельные схемы PostgreSQL и проверяет:

- установку с нуля и повторный запуск без изменения структуры/каталога;
- обновление с отмеченной версией `20260612001`;
- импорт legacy `init.sql` и `ees_schema.sql`, затем применение миграций;
- одинаковые столбцы, типы, defaults, ограничения, индексы, функции, triggers и views;
- одинаковые типы оборудования, шаблоны, паспорта, паспортные параметры и порты по естественным ключам;
- сохранение пользовательского объекта, координат, поворота и заданного параметра;
- отказ при future/unknown/dirty, повреждённом SQL и пустом источнике.

Последовательные ID могут различаться; эквивалентность каталога проверяется по ключам. Пользовательские строки и legacy демонстрационные `users` не сравниваются с заводским каталогом и не очищаются автоматически. Старый bootstrap мог повторно вставлять Alice/Bob, поскольку имя не имеет ограничения уникальности. Новый путь Compose выполняет этот seed только первой миграцией; восстановление уже накопленных дубликатов остаётся отдельной задачей.

Набор запускается существующим Go CI с PostgreSQL при заданном `TEST_DATABASE_URL`. Тесты используют собственные временные схемы, не таблицы приложения. Сверка SQL не удостоверяет паспортные характеристики оборудования: происхождение и физическая проверка ведутся отдельно.

## Контроль содержимого миграций

API сохраняет SHA-256 в `schema_migration_integrity`. Изменённый/удалённый применённый SQL и пропущенная история блокируют обновление. Проверка выполняется под PostgreSQL advisory lock мигратора; исполняются заранее зафиксированные байты. CRLF и LF нормализуются, остальные изменения учитываются. Соединение возвращается пулу, не закрывая его.

Для старой базы первая фиксация имеет `origin=legacy-baseline` и предупреждение: прошлое содержимое невозможно подтвердить задним числом. Новые миграции получают `origin=applied`, сумма записывается до исполнения. Это контроль файлов, не защита от администратора БД.

## Резервная копия и восстановление

Из корня проекта в PowerShell:

```powershell
$backup = ./scripts/database/Backup-EnersyDatabase.ps1
./scripts/database/Restore-EnersyDatabase.ps1 -Backup $backup -Container hybrid-db -NewDatabase enersy_restored
./scripts/database/Test-DatabaseBackup.ps1
```

Backup сохраняет PostgreSQL custom dump и JSON-манифест SHA-256 в `.backups`, исключённый из Git. Бинарные данные копируются через Docker. Копия содержит данные, последовательности и историю миграций, но не роли/права сервера и внешние файловые артефакты. Храните dump и манифест вместе.

Restore проверяет hash, создаёт только новую базу и импортирует одной транзакцией. Существующая база не перезаписывается. При SQL-ошибке новая база может остаться пустой. Переключение рабочего API — отдельное действие после проверки данных и готовности.

Тест использует временный PostgreSQL без сети и рабочего тома. Сравнивает SQL до/после восстановления, кириллицу, параметры, версии/суммы и последовательности; существующая цель и повреждённый dump отклоняются. Эквивалентные casts одного CHECK нормализуются, его значения и отказ для неверного значения проверяются независимо. Контейнер останавливается в finally; evidence остаётся в `.cache`. Проверка добавлена в CI, удалённый запуск пока не подтверждён.

BASE-05 остаётся открытой для аудита legacy bootstrap-данных. `database/audit_legacy.sql` содержит только читающие запросы; дубликаты не удаляются автоматически. Новый контроль сумм пока не развёрнут в работающем API.
