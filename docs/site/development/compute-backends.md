# Вычислительные движки и проверка производительности

Статус на 2026-10-22: основное приложение рассчитывает через Julia. Экспериментальный Rust-модуль `numerics` содержит CSR, Jacobi-PCG и сборку полярного AC-якобиана с переиспользуемой структурой. [C ABI и Julia-адаптер](./native-jacobian.md) созданы, проверены и измерены отдельно; к обычному HTTP-расчёту или браузеру Rust ещё не подключён. PCG остаётся алгоритмом для SPD-систем, а не решателем общего AC-якобиана.

## Rust-прототип Якобиана: измерения 2026-10-22

`JacobianPlan` строит CSC-структуру и позиции вкладов один раз. `update` записывает значения в буфер вызывающей стороны без выделений памяти. Сохраняются структурные нули; после изменения топологии, нумерации или классификации PV/PQ нужен новый план. Само ядро Якобиана использует безопасный Rust и стандартную библиотеку без новых зависимостей; операции с указателями вынесены в отдельный ABI-модуль. [Исходник и комментарии](/generated/code/numerics__src__jacobian_rs), [проверки](/generated/code/numerics__tests__jacobian_rs), [пример измерения](/generated/code/numerics__examples__jacobian_probe_rs).

Входы — рассчитанные P/Q, модули напряжений и углы в согласованных p.u./радианах, CSC-матрица комплексных проводимостей и производные ZIP-нагрузок. Поддержан действующий порядок уравнений Enersy: P(PV/PQ), Q(PQ), |V|²(PV). Геометрия, выбор физических моделей и итерации Newton находятся вне этого модуля. Нельзя передавать вместо рассчитанных P/Q паспортные мощности.

Три новых Rust-теста проверяют аналитическую двухузловую цепь (допуск 10⁻¹²), центральные разности при h=10⁻⁶ (допуск 5·10⁻⁷), несимметричную комплексную Y, отсутствующую диагональ PQ, PV/PQ в произвольном порядке, несколько ZIP-записей на узле, смену состояния и неверные данные. Все 8 тестов `numerics`, включая прежний PCG, прошли в debug/release; clippy прошёл с запретом предупреждений.

Стенд использует три семейства сетей на 1k/10k/100k узлов, seed=20261021, неплоское состояние Vᵢ из генератора. Каждый седьмой узел — PV, на каждом десятом PQ заданы тестовые ZIP-производные. Это проверка Якобиана в точке, не полный расчёт режима. Все элементы девяти Rust/Julia-матриц совпали точно на данном стенде; заранее заданный предел сравнения — 10⁻¹¹ плюс 10⁻¹²·max|JJulia|. Совпадение битов на других платформах не обещается.

По 9 измерений, Linux Docker, лимиты 2 CPU / 2 ГиБ, один поток Julia/BLAS, CPU-архитектура `znver3`, Julia 1.10.12, rustc 1.85.1, Rust release. Для Julia-пересборки и Rust-update выполнено по три прогрева; Rust-план уже создавался перед пробами. Первый вызов/создание плана записаны отдельно. Ни компиляция Rust, ни запуск процесса, ни обмен файлами в kernel-время не входят.

| Сеть 100k | Julia*, мс | Rust полный**, мс | Rust update, мс |
| --- | ---: | ---: | ---: |
| Радиальная | 89,764 | 29,712 | 5,997 |
| Кольцо | 58,352 | 30,136 | 4,360 |
| Сетка | 104,185 | 63,447 | 7,520 |

\* Текущая production-функция Julia строит структуру заново при каждом вызове. \** Rust полный включает новый план, выделение выходного буфера и update. Медианы отдельных стадий не складываются в медиану полного вызова. Выигрыш повторного update объединяет смену алгоритма хранения и языка; Julia с аналогичным переиспользованием структуры здесь не измерялась. Это не доказательство превосходства языка или ускорения всего Newton.

Для 1k полная Rust-пересборка местами медленнее: radial 0,441 против Julia 0,377 мс, mesh 0,611 против 0,472 мс. Чтение входа и запись выхода Rust-пробы на 100k потребовали примерно 385–656 мс; полный контейнерный wall-time дополнительно включает запуск и все пробы. Это показывает стоимость данного файлового стенда, не будущего FFI. Пики cgroup двух отдельных runtime включают входы, все пробы и служебные операции; их нельзя переносить на общий процесс Julia+Rust или трактовать как память одного update.

[Исходные измерения, лимиты, контрольные суммы и версии образов](/benchmarks/rust-jacobian-20261022.json). Бинарные промежуточные файлы после проверки удаляются; генератор и параметры позволяют создать их заново. Код Julia-стороны включён в [справочник](/generated/code/backend-julia__benchmark__rust_jacobian_jl).

Экспериментальная [граница C ABI уже проверена и измерена](./native-jacobian.md); далее нужны подключение к итерациям worker, переиспользование/сброс плана при PV↔PQ и смене схемы, отмена, полные физические эталоны и замеры полного решения. WASM-биндинг ещё не создан. Файловый benchmark не добавлен в путь пользовательского расчёта; Docker/Compose остаётся основой поставки.

## Приоритет Rust и браузерные вычисления

Уточнение пользователя 2026-10-21: для новых алгоритмов, требующих высокой скорости, приоритет отдаётся Rust. Проверенные модели Julia сохраняются; перенос конкретного участка принимается после независимой проверки физики и сравнения полной стоимости выполнения. Экспериментальный `numerics` пока не является подключённым AC-решателем. PCG требует симметричной положительно определённой системы; его нельзя автоматически назначать решателем общего якобиана AC.

WASM рассматривается и для расчётных задач, которые разумно выполнять рядом с редактором. Сравнение с текущей реализацией и Rust native на одинаковом сценарии должно учитывать первый запуск с загрузкой/инициализацией модуля, прогретые повторы, передачу и копирование массивов, полный отклик, пиковую память и задержки интерфейса. Число узлов само по себе не определяет место исполнения.

Тяжёлый браузерный расчёт выполняется в Web Worker с прогрессом, отменой, ограничениями ресурсов и обработкой прекращения worker. Закрытие вкладки не считается надёжным фоновым серверным заданием. Native и WASM используют одно ядро без зависимостей от HTTP/DOM, общие версии моделей, единицы и физические эталоны. Место исполнения и версия движка фиксируются в результате; сервер проверяет права и входные данные при сохранении клиентских результатов.

Docker/Compose остаётся основой поставки: WASM собирается контейнерной стадией и поставляется с frontend без обязательного Rust toolchain у пользователя. Автономная сборка BASE-09 и браузерный WASM — отдельные варианты исполнения. Это план PERF-04; браузерный решатель ещё не реализован и ускорение не измерено.

## Автономная локальная сборка

Запрос пользователя от 2026-10-21, задача BASE-09: продолжать развитие текущей архитектуры и добавить второй вариант поставки с вычислениями на компьютере пользователя. Это план, локальный артефакт ещё не реализован.

Основной вариант сохраняет Docker/Compose и вычислительные workers. Автономный вариант должен выполнять поддержанные сценарии офлайн без отдельно разворачиваемого сервиса и ручного запуска worker. Рассматриваются встроенная библиотека либо дочерний процесс, которым полностью управляет приложение. Локальный расчёт не означает обязательного выполнения в UI-потоке или отказа от изоляции тяжёлых задач.

Физические модели, ядро, снимки, диагностика и формат результатов остаются общими. Выбор упаковки Julia/native runtime, поддержанных ОС и способа управления расчётом требует отдельного решения и испытаний; Rust не назначается обязательной заменой Julia. Конечному пользователю не нужны компиляторы и отдельно установленный runtime; сборка и CI могут оставаться контейнерными. Для двух вариантов необходимы общие физические эталоны, совместимость проектов/каталогов и фиксация движка/версии результата. Локальная поставка не отменяет разграничение пользователей и сессий серверной установки.

## Первый собственный kernel

`numerics/src/csr.rs` содержит разреженное хранение и умножение, `pcg.rs` — итерационный алгоритм, `lib.rs` — типизированные ошибки. Нет HTTP/SQL/WASM-зависимостей и скрытых допусков. Разработчик может менять отдельный алгоритм; код входит в [автоматический справочник](/generated/code/). Тесты запускаются `cargo test --manifest-path numerics/Cargo.toml --locked --offline`.

PCG предназначен только для вещественных симметричных положительно определённых систем. Это **не** универсальный решатель AC: Якобиан Ньютона обычно не подходит этому семейству. Проверяются симметрия, диагональ, конечность чисел и положительная кривизна; полная математическая сертификация SPD остаётся условием постановки. Не используется обратная матрица или плотная копия. Тестовая резистивная сеть задаёт Ом/А/В/Вт и аналитические напряжения/баланс; разреженная цепь 1000 неизвестных проверяет число ненулевых элементов и известное решение. Это тест корректности, не измерение промышленного масштаба.

## Доступные Rust-библиотеки

- [faer](https://docs.rs/faer/latest/faer/sparse/linalg/solvers/index.html): кандидат для общей разреженной линейной алгебры и факторизаций; для AC нужен подходящий solver, а не принудительное использование PCG.
- [diffsol](https://github.com/martinjrobins/diffsol): кандидат для ODE/DAE, BDF/SDIRK и событий. Требуются собственные физические тесты, согласованная инициализация и проверка лицензии закреплённой версии перед включением.

Эти зависимости пока не добавлены. Собственные алгоритмы и библиотечные реализации должны работать через одинаковый контракт и комплект эталонов. Реестр моделей должен отдельно описывать применимость, чтобы выбор native-движка не менял физику.

## Предлагаемое разделение

| Средство | Роль | Условие применения |
| --- | --- | --- |
| Julia | Уравнения, экспериментальные модели, сборка и проверка решателей | Сохраняется текущий работающий контур и независимые физические эталоны |
| Rust native | Расчётные kernels или отдельный worker: топология, сборка, повторяемые вычислительные циклы | Сравнение показывает преимущество времени/памяти или требуются предсказуемые задержки |
| C/C++/Fortran | Проверенные библиотеки линейной алгебры и специализированных решателей | Подходящие лицензии, переносимая сборка и тестируемый интерфейс; новый самописный решатель не обязателен |
| Rust WASM | Геометрия, предварительные проверки и подходящие локальные расчёты в Web Worker | Измерен выигрыш полной операции с учётом передачи данных, памяти и задержек UI; общие эталоны с native |
| Go | Задания, API, хранение, ограничения ресурсов | Не добавлять вторую независимую реализацию физических моделей в HTTP-обработчики |

Rust предлагается первым кандидатом для нового native-модуля, поскольку уже есть в проекте. Это не утверждение, что Rust всегда быстрее Julia или C++. Julia требует контроля типов, выделений памяти и отдельного учёта компиляции; эти меры описаны в [официальном руководстве по производительности](https://docs.julialang.org/en/v1/manual/performance-tips/). Julia может вызывать библиотеки с C-интерфейсом через [FFI](https://docs.julialang.org/en/v1/manual/calling-c-and-fortran-code/), Rust также поддерживает [FFI](https://doc.rust-lang.org/nomicon/ffi.html). Это позволяет сравнить небольшой модуль без переписывания приложения.

## Сначала измерение

Первый стенд должен разделять: декодирование и SQL; компиляцию топологии; сборку Y/residual/Jacobian; факторизацию; итерации; сериализацию результатов. Отдельно публиковать холодный запуск и прогретые повторы, версию процессора/OS/toolchain, число потоков, время, пиковую память и выделения.

Кандидатами являются сборка разреженных матриц, вычисление residual/Jacobian, обработка событий и шаги EMT. Для текущего AC-пути переход от плотных матриц к разреженным проверяется до вывода, что ограничение связано с языком. Нельзя сравнивать разные постановки, разные допуски, выключенные физические эффекты или debug Rust с оптимизированной Julia.

Общий набор приёмки фиксирует снимок сети, версии моделей, SI/p.u.-базисы, начальные состояния, события и допуски до измерения. Кроме времени, сравниваются невязки, потоки, баланс энергии и порядок событий. Исправленный физический результат важнее ускорения ошибочного алгоритма.

## Контракт optional native-модуля

Поставка и запуск остаются контейнерными. Будущий Rust worker добавляется в Compose и общается с Go через версионированный протокол; библиотечный kernel при необходимости собирается внутри образа Julia. Отдельный профиль `numerics-check` уже описывает проверку автономной библиотеки; он не добавляет новый рабочий сервер в обычный запуск приложения.

Использовать C ABI для библиотечного kernel либо версионированный протокол отдельного worker. На границе явно задаются Float64/ComplexF64, layout и длины массивов, владение памятью, единицы, версия ABI, коды ошибок и возможности отмены. Не выполнять HTTP/JSON-вызов на каждый элемент или каждый шаг. FFI-вызов сам по себе не обеспечивает изоляцию и принудительную отмену; это ответственность процесса worker.

Снимок и результат фиксируют конкретный движок, версию и настройки. Автоматического молчаливого переключения при ошибке нет. Если опубликована совместимая Julia-реализация, пользователь может явно выбрать её; unsupported-профиль остаётся неподдержанным независимо от языка. Опциональный модуль не должен стать обязательной зависимостью базового проекта.

Подключение к рабочему расчёту требует стенда PERF-01 и численного барьера CORE-07. Автономный прототип и критерии перехода входят в PERF-04; выбор для DAE/EMT проверяется своим сценарием, а не выводится из скорости AC.
