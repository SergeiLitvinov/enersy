# Версии исследования — Study

Статус 2026-10-24: реализованы проектное хранение, HTTP API и типизированный TypeScript-клиент. Версия Study сохраняет согласованный снимок исходной сети, происхождение паспортов и явно заданные настройки AC-расчёта. Данные переживают перезагрузку клиента и не меняются при редактировании схемы. Форма сохранения/выбора Study в редакторе и запуск выбранной версии через Run ещё не подключены. Окно «Границы» пока использует настройки открытого редактора; наличие API не означает, что оно уже восстанавливает Study.

## Что фиксируется

У Study есть стабильный ID в проекте и указатель на последнюю ревизию. Новая ревизия добавляется, старые не переписываются. Каждая версия содержит:

- полный JSON-вход worker: оборудование, параметры, геометрию и связи из серверного снимка;
- явные базисы мощности/напряжения, допуск, бюджет итераций и мягкий бюджет времени;
- выбранные профиль, метод и ID движка, терминальные границы напряжения;
- отдельные байты происхождения экземпляров и проектных паспортов;
- автора, проект, исторический ID/название схемы, ревизию топологии, время и SHA-256 артефактов.

Снимки хранятся как BYTEA. PostgreSQL вычисляет SHA-256 непосредственно по байтам через generated columns; приведение входа worker к JSONB не выполняется. Документ настроек хранится как JSONB с версией формата. `studyReference` во входе содержит строковые ID Study и ревизию. Секреты сессий в снимок не включаются.

Статус версии — `captured`. Он означает захват данных, а не сходимость, физическую пригодность модели или нормативное соответствие. Это пока профиль legacy-симметричного AC, а не полная система ModelBinding. ID движка является запросом; исполняемый файл, его версии и контрольные суммы должен фиксировать будущий запуск. Study не замораживает библиотеку решателя, не доказывает устойчивость и не обещает одинаковый результат разных версий математического кода.

Источник читается в одной REPEATABLE READ транзакции, включая происхождение. Короткая транзакция записи затем повторно проверяет актуальные права и принадлежность схемы, сериализует команды/квоту и проверяет ревизии. Захватывается согласованный источник в момент чтения, а не обязательно состояние на момент commit. Ревизия топологии не является ревизией всех параметров: изменение параметра другой сессией до захвата может попасть в новый снимок. Предыдущая версия Study при этом не меняется. Подтверждение ожидаемого набора ревизий оборудования и визуальное сравнение источника остаются частью будущего workflow.

## Явный документ версии

Для создания нужен действующий проект и его схема. Пример тела запроса; `topologyRevision` берётся из прочитанной схемы:

```json
{
  "topologyRevision": "0",
  "document": {
    "formatVersion": 1,
    "name": "Рабочий режим",
    "modelGroup": "three-phase",
    "method": "newton-raphson",
    "computeBackend": "julia",
    "maxTimeMs": 20000,
    "base": {"s_base_mva": 100, "v_base_kv": 10},
    "solverOptions": {"tolerance": 1e-8, "max_iterations": 50},
    "operatingLimits": []
  }
}
```

Базисы — МВА и линейное действующее кВ, допуск невязки — p.u. Все поля обязательны; скрытых значений по умолчанию нет. Пустой список границ задаётся `[]`, не null. Поддержаны ID движка `julia` и `julia-rust-jacobian`, только `three-phase/newton-raphson`, 1..20000 мс, 1..1000 итераций, положительные конечные базисы/допуск и до 1000 явных границ. Существование физического терминала и разрешимость сети проверяет будущий расчёт; при захвате проверяется, что компонент границы принадлежит снимку. Недоступный в данный момент движок не мешает сохранить намерение; это не разрешение на автоматический fallback при запуске.

## HTTP и конфликты сессий

Все пути ниже начинаются с `/api/projects/{project}`. ID и ревизии — точные десятичные строки BIGINT; ID схемы/оборудования остаётся в диапазоне PostgreSQL INTEGER.

| Метод и путь | Назначение |
| --- | --- |
| `POST /schemes/{scheme}/studies` | Создать Study и версию 1 со снимком |
| `POST /studies/{id}/versions` | Добавить следующую версию того же источника |
| `GET /studies?afterId=...&limit=20` | Последние версии Study, страница по стабильным ID |
| `GET /studies/{id}` | Метаданные текущей версии |
| `GET /studies/{id}/versions?afterRevision=...&limit=20` | История, страница по ревизиям |
| `GET /studies/{id}/versions/{revision}` | Метаданные конкретной версии |
| `GET /studies/{id}/versions/{revision}/input` | Точные байты входа worker |
| `GET /studies/{id}/versions/{revision}/provenance` | Точные байты происхождения |

Записи требуют корректный Origin, JSON Content-Type и UUID `Idempotency-Key`. При добавлении версии обязателен сильный `If-Match: "N"` — ревизия Study, которую редактировал пользователь. `topologyRevision` в теле относится к исходной схеме; это другая шкала. `ETag` метаданных подтверждает ревизию Study, а `ETag` артефакта — SHA-256 его байтов. Ответы имеют no-store и текущую проверку сессии/проекта. Владельцы, admin и editor могут сохранять; viewer может читать, но не создавать версию. Чужой ID или утраченный доступ не дают данные через другой доступный проект.

Повтор той же команды с теми же документом, источником и ожидаемыми ревизиями возвращает прежнюю версию, даже если исходная схема уже изменена или удалена. Нельзя менять UUID команды после потери подтверждения, пока исход не проверен. Повтор UUID с другим намерением возвращает 409 `study_command_conflict`. Два разных сохранения одной ожидаемой ревизии дают ровно одного победителя; второе получает 412 `study_revision_conflict`, без изменения истории. Неверная ревизия источника — 412 `study_source_conflict`. Клиент не повторяет конфликтующую запись автоматически и не переписывает локальный документ.

Исторический ID схемы не является живым FK: удаление схемы не удаляет захваченные байты. При создании SQL trigger проверяет исходную принадлежность проекту; перепривязка идентичности Study запрещена. Старые версии защищены от UPDATE/DELETE. Удаление всего проекта может удалить его частную историю; отдельного API удаления версии сейчас нет.

Текущие пределы: тело настроек 128 KiB, вход и происхождение по 8 MiB, 100 версий и суммарно 64 MiB на проект с учётом документов/входов/происхождения. Превышение возвращает 413 и откатывает запись/указатель версии. Это границы текущей поставки; крупные потоковые снимки и политика очистки остаются в TODO.

## Доступ разработчика

Клиент [TypeScript API](/api/typescript/index.html) экспортирует `createStudy`, `appendStudyVersion`, `readStudy`, `listStudies`, `listStudyVersions`, `readStudyArtifact`. Создание и добавление версии требуют явный документ, UUID команды, ревизию источника и AbortSignal. Запросы используют одну текущую cookie-сессию, отмену и no-store; пользовательский ID не передаётся как доказательство прав. Проверяются область ответа, ID, ETag, подтверждение документа и целочисленная ревизия без потери точности.

`readStudyArtifact` читает фиксированную версию с контролем длины, заголовков идентичности и независимым SHA-256 через Web Crypto. Возвращаются Uint8Array, чтобы потребитель мог разбирать крупный JSON вне потока интерфейса. Разрыв чтения/отзыв доступа не возвращает частичный объект. Функция не является запуском или отменой расчёта worker.

Публичного маршрута запуска версии пока нет. Не отправляйте полный захваченный вход в старый проектный calculate: он по-прежнему читает текущую схему и принимает только свои опции. Следующий этап — запуск по ссылке на неизменяемую версию с отдельным происхождением результата, затем форма выбора/сохранения и сравнения Study в редакторе. Существующая защита приватного расчёта не ослабляется ради исторической схемы.

## Проверки и миграция

Миграция `20261024001_project_studies` проверена на пустой/обновлённой PostgreSQL, вместе с прежними миграционными регрессиями. SQL запрещает чужую исходную схему, пропуск ревизий, висячий указатель и изменение/удаление версии. Down отказывается удалять существующую историю; пустой up/down проходит. Полный backup/restore подтвердил байты, SHA-256, кириллицу, последовательности и неизменяемость Study, включая цикл FK head/version. Повторное восстановление в существующую БД и повреждённый dump отклоняются.

Полный Go-набор с настоящими PostgreSQL и Rust-worker прошёл. Новые проверки покрывают сохранение/повтор команды, параметры источника, конфликт двух сессий, viewer/чужой проект/отзыв сессии, ID больше 2^53, историю после удаления схемы, предел количества и отдельно предел байтов с откатом. Последний использует явно обозначенный storage fixture с длинной строкой legacy-параметра, не физический эталон. `go vet` прошёл; локальный race не запускался из-за отсутствия cgo toolchain, существующий CI Go выполняет race. Удалённый CI здесь не подтверждён.

`TestStudyFrozenInputWorkerPostgres` дважды запускает сохранённый вход на настоящем Rust-Якобиане после изменения нагрузки в БД. Независимый эталон: E=1 кВ, R=1 Ом, P=0,2 МВт, Q=0; `V=(1+sqrt(0,2))/2`, допуск 1e−10 кВ. Получен прежний режим, а не режим изменённой нагрузки. Проверка включена в Docker-команду native-приёмки вместе с настоящим архивом; команда прошла локально. Само численное ядро этим этапом не менялось.

Frontend: 491 успешно, одна opt-in HTTP-проверка пропущена; типы, lint и сборка прошли. Восемь новых проверок клиента охватывают явный документ, область, CAS без автоматического повтора, точные ID/курсоры, длину/идентичность/SHA-256 артефакта, отмену и утраченный доступ. Пользовательская форма Study ещё не существует и браузерная приёмка её не заявляется.
