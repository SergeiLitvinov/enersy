# Версии исследования — Study

Статус 2026-10-25: реализованы проектное хранение, HTTP API, типизированный TypeScript-клиент и интерфейс исследований в навигаторе проекта. Версия Study сохраняет согласованный снимок исходной сети, происхождение паспортов и явно заданные настройки AC-расчёта. Данные переживают перезагрузку клиента и не меняются при редактировании схемы. Сохранение, выбор, история и просмотр снимка доступны из проекта; запуск выбранной версии через Run ещё не подключён. Окно «Границы» пока использует настройки открытого редактора; наличие API не означает, что оно уже восстанавливает Study.

## Что фиксируется

У Study есть стабильный ID в проекте и указатель на последнюю ревизию. Новая ревизия добавляется, старые не переписываются. Каждая версия содержит:

- полный JSON-вход worker: оборудование, параметры, геометрию и связи из серверного снимка;
- явные базисы мощности/напряжения, допуск, бюджет итераций и мягкий бюджет времени;
- выбранные профиль, метод и ID движка, терминальные границы напряжения;
- отдельные байты происхождения экземпляров и проектных паспортов;
- автора, проект, исторический ID/название схемы, ревизию топологии, время и SHA-256 артефактов.

Снимки хранятся как BYTEA. PostgreSQL вычисляет SHA-256 непосредственно по байтам через generated columns; приведение входа worker к JSONB не выполняется. Документ настроек хранится как JSONB с версией формата. `studyReference` во входе содержит строковые ID Study и ревизию. Секреты сессий в снимок не включаются.

Статус версии — `captured`. Он означает захват данных, а не сходимость, физическую пригодность модели или нормативное соответствие. Это пока профиль legacy-симметричного AC, а не полная система ModelBinding. ID движка является запросом; исполняемый файл, его версии и контрольные суммы должен фиксировать будущий запуск. Study не замораживает библиотеку решателя, не доказывает устойчивость и не обещает одинаковый результат разных версий математического кода.

Источник читается в одной REPEATABLE READ транзакции, включая происхождение. Короткая транзакция записи затем повторно проверяет актуальные права и принадлежность схемы, сериализует команды/квоту, сверяет топологию и ревизии оборудования с прочитанным входом. Строки оборудования блокируются FOR SHARE до commit/rollback: триггер изменения параметров не может незаметно продвинуть ревизию после проверки. При расхождении запись целиком откатывается с 412 `study_source_conflict`.

Это серверная проверка окна между чтением и записью. Клиент пока присылает ожидаемую топологию, но не полный манифест ревизий параметров, которые показывались в его вкладке. Изменение до серверного чтения может попасть в новый снимок. Версионированный контракт единиц каталога также не заменяется ревизией оборудования. Предыдущие версии Study не меняются; клиентский манифест и визуальное сравнение источника остаются частью будущего workflow.

### Сверка оборудования перед фиксацией — 2026-10-26 {#source-revision-guard}

`calculationComponent.Revision` читается вместе со значениями в исходной транзакции и не сериализуется в запрос worker (`json:"-"`); ревизии происхождения по-прежнему находятся в отдельном артефакте. После блокировок проекта и схемы `checkStudySourceRevisions` одним упорядоченным запросом сравнивает ID/ревизии всех объектов и удерживает их строки до завершения короткой транзакции. Численный worker в этой транзакции не вызывается. Новая SQL-миграция и изменение HTTP-формата запроса не требуются.

Прежний код сохранял согласованный, но уже устаревший источник, если параметр менялся после чтения при прежней топологии. Регрессия воспроизвела успешную запись версии 1 вместо конфликта. Новый контракт отклоняет такой захват до создания Study/версии. Неуспешная команда не получает квитанцию успеха: явный повтор может захватить обновлённый источник. После успешного сохранения повтор UUID возвращает именно прежнюю версию, даже если параметры снова изменились.

`TestStudyParameterChangeBeforeCommitPostgres` останавливает SaveStudy на реальном advisory-lock после чтения, меняет P нагрузки 0.2 → 0.1 без изменения топологии и проверяет конфликт, отсутствие частичных строк, успешный повтор и неизменность его результата после следующей правки. `TestStudySourceLocksParameterRevisionUntilRollbackPostgres` через `pg_blocking_pids` подтверждает ожидание прямого SQL-писателя на блокировке компонента и освобождение после rollback. Произвольная задержка не используется как доказательство гонки. Отдельная HTTP-проверка сохраняет код `study_source_conflict` и статус 412, уже поддержанные формой. Логи — `.cache/study-source-revisions/`.

Локально в Docker PostgreSQL 15.19 / Go 1.26.10 прошли три новые проверки, прежний жизненный цикл/HTTP Study, полный Go-набор с PostgreSQL и `-race`, `go vet`, сборка бинарника и статический анализ (0 замечаний). Настоящий Go → PostgreSQL → Julia сценарий сохранил независимый физический результат и проверку единиц после добавления внутреннего поля ревизии. Проверка не устанавливает ревизию клиентского отображения до запроса и не добавляет выполнение сохранённой версии Study: это остаётся в CORE-06.

## Явный документ версии

Для создания нужен действующий проект и его схема. Пример тела запроса; `topologyRevision` берётся из прочитанной схемы:

```json
{
  "topologyRevision": "0",
  "document": {
    "formatVersion": 1,
    "name": "Рабочий режим",
    "modelGroup": "three-phase",
    "method": "newton-raphson",
    "computeBackend": "julia",
    "maxTimeMs": 20000,
    "base": {"s_base_mva": 100, "v_base_kv": 10},
    "solverOptions": {"tolerance": 1e-8, "max_iterations": 50},
    "operatingLimits": []
  }
}
```

Базисы — МВА и линейное действующее кВ, допуск невязки — p.u. Все поля обязательны; скрытых значений по умолчанию нет. Пустой список границ задаётся `[]`, не null. Поддержаны ID движка `julia` и `julia-rust-jacobian`, только `three-phase/newton-raphson`, 1..20000 мс, 1..1000 итераций, положительные конечные базисы/допуск и до 1000 явных границ. Существование физического терминала и разрешимость сети проверяет будущий расчёт; при захвате проверяется, что компонент границы принадлежит снимку. Недоступный в данный момент движок не мешает сохранить намерение; это не разрешение на автоматический fallback при запуске.

## HTTP и конфликты сессий

Все пути ниже начинаются с `/api/projects/{project}`. ID и ревизии — точные десятичные строки BIGINT; ID схемы/оборудования остаётся в диапазоне PostgreSQL INTEGER.

| Метод и путь | Назначение |
| --- | --- |
| `POST /schemes/{scheme}/studies` | Создать Study и версию 1 со снимком |
| `POST /studies/{id}/versions` | Добавить следующую версию того же источника |
| `GET /studies?afterId=...&limit=20` | Последние версии Study, страница по стабильным ID |
| `GET /studies/{id}` | Метаданные текущей версии |
| `GET /studies/{id}/versions?afterRevision=...&limit=20` | История, страница по ревизиям |
| `GET /studies/{id}/versions/{revision}` | Метаданные конкретной версии |
| `GET /studies/{id}/versions/{revision}/input` | Точные байты входа worker |
| `GET /studies/{id}/versions/{revision}/provenance` | Точные байты происхождения |

Записи требуют корректный Origin, JSON Content-Type и UUID `Idempotency-Key`. При добавлении версии обязателен сильный `If-Match: "N"` — ревизия Study, которую редактировал пользователь. `topologyRevision` в теле относится к исходной схеме; это другая шкала. `ETag` метаданных подтверждает ревизию Study, а `ETag` артефакта — SHA-256 его байтов. Ответы имеют no-store и текущую проверку сессии/проекта. Владельцы, admin и editor могут сохранять; viewer может читать, но не создавать версию. Чужой ID или утраченный доступ не дают данные через другой доступный проект.

Повтор той же команды с теми же документом, источником и ожидаемыми ревизиями возвращает прежнюю версию, даже если исходная схема уже изменена или удалена. Нельзя менять UUID команды после потери подтверждения, пока исход не проверен. Повтор UUID с другим намерением возвращает 409 `study_command_conflict`. Два разных сохранения одной ожидаемой ревизии дают ровно одного победителя; второе получает 412 `study_revision_conflict`, без изменения истории. Неверная ревизия источника — 412 `study_source_conflict`. Клиент не повторяет конфликтующую запись автоматически и не переписывает локальный документ.

Исторический ID схемы не является живым FK: удаление схемы не удаляет захваченные байты. При создании SQL trigger проверяет исходную принадлежность проекту; перепривязка идентичности Study запрещена. Старые версии защищены от UPDATE/DELETE. Удаление всего проекта может удалить его частную историю; отдельного API удаления версии сейчас нет.

Текущие пределы: тело настроек 128 KiB, вход и происхождение по 8 MiB, 100 версий и суммарно 64 MiB на проект с учётом документов/входов/происхождения. Превышение возвращает 413 и откатывает запись/указатель версии. Это границы текущей поставки; крупные потоковые снимки и политика очистки остаются в TODO.

## Доступ разработчика

Клиент [TypeScript API](/api/typescript/index.html) экспортирует `createStudy`, `appendStudyVersion`, `readStudy`, `listStudies`, `listStudyVersions`, `readStudyArtifact`. Создание и добавление версии требуют явный документ, UUID команды, ревизию источника и AbortSignal. Запросы используют одну текущую cookie-сессию, отмену и no-store; пользовательский ID не передаётся как доказательство прав. Проверяются область ответа, ID, ETag, подтверждение документа и целочисленная ревизия без потери точности.

`readStudyArtifact` читает фиксированную версию с контролем длины, заголовков идентичности и независимым SHA-256 через Web Crypto. Возвращаются Uint8Array, чтобы потребитель мог разбирать крупный JSON вне потока интерфейса. Разрыв чтения/отзыв доступа не возвращает частичный объект. Функция не является запуском или отменой расчёта worker.

Публичного маршрута запуска версии пока нет. Не отправляйте полный захваченный вход в старый проектный calculate: он по-прежнему читает текущую схему и принимает только свои опции. В интерфейсе проекта доступны сохранение, выбор, история, просмотр снимка и сравнение настроек при конфликте; [порядок работы](../guide/studies.md). Следующий этап — запуск по ссылке на неизменяемую версию с отдельным происхождением результата и полное сравнение сетей. Существующая защита приватного расчёта не ослабляется ради исторической схемы.

## Проверки и миграция

### Интерфейс проекта · 2026-10-25

В навигаторе проекта добавлены раздел исследований и действие захвата выбранной сохранённой схемы. Форма явно требует физические базисы и позволяет задать движок, бюджет, настройки решателя и терминальные границы. Чтение истории и снимка не зависит от живой схемы. Отдельный просмотр использует существующие таблицы архивного входа и происхождения, без выдуманных ревизий оборудования или ID связей ради графического preview. Геометрическое сравнение сетей пока не реализовано.

При CAS-конфликте черновик сохраняется, актуальный документ показывается отдельно. Принятие новой ожидаемой ревизии не записывает данные автоматически. При неизвестном исходе записи повтор использует ту же команду и тело; поля временно заблокированы. Следующим этапом добавлен журнал вкладки, описанный ниже; API-идемпотентность сама по себе не заменяет восстановление клиентского намерения.

Итоговый полный frontend-набор на этом этапе: 501 тест успешно, одна opt-in HTTP-проверка пропущена; типы, lint и production-сборка прошли. В набор входят 10 тестов формы/навигатора/парсера снимка. Они проверяют явные базисы, запрет записи viewer, сохранение черновика при конфликте, отдельное подтверждение нового CAS, повтор прежней команды при сетевой ошибке, чтение исторической версии, отсутствие чтения живой схемы для снимка, удалённый источник, смену проекта и отзыв доступа. Численное ядро и SQL этим этапом не изменены; прежние численные проверки здесь повторно не заявляются.

Браузерная проверка выполнена на отдельном Docker-стенде `enersy-study-ui` с разрешённым временным аккаунтом. Созданы исходная схема с одной шиной и три версии исследования. После изменения параметра объекта первая версия сохранила происхождение ревизии 1 и прежние данные, вторая получила ревизию 2 и новое значение. Выбор экспериментального Rust-движка и границы 9–11 кВ сохранились в документе, без запуска расчёта. Запись от устаревшей версии получила конфликт; форма сохранила свой текст, показала актуальные настройки и создала третью версию только после отдельного подтверждения. После перезагрузки страницы история и выбор второй версии также восстановлены через навигатор проекта без предварительного выбора живой схемы. Проверено оформление формы и раздела, в том числе фактически узкое окно браузера. Это проверка workflow хранения, а не физический эталон одношинной сети.

### Хранение и API · 2026-10-24

## Журнал команды вкладки · 2026-10-25

Команда создания/добавления Study до первого POST синхронно сохраняется в ограниченный sessionStorage-журнал, отдельно для аккаунта, сессии и проекта. Не сохраняются auth-токен, пароль, граф сети или optimistic acknowledgement. Формат, ID, настройки и длина проверяются при каждой загрузке. Одна запись на проект, до 32 записей на вкладку и 128 КиБ на запись; другое намерение не может перезаписать незавершённую команду. Недоступная/повреждённая запись блокирует dispatch. Повтор использует прежний UUID/документ/CAS; acknowledgement проверяется SDK, после чего запись удаляется. Прерванный компонент оставляет подготовленную команду. Форма/навигатор не отправляют её автоматически после remount/reload. Ручная очистка не отменяет серверный commit.

UI передаёт ожидаемые `X-Enersy-Account-Id` и `X-Enersy-Session-Id`. Сервер проверяет их против той же извлечённой cookie-сессии, с которой выполняется Store; несовпадение — 409 `study_session_changed` до захвата или replay. Токен и права по-прежнему проверяются сервером; ID не дают доступа. Старые API-клиенты без обоих заголовков сохраняют прежний контракт; частичный/повторный заголовок отклоняется. Выход и обнаруженная смена identity очищают прежние записи этой функции в пределах вкладки; вкладки и проекты не разделяют один mutable active intent. Изменение роли пересоздаёт контекст; viewer не отправляет восстановленную запись.

Это восстановление в той же вкладке/сессии, без гарантии пережить закрытие вкладки, новую сессию или очистку браузером. Приватное локальное хранилище не является серверным журналом или средством защиты от доступа к самому браузерному профилю. Истечение доступа скрывает UI; дальнейшая запись требует актуальных прав. Полный серверный журнал/межустройственное восстановление и ожидаемый manifest ревизий параметров остаются открытыми. Повтор ещё не выполненной команды может захватить изменённые параметры при неизменной топологии; уже выполненная команда возвращает прежний снимок.

Docker-проверки: 509 frontend-тестов прошли, одна opt-in HTTP-проверка пропущена; typecheck, lint и production build прошли. Новые проверки охватывают сохранение до отправки, отказ при недоступном хранилище, сохранность команды/документа после remount, отсутствие автоматического POST, явный повтор и очистку после подтверждения, изоляцию аккаунта/сессии/проекта, повреждённую запись и очистку только своих storage-ключей. Реальная PostgreSQL-проверка Study HTTP подтвердила правильный bound replay, отказ другого аккаунта и другой сессии того же аккаунта, запрет повторного заголовка и отсутствие новых версий при отказе. `go vet` прошёл; численные модели этим этапом не менялись.

Браузер: на одноразовом `enersy-study-ui` подтверждение создания намеренно потеряло ETag в тестовом nginx, тогда как реальный API выполнил commit. БД содержала ровно одну версию. После reload и открытия проекта журнал появился без автоматического повтора; после возвращения штатного nginx и явного повтора открылась исходная версия №1, локальная запись исчезла, в БД осталось `count=1, max(revision)=1`. Использовалась пустая схема как fixture хранения, а не физический эталон. Тестовая конфигурация в основной поставке не используется.
