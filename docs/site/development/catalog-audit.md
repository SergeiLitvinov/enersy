# Сверка старого каталога с seed-эталоном

Команда `server -audit-catalog` сравнивает фактический каталог с эталоном, созданным из **чистой PostgreSQL-базы полным набором миграций**. Она работает только на чтение и не применяет миграции. Эталон описывает поставляемые seed-данные программы, а не подтверждённые заводом характеристики или физическую пригодность оборудования.

## Запуск

```powershell
./scripts/database/Audit-EnersyDatabase.ps1 -Catalog -OutputFile .cache/catalog-audit.json
```

Каталог вывода должен существовать. Можно вызвать CLI напрямую внутри контейнера:

```powershell
docker compose exec -T go-api /app/server -audit-catalog
```

Это отдельный режим от `-audit-database`; одновременно выбирать их нельзя. HTTP-маршрута нет. Ни один из режимов аудита не запускает обычный сервер или обновление БД. Для ещё не обновлённой базы используется одноразовый контейнер с нужным образом и параметрами подключения: обычный запуск API выполняет миграции и не заменяет предварительный аудит. Поля `database` и `schema` идентифицируют область подключения для последующего операторского разбора.

## Область сравнения

| Раздел | Естественный ключ | Сравниваемые поля |
| --- | --- | --- |
| `types` | код типа | имя, категория, описание |
| `templates` | код типа + ключ параметра | имя, тип, default, единица |
| `models` | код типа + название модели | производитель, описание |
| `model_params` | код типа + название модели + ключ параметра | сохранённое значение |
| `ports` | код типа + имя порта | домен |

Числовые ID не определяют равенство с эталоном. Переименование, регистр и точный текст значимы; trim, case folding, подстановка defaults и численное округление не выполняются. `NULL`, пустая строка, `10.5` и `10.500` различаются. Производитель пока является полем legacy-модели, а не частью её ключа: это отражает текущую схему БД, а не универсальную идентичность изделия.

Отсутствующая таблица или нужный столбец обозначается `available=false`, `actualRows=null`; это не превращается в нулевой результат или перечень якобы доказанных пропусков. LEFT JOIN сохраняют строки с отсутствующей привязкой к родителю: они попадают в `invalid`, а не исчезают из отчёта. Описание legacy-портов не подтверждает существование физической модели/терминала.

Все чтения относятся к одной подтверждённой PostgreSQL транзакции `READ ONLY REPEATABLE READ`. Используются те же ограничения запросов, что в [общем аудите](./bootstrap-audit.md). До 100 000 строк каждого раздела проверяются целиком; превышение лимита завершает операцию с ошибкой, без частичного успешного отчёта.

## Категории и привязки

| Категория | Значение |
| --- | --- |
| `matched` | одна исходная запись соответствует эталонному ключу и полям |
| `modified` | ключ найден однозначно, сохранённые поля отличаются |
| `extra` | однозначная запись отсутствует в эталоне; это может быть пользовательская модель |
| `missing` | эталонный ключ не найден в доступном исходном разделе |
| `ambiguous` | несколько кандидатов на ключ либо один исходный ID относится к нескольким ключам; автоматического выбора нет |
| `invalid` | нет полного ключа или пригодной ссылки на исходную строку |

`modified` не доказывает ошибку или авторство ручного изменения; отличаться могут и версии исходного справочника. Аудит не исправляет значения по эталону. Для каждой привязки выдаются раздел, SHA-256 ключа, категория, исходные ссылки и имена изменившихся полей. Строковые ID не округляются. Для `ports` ссылка составная: ID типа и хеш имени порта. Её нельзя считать отдельным SERIAL ID.

Для каждого раздела выводятся полные счётчики и до 1000 привязок. Для неоднозначного ключа выдаётся до 20 исходных ссылок. `bindingsTruncated` и `refsTruncated` прямо обозначают неполный список деталей; они не меняют полных счётчиков и не разрешают выбрать первого кандидата. Отчёт не является готовой командой переноса или правом записи. Перед будущим применением плана требуется подтвердить целевую БД, актуальность снимка, все связи и способ разрешения неоднозначности.

В JSON не выдаются имена изделий, производители и паспортные значения. Ключи и поля сравниваются по SHA-256; ссылки на строки нужны оператору для закрытого разбора конкретных ID. `snapshotSha256` относится к каноническому набору исходных ссылок, ключей и хешей полей, независимо от порядка чтения строк. `baselineSha256` — хеш канонического JSON разобранного эталона, а не SHA файла с его отступами. `migrationSha256` связывает эталон с отсортированными версиями/контрольными суммами применяемых up-SQL; CRLF нормализуются как в основном миграторе. Эти суммы не защищают от администратора, имеющего право изменить программу и БД.

Статус `matches_seed_baseline` относится только к перечисленным ключам и полям. Это не полный аудит структуры, пользователей, приватного каталога, физики, единиц, нормативного соответствия или готовности расчёта. Он не заменяет `-audit-database`, резервную копию или проверку происхождения паспортов. Ошибки и неизвестный/устаревший эталон не дают частичный успешный отчёт; наблюдаемые отличия дают `review_required` при успешном выполнении CLI. Автоматизация читает статус и счётчики, а не только код завершения.

## Воспроизводимый эталон

Файл `database/catalog-baseline.v1.json` поставляется в образе API. Его записи не содержат исходных числовых ID. Для версии `20261024001` эталон содержит 13 типов, 77 шаблонов, 90 моделей, 389 паспортных параметров и 35 описаний портов — всего 604 записи.

После изменения миграций разработчик явно запускает:

```powershell
./scripts/database/Update-CatalogBaseline.ps1
```

Скрипт поднимает собственную PostgreSQL в tmpfs без host-портов, запускает Go-тест-генератор и удаляет свой стенд. Go/компилятор на host не требуется; образ инструментария можно задать через `-GoImage`. Источник приложения монтируется только для чтения, каталог результата доступен для записи. Генератор всегда создаёт новую изолированную схему, применяет миграции и требует чистую версию с проверенной `applied`-историей, без исторического baseline. Генератор сверяет отпечатки SQL до и после чтения, а также сохранённую историю применённых байтов; несогласованный источник отвергается.

Это операция разработки, перезаписывающая только эталонный JSON; она не читает рабочую БД и не копирует оттуда значения. Diff эталона нужно просмотреть. Обычный `TestCatalogBaselinePostgres` в существующем PostgreSQL CI заново разворачивает чистую схему и сравнивает результат с поставляемым JSON; автоматического переписывания при обычных тестах нет. В Go CI явно задано `UPDATE_CATALOG_BASELINE=0`. При runtime-чтении проверяются формат и отпечаток полного набора up-SQL; содержимое эталона независимо воспроизводится и сравнивается в CI. Во время рабочего аудита отдельная чистая БД не создаётся.

В разработке `CATALOG_BASELINE_SOURCE` может задать другой файл. Формат, размер до 2 МиБ, состав разделов/полей, уникальность ключей и связь с миграциями проверяются до сравнения. Этот параметр не предназначен для объявления пользовательской базы новым эталоном.

## Проверки 2026-10-25

На PostgreSQL 15 в Docker подтверждены чистая база, оба исторических SQL, точность строковых ID, неизменность источника, порядок строк, NULL/пустая строка, ручное значение, пользовательская модель, пропущенный параметр, неоднозначные ключи/исходные ID, запись без родителя, отсутствующий раздел, устаревший эталон и ограничения деталей. NULL/пустая строка дополнительно проверены независимым Go SHA-256 по байтовому контракту: `0x00` для NULL, `0x01 + UTF-8` для заданной строки.

Исторический `ees_schema.sql` до миграций содержит 313 паспортных параметров вместо 389: аудит показывает 76 пропусков. Для обоих исторических источников отдельный тест явно изменяет значение и добавляет модель, затем запускает штатную миграцию. Пропуски восполняются, пользовательское значение и модель сохраняются с прежними ID; аудит после обновления продолжает показывать эти отличия. Строки fixture служат проверке хранения, а не физическим примером.

Повторный запуск PowerShell-генератора дал тот же JSON. `go vet`, проверки каталога и прежние миграционные регрессии прошли. На рабочей установке режим сравнения подтвердил 604 совпадения в этой области; данные не исправлялись. Это не новый прогон численного ядра, не подтверждение удалённого CI и не завершение разбора legacy-пользователей по именам.

## Явная карта ссылок на legacy-модели {#legacy-model-map}

Операторские команды `-check-catalog-map` и `-apply-catalog-map` проверяют и применяют явно подготовленную карту привязок экземпляров к общему legacy-каталогу. Они предназначены для разбора конкретных исходных ID после аудита. Кандидат не выбирается по имени или первым совпадением: оператор задаёт каждый исходный и целевой ID, объект, схему, ожидаемую ревизию и причину выбора. Можно выбрать разные целевые модели для разных объектов, ранее ссылавшихся на один ID.

Операция меняет только `scheme_components.equipment_model_id`. Сохранённые значения параметров, их текстовая точность, имена, координаты, соединения, строки каталога, пользователи и права остаются прежними. Проектные версии паспортов не переназначаются. Совпадение названия или типа само по себе не подтверждает эквивалентность изделий: выбор и происхождение целевой модели требуют отдельной проверки. Карта не копирует defaults нового паспорта в экземпляр и не исправляет расчётную модель.

### Формат карты

Вход — один UTF-8 JSON до 1 MiB; максимум 1000 изменений. Все ID и ревизии — положительные десятичные строки без ведущих нулей. Неизвестные поля, дубли ключей (включая различие только регистром), повтор объекта, лишний JSON и числовые ID отклоняются. `reason` обязателен, до 1000 байт UTF-8.

```json
{
  "formatVersion": 1,
  "scope": "legacy-model-reference-map",
  "database": "app_db",
  "schema": "public",
  "snapshotSha256": "<точное значение из текущего audit-catalog>",
  "baselineSha256": "<точное значение из текущего audit-catalog>",
  "migrationSha256": "<точное значение из текущего audit-catalog>",
  "changes": [
    {
      "componentId": "123",
      "schemeId": "12",
      "expectedRevision": "8",
      "fromModelId": "17",
      "toModelId": "23",
      "reason": "Выбор по проверенному источнику после разбора неоднозначности"
    }
  ]
}
```

Это шаблон структуры, а не готовая карта: подставляются реальные сведения, три отпечатка должны содержать 64 шестнадцатеричных символа. `database`/`schema` тоже берутся из своего аудита. Файл карты и JSON-квитанция могут содержать операторский комментарий; общий аудит по-прежнему не выводит названия изделий или паспортные значения.

### Проверка и применение

До применения сохраняют и проверяют резервную копию. Рабочие записи не исправляются при сборке или штатном запуске сервера. Обе команды обходят bootstrap/мигратор и требуют уже полностью обновлённую, чистую БД с согласованной историей checksum. Исторический `legacy-baseline` допускается как зафиксированное состояние, не как доказательство прежних байтов SQL.

```powershell
$map = Get-Content -LiteralPath .cache/reviewed-catalog-map.json -Raw -Encoding utf8
$map | docker compose exec -T go-api /app/server -check-catalog-map
# После проверки самой карты и результата, в окно обслуживания:
$map | docker compose exec -T go-api /app/server -apply-catalog-map
```

Один операторский режим выбирается за запуск; его нельзя совмещать с аудитом, provision или другой командой карты. HTTP-маршрута нет: это операция администратора с прямым доступом к контейнеру/БД, а не обход проектных прав через пользовательский API.

Проверка выполняется в подтверждённой сервером `READ ONLY REPEATABLE READ` транзакции и возвращает `checked_not_applied`. Успешная проверка не резервирует данные для будущего применения: вся проверка повторяется. Применение до чтения каталога получает кратковременные maintenance-блокировки таблиц каталога, экземпляров, схем, параметров и истории миграций. Конфликт блокировки ограничен двумя секундами; запрос — десятью секундами, вся CLI-операция — пятнадцатью. Каталог и обновления проверяются в одной транзакции; при ошибке откатывается весь пакет.

Перед записью должны совпасть область БД, отпечатки источника/эталона/SQL, существующие привязки, ID схемы и ревизии каждого объекта. Старая и новая модели должны принадлежать тому же типу, что экземпляр. Отсутствие строки, проектный паспорт, изменение каталога или параметра после подготовки карты блокируют операцию. Перед commit повторно проверяется источник SQL. Существующий trigger повышает ревизию изменённого объекта; устаревшие редакторы получают конфликт при сохранении. Физические терминалы не меняются, поэтому ревизия топологии не повышается.

Результат `applied` возвращается только после commit. JSON содержит изменения, исходный отпечаток каталога и SHA-256 канонически закодированной карты; хеш не является электронной подписью. Повтор прежней карты отклоняется по ревизии/исходной ссылке. При потере ответа проверяют фактические ссылки и ревизии; автоматически повторять применение или объявлять его неисполненным нельзя. Для обратного переназначения нужна новая явно проверенная карта с актуальными ревизиями. Исторические архивы и замороженные исследования не переписываются.

Это реализованный этап переноса ссылок на модели. Перенос иных legacy ID, разбор неоднозначных пользователей, сохранение внешних ссылок и обобщённые карты импорта остаются в BASE-05; команда их не подменяет.

### Однозначность ID перед картой {#legacy-map-identities}

Проверка и применение карты требуют проверенных, непустых и уникальных `id` в `component_types`, `equipment_models`, `circuit_schemes` и `scheme_components`. Это отдельное условие после сверки истории миграций, до чтения каталожного снимка и проверки изменений. Свежий `snapshotSha256`, корректный тип и существующий target ID не устраняют неоднозначность, если одному ID соответствуют две строки модели. Прежний EXISTS мог принять такую ссылку.

Используется тот же подсчёт идентичности, что и в [общем аудите БД](./bootstrap-audit.md#legacy-identity-checks), но только для четырёх участвующих таблиц. Отсутствующая таблица/ID-колонка, NULL или повтор ID блокируют всю карту. В check сохраняется READ ONLY REPEATABLE READ; при apply проверка выполняется под уже взятыми блокировками этих таблиц. Ничего не объединяется и не перенумеровывается. Проверка не расширяется на `users` или современную авторизацию и не заменяет проверки остальных ссылок/ограничений.

На временной PostgreSQL 15.19 регрессионный тест сначала подтвердил, что прежний валидатор принимает два разных изделия с одним target ID даже после обновления snapshot SHA. После исправления отклоняются check и apply; ссылка и ревизия компонента остаются прежними. Отдельно проверены все четыре таблицы: NULL, повтор ID, отсутствующая колонка/таблица, граница схемы и восстановление корректных данных. Повреждённая посторонняя legacy-таблица не расширяет область этой проверки. Целевой Go-набор с race, vet и сборкой прошёл; рабочая база не изменялась.

### Существование родительской схемы и типа {#legacy-map-parent-links}

Для каждой записи карты должны существовать не только компонент, прежняя и выбранная модели, но и его `circuit_schemes` и `component_types` по сохранённым ссылкам. Проверка уникальных ID сама по себе не обнаруживает отсутствующую строку родителя. Свежий отпечаток каталога также не подтверждает существование схемы: он описывает каталог, а не все строки проекта.

Проверка связей явно соединяет компонент с реальными схемой и типом перед сравнением ревизии и моделей. Поэтому удаление родителя в повреждённой legacy-базе не маскируется совпадением числовых ID в оставшихся строках. Родители не создаются и не выбираются автоматически, связь компонента с ними не меняется. Ограничения по математической модели и project-passport binding остаются прежними.

Проверяется весь пакет до первого UPDATE: если во второй записи потеряна схема, первая корректная запись тоже не применяется. Это относится к check и apply. Регрессионные проверки на одноразовой PostgreSQL 15.19 сначала воспроизвели принятие карт с отсутствующими схемой и типом, затем подтвердили отказ обоих режимов, отсутствие успешного JSON от настоящего CLI и сохранение параметров, ссылок и ревизий. Целевой набор карт с race, go vet и сборкой прошёл. Проверка не исправляет остальные legacy-ссылки и не заменяет общий аудит/backup перед переносом; BASE-05 остаётся открытым.

| Сценарий | Результат |
| --- | --- |
