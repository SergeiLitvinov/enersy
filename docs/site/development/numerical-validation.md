# Численная проверка AC-ядра

## Единицы каталога во входе расчёта — 2026-10-26 {#parameter-unit-labels}

При отсутствии явной декларации экземпляра Go API захватывает единицы из `component_params_template` в той же REPEATABLE READ-транзакции, что значения, оборудование и связи. Единицы шаблонов читаются одним дополнительным пакетным запросом для типов текущей схемы. Для сохранённых ключей, найденных в шаблоне, компонент входа получает `parameterUnits`. Эти сведения попадают и в новые снимки Study/архива, поскольку входят в исходные байты запроса worker. Явные декларации экземпляра, описанные ниже, имеют приоритет. Старые архивы не переписываются. Пример фрагмента компонента:

```json
{"id":2,"type":"load","params":{"p":"10"},"parameterUnits":{"p":"МВт"}}
```

Julia сверяет переданные обозначения с единицами параметров текущей AC-модели до сборки сети. Поддержаны равнозначные обозначения одного масштаба: MW/МВт, Mvar/Мвар, MVA/МВА, kV/кВ, Ohm/Ом/Ω, km/км, Ohm/km/Ом/км/Ω/km, S/km/См/км, deg/град/°, `%`, а для безразмерной величины — `1` или пустая строка. Регистр значим. Для числовых величин пустая строка единицы не означает известную единицу.

Это проверка обозначения, без автоматического пересчёта. `p=10` с единицей `Вт`, `kW`, `mW`, `p.u.` или неизвестным текстом не интерпретируется как 10 MW: возвращается HTTP 400 `parameter_unit_mismatch` с типом/ID оборудования, ключом, переданной и ожидаемой единицей. Нестроковая единица или единица без соответствующего сохранённого параметра также отклоняется. Для номиналов шин/аппаратов проверяется kV, для их положения — безразмерная единица. Описания параметров не создаются заново для каждого объекта; проверка использует общие неизменяемые при обслуживании запросов метаданные реализации.

**Границы:** `parameterUnits` пока необязателен и может быть частичным. Ключи вне legacy-шаблона не получают придуманную единицу. Переданные единицы параметров, не используемых описанием этой AC-модели (например, `c` у q_nom-шунта), не подтверждаются этой проверкой. Старый вход без единиц продолжает использовать опубликованные соглашения модели; его принятие не доказывает происхождение строки. Для параметров без явной декларации проверяется текущая подпись каталога, а не историческая единица экземпляра. Обязательная полнота, физический контракт SI/p.u. и миграция неоднозначных legacy-данных остаются в CORE-01. Само поле не превращает неизвестный паспорт в подтверждённый.

Приёмка Julia — `test/parameter_units.jl`: равнозначные обозначения дают прежние узлы/ветви/баланс точно; восемь неподходящих обозначений мощности отклоняются, проверяются топологические параметры и повреждённые объявления. PostgreSQL-регрессия `TestCalculationInputConcurrentCommitPostgres` меняет значение, положение, связи и единицу одним конкурентным commit: первый вход сохраняет 110 кВ, следующий — 220 V; сочетание 110 V не допускается. Транспортный mock этого теста не является физическим результатом. Отдельная `TestParameterUnitsWorkerPostgres` проходит настоящий путь Go → PostgreSQL → Julia и сравнивает режим с независимым физическим квадратным уравнением, затем меняет единицы только в своей одноразовой БД.

```sh
docker compose --profile julia-check run --rm --no-deps --build julia-check
docker compose -f tests/integration/go-compose.yml --profile parameter-units-check run --rm parameter-units-check
docker compose -f tests/integration/go-compose.yml --profile parameter-units-check down
```

## Явные единицы экземпляра — 2026-10-30 {#instance-unit-declarations}

Миграция `20261030001` добавляет к строке `scheme_component_params` nullable-поля `unit_format_version` и `declared_unit`. Старая запись остаётся без декларации: единица не выводится из сегодняшнего каталога. Версия 1 описывает формат явно указанного обозначения, а не версию математической модели, физическую размерность или подтверждение заводских данных.

Общий атомарный PATCH оборудования, в том числе приватный маршрут проекта, принимает:

```http
PATCH /api/projects/8/schemes/7/components/4
Content-Type: application/json
If-Match: "12"

{
  "params": {"p": "10.0000"},
  "parameterUnitDeclaration": {"formatVersion": 1, "units": {"p": "MW"}}
}
```

Каждая передаваемая единица требует значение того же параметра в этом изменении: сервер не присваивает новую единицу старому числу без явной передачи. Поддержаны также ключи вне legacy-шаблона. Допустимы непустые обозначения до 64 Unicode-символов без окружающих пробелов и управляющих символов. Неизвестная версия, `null`, повторяющиеся ключи декларации и единица без значения отклоняются. Формат не выполняет пересчёт и не доказывает физическую пригодность обозначения; это проверяет выбранный профиль worker.

Права, блокировки родительского проекта/схемы, If-Match и транзакция те же, что у изменения значений. Изменение единицы входит в ревизию компонента через существующий триггер параметров. Ошибка второй части записи откатывает значение, единицу и ревизию целиком. Обычное редактирование значения без новой декларации сохраняет прежнюю явную единицу. API удаления декларации пока нет. Создание из версионированного паспорта проекта фиксирует непустые единицы его собственных параметров вместе со значениями; дополнительные переопределения вне паспорта сохраняют прежний путь без явной декларации.

Снимок схемы и вход расчёта публикуют `declaredParameterUnits: {"formatVersion":1,"units":{"p":"MW"}}` только для явно заданных единиц. Во входе worker карта `parameterUnits` содержит эффективные обозначения: явные единицы имеют приоритет над текущим шаблоном. Остальные параметры сохраняют прежний путь захвата шаблонов. Пустая новая декларация и выдуманное заполнение отсутствующих полей не создаются. Клиент проверяет форму метаданных и соответствие ключей параметрам; в сохранённом входе дополнительно проверяется точное совпадение явных и эффективных обозначений.

Панель обычных параметров и форма нагрузки показывают явную единицу вместо изменившейся подписи шаблона; числовые строки остаются прежними. Если единица меняется при несохранённом тексте, поле и профиль нагрузки блокируют применение такого текста до явного возврата сохранённого состояния; текст не удаляется автоматически. Равенство нового серверного числа введённой строке не отменяет конфликт единиц. В инспекторе доступно отдельное действие «Задать значение и единицу»: оно отправляет одну пару через атомарный PATCH с исходной ревизией. Поле единицы предзаполняется только явной декларацией экземпляра; подпись текущего шаблона остаётся подсказкой. Число не пересчитывается. Прямые расчёты из UI, включая приватное архивирование, всегда запрашивают `unitContract=legacy-ac-three-phase-rms-v1` и требуют подтверждение выбранного профиля в ответе. Неизвестные/неподдержанные единицы, параметры вне профиля и неполная декларация не принимаются как успешный UI-расчёт. Сам HTTP API сохраняет явный выбор профиля для внешних клиентов; глобальная обязательность остаётся открытой задачей. Проверка v1 относится к переданным обозначениям и не удостоверяет историческое происхождение legacy-единиц. История Study/Run хранит захваченные байты и не меняется от следующих правок единиц или справочника. Визуальная приёмка новых подписей ещё открыта вместе с приёмкой выбора профиля Study.

При создании из проектного паспорта непустые единицы копируются из выбранной неизменяемой версии, включая параметры с переопределённым значением экземпляра. Пустая единица не превращается в `1`; дополнительные ключи, которых нет в паспорте, не получают паспортную декларацию из текущего шаблона. Старые экземпляры не дополняются задним числом. Проверка совместимости паспорта с шаблоном перед созданием сохранена: несовместимая новая привязка отклоняется. Уже созданный экземпляр использует свою сохранённую декларацию при последующей смене шаблона.

Значение и паспортная единица вставляются одной строкой в общей транзакции создания; ошибка единицы откатывает весь компонент. Ответ HTTP 201 содержит `declaredParameterUnits` из того же подтверждённого состояния. Парсер ответа и приватный адаптер сохраняют эти данные, а очередь и состояние редактора получают их до следующего чтения графа. Формат результата внутреннего Go-метода создания теперь именованный: ID, значения, ревизия и декларация возвращаются вместе. Числовые строки, источник паспорта, разграничение проектов и правила If-Match последующих правок сохраняются.

Обратная миграция отказывается удалять столбцы при наличии явных деклараций. Проверяющее ограничение берёт блокировку таблицы до удаления столбцов, чтобы не потерять единицы при конкурентной записи. Это намеренная защита данных; downgrade с такими данными требует отдельного плана сохранения и переноса деклараций.

На одноразовом PostgreSQL проверены реальная HTTP-запись с подтверждением ревизии, чтение метаданных в графе, права viewer, устаревший If-Match, приоритет экземпляра над изменённым шаблоном, обычное редактирование значения, атомарный rollback и отказ downgrade без потери декларации. Реальный Study Run Go→Julia сохраняет MW экземпляра даже после смены подписи шаблона на W до захвата и совпадает с независимым физическим эталоном. Seed-baseline пересоздан штатным генератором на свежей БД: изменились только версия/отпечаток цепочки миграций, записи каталога не менялись.

Это сохраняемая декларация обозначений, а не завершённый физический контракт CORE-01. Обязательное заполнение, нормализация SI/p.u., размерности, фазные соглашения, интерфейс ввода и миграция неопределённых legacy-единиц остаются отдельными работами.

### Единицы при восстановлении правок {#recovery-unit-evidence}

Журналы редактора v1/v2 сохраняют необязательное `base.declaredParameterUnits` вместе с исходными значениями. Намерение `parameter` может содержать необязательную строку `unit`: это явно запрошенная единица одновременно переданного значения, а не единица текущего шаблона. Новая форма сохраняет такое намерение в общей очереди. Подтверждение обновляет исходную пару следующих правок; при повторной сверке PATCH включает значение и намеренную декларацию вместе. Старые серверы, не поддерживающие необязательные поля, требуют согласованного обновления с frontend; клиент не удаляет поля ради скрытого обхода ошибки. Снимки и восстановленные рабочие контексты имеют независимые копии декларации; новое чтение схемы не переписывает историческую базу журнала. Сервер проверяет версию, состав, принадлежность ключей исходным параметрам, Unicode и отсутствие повторяющихся ключей. Старый журнал без декларации остаётся без неё: подпись текущего шаблона не становится историческим доказательством.

Трёхсторонняя сверка учитывает исходную, намеренную и серверную единицы. Совпадение числовой строки и намеренной единицы с серверной парой означает `already_applied`: потерянное подтверждение явной смены единицы не требует повторной записи. В остальных случаях изменение серверной единицы относительно исходной, в том числе появление или исчезновение декларации, даёт статус `unit_changed`, даже если числа совпадают. Применение выбранного такого параметра блокируется в интерфейсе и очереди до PATCH. Обозначения сравниваются точно, без автоматического признания алиасов эквивалентными или пересчёта. Пользователь может принять серверную пару и повторно ввести значение в актуальной единице; независимые выбранные поля положения и параметры с неизменившейся единицей разрешаются отдельно. При отсутствии явных единиц с обеих сторон сохранено прежнее сравнение строк с подписью «единица не зафиксирована»; это не подтверждение физической корректности.

Частичное разрешение обновляет исходные значение и единицу вместе. Если во время запроса появилась новая правка того же параметра, а серверная единица отличается, её прежняя исходная пара сохраняется для новой сверки. Принятие серверного состояния не удаляет другие поля или более поздние намерения. Формат журнала хранит данные восстановления, но не выполняет команды при чтении; автоматическое восстановление после reload остаётся отдельной задачей USER-01.

## Полная декларация единиц worker v1 {#unit-contract-v1}

Вычислительный HTTP API Julia принимает явный `unitContract` с целым `formatVersion: 1` и профилем `legacy-ac-three-phase-rms-v1`. Профиль фиксирует соглашения действующей симметричной AC-модели: линейные RMS-напряжения в kV, трёхфазные мощности в MW/Mvar/MVA, сопротивления на фазу в Ohm, углы в deg, длину в km, удельные параметры в Ohm/km и S/km. Смыслы знаков мощности и базисы сохраняются из описаний соответствующих моделей; это не новый SI-конвертер.

Пример полного запроса непосредственно к worker `POST /calculate`:

```json
{
  "unitContract": {"formatVersion": 1, "profile": "legacy-ac-three-phase-rms-v1"},
  "components": [
    {"id": 1, "type": "generator",
     "params": {"p": "0", "r": "0.1", "x": "0.5", "e": "10", "voltage_nom": "10"},
     "parameterUnits": {"p": "MW", "r": "Ohm", "x": "Ohm", "e": "kV", "voltage_nom": "kV"}},
    {"id": 2, "type": "load",
     "params": {"p": "10", "q": "3", "voltage_nom": "10"},
     "parameterUnits": {"p": "MW", "q": "Mvar", "voltage_nom": "kV"}}
  ],
  "connections": [{"from": 1, "to": 2, "fromPort": "bottom", "toPort": "top"}],
  "base": {"s_base_mva": 100, "v_base_kv": 10}
}
```

При указанном контракте каждый компонент требует объект `parameterUnits`, а каждый сохранённый в `params` ключ — известное определение единицы текущей модели и соответствующее обозначение. Это включает описанные моделью ключи вне старого SQL-шаблона: например, `phase_shift_deg` и ZIP-коэффициенты. Неописанные/неиспользуемые поля отклоняются, даже если им приписано знакомое обозначение; пустой объект единиц допустим только при пустом `params`. Единица без параметра тоже запрещена. Безразмерный параметр должен явно объявлять `1`: пустая строка не считается полной декларацией v1.

Равнозначные обозначения того же масштаба (например, Ohm/Ω/Ом) принимаются. W/kW/mW не превращаются в MW, rad — в deg, неизвестная единица не получает default. Неполные объявления отклоняются до сборки сети с `missing_parameter_units` / `missing_parameter_unit`; неописанный ключ — с `unsupported_unit_contract_parameter`. Неизвестная версия/профиль, JSON null вместо контракта, строковая/дробная/логическая версия и дополнительные поля envelope тоже дают HTTP 400. Проверка единиц не подставляет недостающие обязательные физические параметры.

Успешный ответ содержит `input_unit_contract`: версию, профиль, количества проверенных компонентов/параметров и `validation_scope=request-declarations-only`. Для примера выше это 2 компонента и 8 параметров. Это подтверждение деклараций в данном запросе, а не исторического происхождения единиц, достоверности паспорта или сохранения контракта в БД. Численные значения и переданный JSON не изменяются при проверке.

В Go API профиль выбирается параметром запроса `unitContract=legacy-ac-three-phase-rms-v1` для расчёта схемы. Документ Study принимает объект `unitContract` из примера выше; выбранный профиль сохраняется в неизменяемом входе Run и архиве. Клиент проверяет профиль снимка и сохраняет его при редактировании Study. В форме Study доступен выбор проверки единиц: для нового исследования по умолчанию включена полная декларация, при редактировании сохраняется профиль выбранной версии, включая прежний режим без контракта. Переключение изменяет только новую сохраняемую версию. Успешный ответ worker без подтверждения выбранного профиля и количества проверенных компонентов/параметров отклоняется; старый worker не может незаметно выполнить такой запуск без проверки единиц.

Без `unitContract` сохраняется прежняя проверка частичных обозначений, описанная выше; её ответы не получают подтверждение v1. Этот выбор по умолчанию относится к новым Study в форме; непосредственные расчёты схем и внешние API-клиенты продолжают выбирать профиль явно. Go использует явно сохранённые декларации экземпляра; для остальных параметров захватывает текущие обозначения шаблона. Обязательная фиксация единиц при создании/редактировании, разрешение legacy-неопределённостей, обязательный переход обычных запусков и преобразования SI/p.u. остаются в CORE-01. Поэтому весь контракт физических величин ещё не завершён.

На одноразовом Docker-стенде проверены Go→Julia расчёт и Run Study с этим профилем. После создания Study изменение текущих значений и обозначений шаблона не меняет замороженный вход Run; результат проверен по независимому физическому эталону. Отдельно проверены отказ при неподходящем масштабе единиц и отклонение ответа worker без подтверждения профиля.

Для компонента без сохранённых параметров Go явно передаёт `parameterUnits: {}` при выбранном v1: это допустимая пустая декларация, например для идеальной шины. ## Контроль шага Newton и несколько корней — 2026-10-22

[Диагностика 2026-10-26](./root-selection.md) отдельно проверяет неединственность исходного 100k manufactured-случая и специальную алгебраическую кривизну. Она не является новым правилом выбора рабочего корня или сертификатом динамической устойчивости.

Вместо безусловного полного шага используется `armijo-infinity-positive-voltage-v1`. Начальная длина α=1; при недопустимом состоянии или недостаточном уменьшении фактической невязки она делится пополам не более 24 раз. Условие приёмки: ‖F(x+αΔx)‖∞ ≤ (1−10⁻⁴α)·‖F(x)‖∞. Все модули напряжения должны быть положительными и конечными, углы — конечными. Значения не обрезаются и уравнения не меняются. Неудача всех 25 проб возвращает `line_search_failed`; предел Newton-итераций и допуски не увеличиваются автоматически.

Результат фиксирует `solver.step_policy`, `armijo_coefficient`, `max_backtracks_per_step`, `line_search_trials`, `damped_steps` и `min_step_length`. Пробы включают отклонённые недопустимые состояния, поэтому это не число вычислений невязки. Счётчики суммируются по Q-проходам и островам; минимум α берётся по всем принятым шагам (1 при отсутствии шагов). `root_selection=initial-state-dependent-no-stability-certification` явно сохраняет ограничение выбора корня.

`test/newton_globalization.jl`: 40 проверок на плотном и CSC-пути используют независимую двухузловую цепь с единичной проводимостью, slack V=1, PQ P=−0,2 и Q=0 p.u. Уравнение V(V−1)=−0,2 имеет два аналитических корня (1±√0,2)/2. Старты 0,49 и 0,51 приводят к соответствующим разным корням с допуском 10⁻⁹ p.u. Проверяются уменьшение невязки, сохранение исходных массивов и slack, конечный бюджет поиска и отказ при переполнении всех проб; неразрешимый P=−0,3 не становится успешным результатом.

Ещё 7 проверок относятся к radial/100000, seed=20261021. До изменения он завершался `non_positive_voltage` на втором шаге. Теперь поиск принимает первый шаг α=0,25 и находит корень за 6 итераций с невязкой около 8,49·10⁻¹¹ p.u. Независимая сумма токов по исходным рёбрам подтверждает заданные PQ и баланс. Но максимальное напряжение около 2,0289 p.u., а отличие от заранее заданного manufactured-решения — около 1,0344 p.u. Начав с заранее заданного решения, тот же решатель подтверждает его без итераций. Это прямое свидетельство нескольких корней, а не прохождение строгого эталона 10⁻⁸ p.u.

Ограничение шага по размеру тоже исследовалось отдельно и не обеспечило выбора эталонного корня; физические границы напряжения ради этого не вводились. NUM-NR-START-01 и CORE-05 остаются открытыми в части выбора ветви решения, режимных ограничений и проверки устойчивости. Маленькая невязка сама по себе не даёт такой гарантии. [Профиль до изменения алгоритма](./sparse-compute.md#ac-network-families) сохранён со своими контрольными суммами и не выдаётся за измерение нового пути.

## Мощности на выводах источника — 2026-10-21

`sources.p_mw/q_mvar` сохраняют выдачу внутренней ЭДС. Дополнительно возвращаются `terminal_p_mw/terminal_q_mvar` (выдача в сеть) и `losses_p_mw/losses_q_mvar` внутренней ветви. Независимая проверка `test/source_terminal_power.jl` решает цепь E–Zист–Zлинии–PQ через квадратное уравнение для u=|Vнагрузки|²:

```text
a = (Zист + Zлинии) · conj(Sнагрузки)
u² + (2Re(a) − E²)u + |a|² = 0
Vнагрузки = conj((u + a) / E)
Iэфф = conj(Sнагрузки / Vнагрузки)
Sвыводов = (Vнагрузки + Zлинии · Iэфф) · conj(Iэфф)
SЭДС = E · conj(Iэфф); ΔSист = Zист · |Iэфф|²
```

Используется высоковольтный корень, E=10 кВ (линейное RMS), мощности — полные трёхфазные МВт/Мвар, Z — Ом на фазу; Iэфф=√3·Iфазы в кА. Четыре случая включают Q=±3 и 0 Мвар, Rист=0 и 0,1 Ом. Это результаты статической модели ЭДС за сопротивлением; терминальные Q-ограничения, capability curve и полные потери машины не добавлены.

## Фазосдвиг двухобмоточного трансформатора — 2026-10-21

`phase_shift_deg` задаёт φ=arg(Vнн/Vвн) при нулевом последовательном токе; положительный φ означает опережение НН. Модуль k=Uнн/Uвн остаётся вещественным полем `ratio`, комплексный коэффициент t=k·exp(jφ) используется внутри модели. На общей системе базисов:

```text
I₁ = Y₀V₁ + y(V₁ − V₂/t)
I₂ = Y₂V₂ + yV₂/|t|² − yV₁/conj(t)
Y₁₂ = −y/t; Y₂₁ = −y/conj(t)
```

Токи и напряжения в этих уравнениях — фазоры на фазу; паспортные напряжения — линейные RMS кВ, мощности — полные трёхфазные МВт/Мвар. Y₀ отнесена к ВН, Y₂=0 для текущего трансформатора. Комплексное сопряжение сохраняет баланс мощности идеальной трансформации; нельзя делить диагональ на t² или делать взаимные элементы одинаковыми. Плотная проверочная сборка, разреженная CSC-матрица, потоки и разбиение на острова сохраняют один коэффициент. Параметр конечный, в [−180,180]; отсутствие/пустое поле означает 0° с записью допущения. Это не преобразователь группы соединения, модель нейтрали, РПН или динамики.

`transformer-phase-v1.json` — шесть собственных синтетических цепей 110/10 кВ, независимо решённых PYPOWER 5.1.19: φ=0, ±15°, ±30° и два параллельных трансформатора +5°/−5° с циркулирующим потоком. В PYPOWER отвод расположен на стороне from, поэтому SHIFT=−φ, а последовательное сопротивление приведено к НН. Отличие соглашений подтверждено [формулами makeYbus](https://github.com/MATPOWER/matpower/blob/master/lib/makeYbus.m), не копированием ожидаемых значений Enersy. Внешняя Y₀ задана шунтом ВН и включена в физические мощности/токи порта каждого трансформатора при сравнении.

`backend-julia/test/transformer_phase.jl` содержит 772 проверки: два общих базиса, смена ID/координат/поворота, обратная запись проводов, HTTP-обработчик, потоки/токи/баланс, равенство плотной и разреженной сборки, Якобианы и центральные конечные разности, холостой ход при ±180° и отрицательные входы. Допуски до сравнения: 1e-8 p.u./rad, 1e-6 МВт/Мвар, 1e-8 кА; Якобиан 1e-6 абсолютный/1e-7 относительный. Диапазон входа не является гарантией сходимости любого режима. Существующие AC/ZIP-эталоны сохраняются.

## ZIP-нагрузки — 2026-10-21

В симметричном установившемся AC-профиле нагрузка по умолчанию остаётся постоянной PQ. Явный `zip_enabled=true` включает статическую зависимость от напряжения:

```text
u = U_LL,RMS / U_nom,LL,RMS
P(U) = P_nom · (p_z·u² + p_i·u + p_p)
Q(U) = Q_nom · (q_z·u² + q_i·u + q_p)
```

P_nom — полная трёхфазная MW, Q_nom — полная трёхфазная Mvar; U_nom задаётся явно в kV. Для P и Q используются независимые доли Z/I/P. Все шесть долей обязательны, лежат в [0,1], каждая тройка суммируется в 1 с абсолютным допуском 1e-12. Коэффициенты не перенормируются. Сами P/Q сохраняют действующее соглашение нагрузки: положительный параметр — потребление, отрицательный — инъекция. Частотно-зависимые характеристики, отключение по напряжению, пуск/динамика двигателя и EMT этим не реализованы. Полиномиальная структура соответствует общему [описанию ZIP в MATPOWER](https://matpower.org/doc/ref-manual/classes/mp/dme_load.html); код и тестовые цепи написаны в проекте, MATPOWER при запуске не требуется.

В `PowerFlowSetup` постоянные части входят в спецификации, линейные и квадратичные — в `VoltageDemand` на общем базисе. Они вычитаются из невязок инъекции; Якобиан шага Ньютона получает положительные добавки `dP_потр/d|V|` и `dQ_потр/d|V|`. Плотный эталон и разреженная CSC-сборка используют одни уравнения, матрица сети не уплотняется. При реконструкции PV↔PQ сохраняются зависимые нагрузки. Разные нагрузки одного узла сохраняют собственные U_nom и доли. Баланс использует фактическое потребление при найденном напряжении. Ответ `loads[]` содержит исходный ID, глобальный узел, профиль и номинальные/фактические мощности; знак там положителен для потребления.

`backend-julia/test/zip_loads.jl` содержит 110 проверок:

- Чистое Z при P_nom=10 MW, Q_nom=3 Mvar, U_nom=10 kV: независимый комплексный делитель `Z_нагрузки=U_nom²/conj(S_nom)`, суммарное последовательное `Z=0.2+j1 Ω/фаза`, ЭДС 10∠0 kV. Сравниваются напряжение, угол, P/Q и баланс.
- Чистые Z, I, P и смесь 0.2/0.3/0.5 в резистивной цепи: верхний корень квадратного уравнения `U·(10−U)/0.2 = 10·(z·(U/10)²+i·U/10+p)` в физических единицах, без вызова проверяемого решателя для эталона.
- Разные смеси для P и Q: заранее заданный фазор U=9.7−j0.4 kV, U_nom=9.5 kV и физический закон Кирхгофа определяют номинальные мощности. Восстанавливаются фазор, фактические мощности и потери, включая повторение на базисах 100 MVA/10 kV и 50 MVA/20 kV. Это изготовленный аналитический пример, не результат независимой программы.
- Производные полной невязки проверены центральной разностью с шагом 1e-6: ошибка <1e-8; плотный и разреженный Якобианы согласуются до 1e-12. Для физических примеров: U до 1e-8 kV, угол до 1e-9 rad, P/Q/потери/баланс до 1e-8 MW/Mvar.
- Совместные ZIP/PQ на одном узле, два независимых острова, смена порядка/координат, реальный обработчик HTTP и сохранение профиля при активных Q-ограничениях. Для последнего баланс до 1e-6 MW/Mvar; прежний Q-эталон при этом не объявляется независимым ZIP-эталоном.

## Многоузловые ZIP-эталоны — 2026-10-21

`backend-julia/test/reference/zip-networks-v1.json` содержит четыре внешних эталона, полученных pandapower 3.5.3. Сети проекта на 9/14/30 физических узлов дополнены тремя внутренними узлами ЭДС; четвёртый кейс повторяет 9-узловую сеть с фиксированной Q=-5 Мвар одного PV-источника. Это собственные синтетические сети, **не IEEE-кейсы**. Из прежнего набора читаются только физические входные схемы и карта идентичности оборудования, не ожидаемые напряжения/мощности или матрицы Y.

В каждом кейсе есть разные доли Z/I/P для P и Q, чистые Z/I/P, линии с активной/реактивной зарядной проводимостью и параллельными цепями, источник за импедансом и ёмкостный шунт. На одном узле находятся дополнительные нагрузки с Uном 107 и 112 кВ, включая отрицательную Q. Базис исходного сравнения — 100 MVA/110 kV; проверяются 50 MVA/220 kV, смена ID/координат/порядка объектов, обратная запись проводов и HTTP-обработчик. Состав: 12/17/33 расчётных узла, 11/16/32 нагрузки и 14/21/42 последовательные ветви; в кейсе Q-ограничения — 12/11/14 соответственно.

Внешний расчёт: [pandapower 3.5.3 Newton](https://pandapower.readthedocs.io/en/v3.5.3/powerflow/ac.html), плоский старт, `voltage_depend_loads=true`, `enforce_q_lims=true`, 1e-9 MVA, 50 итераций; numba, lightsim2grid и distributed slack выключены. Его ядро происходит от PYPOWER: это внешняя реализация относительно Enersy, а не доказательство независимости двух семейств алгоритмов. Библиотека нужна только отдельному генератору; рабочее Julia-ядро и Docker-архитектура приложения не заменяются. У линий во внешнем API задана требуемая служебная оценка тока 1 кА; она не участвует в расчёте режима и не объявляется инженерной проверкой допустимой нагрузки.

При прямой передаче нескольких неодинаковых ZIP-нагрузок одного узла pandapower 3.5.3 в `_calc_pq_elements_and_add_on_ppc` усредняет доли по числу нагрузок. В первом примере это дало несогласованный внешний баланс около 0.0656 MW / 0.0195 Mvar, и генератор отказался принимать результат. Поэтому независимая сборка сначала точно суммирует коэффициенты полиномов узла на базисе его напряжения, затем передаёт один электрически эквивалентный ZIP в неизменённую библиотеку. Это сохраняет все исходные нагрузки и их Uном без добавочного сопротивления. Индивидуальные мощности восстанавливаются по внешним напряжениям и исходным характеристикам; их суммы сверяются с нативным `res_load` до 1e-8 MW/Mvar, а полный внешний баланс — до 1e-6. Текущие агрегированные полиномы имеют неотрицательные коэффициенты; произвольные знакопеременные агрегаты этим адаптером не покрыты.

## Арифметика базисов — 2026-10-21

Для трёхфазного S_base в MVA и линейного U_base в kV используются Z_base=U_base²/S_base (Ом/фаза) и I_base=S_base/(√3·U_base) (kA RMS). Конечные положительные входы ещё не гарантируют представимость производных масштабов в Float64. Конструктор отклоняет непредставимые масштабы с `invalid_base`; HTTP возвращает 400. Разложение на мантиссу и двоичный порядок исключает преждевременное переполнение промежуточных произведений — используются стандартные [frexp и ldexp Julia](https://docs.julialang.org/en/v1.10/base/math/#Base.Math.frexp).

156 новых проверок сравнивают формулы с BigFloat (256 бит), проверяют диапазон порядков и HTTP-диагностику. Допуск — 8·eps(Float64) относительно и минимальное положительное субнормальное Float64 абсолютно. Полный набор текущего исходного кода в Docker Julia 1.10.12: 1329 проверок прошли. Это проверка арифметики базисов, а не подтверждение полного расчёта сети на экстремальных масштабах; существующие независимые физические эталоны также прошли. Подробности воспроизведения — [NUM-BASE-01](./defects.md#num-base-01-переполнение-промежуточных-выражений-базиса-2026-10-21).

## Нагруженный трансформатор через компилятор

`compiled_transformer` в JSON — отдельный независимый трёхузловой эталон:
внутренняя ЭДС 113.3 kV за R=0.1 Ω, X=0.5 Ω, шина 110 kV, трансформатор
110/10 kV, нагрузка 10 MW + j3 Mvar. Паспорт трансформатора: 100 MVA,
Pкз=1 MW, Uкз=10%, Pxx=0.1 MW, Ixx=1%.

В PYPOWER сопротивление трансформатора отнесено к стороне НН, коэффициент
from-side равен 11; в проекте сопротивление отнесено к ВН, `ratio=1/11`.
При общем Vbase=110 kV эти записи дают одинаковую Y. Ветвь намагничивания
PYPOWER задана шунтом шины ВН, в проекте включена в порт трансформатора;
при сравнении потока порта добавляется независимая мощность этого шунта
`|Vhv|²(G−jB)` к потоку PYPOWER. Ожидаемые значения не берутся из Enersy.

Схема создаётся из RawComponent/RawConnection и проходит `calculate`:
терминальная топология, модели, Y, классификация узлов, Newton и отчёт.
Проверены V/θ/P/Q и мощности концов с допусками из таблицы, перестановка
объектов/связей, перенумерация ID и изменение координат/поворотов.
При смене общего базиса на 50 MVA / 10 kV физические kV/углы/MW/Mvar
сохраняются: допуск 1e-7 kV/deg и 1e-6 MW/Mvar.
Этот кейс проверяет функцию расчёта; отдельный HTTP-тест трансформатора
и многоузловые сети через редактор ещё не добавлены.

## Многоисточниковые физические схемы через HTTP

`compiled_networks` содержит три собственные схемы с 9/14/30 физическими
узлами сети и тремя дополнительными внутренними узлами ЭДС (итого 12/17/33).
У всех источников заданы сопротивления в Ω, ЭДС в kV и активная мощность в MW;
один источник явно выбран slack, два работают PV на внутренних узлах.
Кольцо с дополнительными ветвями составлено из π-моделей линий: длина в km,
R/X в Ω/km, G/B в S/km, одна или две параллельные цепи. На каждом физическом
узле задана нагрузка P/Q, к одному узлу подключён конденсатор 2 Mvar.
Tap/фазосдвиг отсутствуют в этих трёх схемах; они отдельно проверяются в кейсах ядра.

Генератор формирует исходные DTO схемы, независимо собирает эквивалентную
сеть PYPOWER и решает её. Активная проводимость наполнения линии в PYPOWER
представлена половинами GS на двух шинах: номинальная мощность каждой половины
`G0·L·circuits·U_nom²/2`. Для сравнения физических портов в JSON сохранены
как исходные потоки PYPOWER, так и сумма потока с мощностью этого шунта при
независимом расчётном напряжении. В Enersy G входит непосредственно в π-модель.

Проверяются результат `calculate`, тот же результат после перенумерации
ID/перестановки объектов и связей/изменения координат и поворотов, затем JSON
через реальный HTTP-сокет `/calculate`. Сопоставление выполняется по исходному
оборудованию и признаку внутреннего узла, а не по индексам компилятора.
Проверены все узловые V/θ/P/Q, мощности обоих концов всех ветвей, выбор slack,
два PV и баланс P/Q. Допуски — из таблицы, остаток баланса меньше 1e-6 MW/Mvar.

## Профиль Q-границ внутренней ЭДС

Опциональные параметры генератора `q_min_emf_mvar` и `q_max_emf_mvar`
задаются парой, конечны, минимум не больше максимума. Границы относятся к
инъекции **внутреннего узла ЭДС**, а не к мощности терминала за сопротивлением.
Без них ограничения не выдумываются. Это экспериментальный профиль текущей
модели источника, не паспортная capability curve электрической машины.

После сходимости PV с нарушением границы становится PQ: P сохраняется, Q
фиксируется на границе, модуль ЭДС освобождается. Следующий Newton получает
предыдущие напряжения/углы; общий `max_iterations` ограничивает сумму шагов.
После каждого решения проверяется также возможность возврата PQ→PV.
Контракт локального регулирования: при Qmax модуль ЭДС ≤ уставки, при Qmin ≥
уставки; нарушение соответствующего условия освобождает границу и восстанавливает
исходные P/модуль ЭДС. При равных границах Q остаётся фиксированным.
Численный допуск сравнения Q в p.u. и напряжения в p.u. — `options.tolerance`.
Смена slack не реализована. Внешняя проверка регуляторов после решения соответствует
описанию [циклов PowerWorld](https://www.powerworld.com/WebHelp/Content/MainDocumentation_HTML/Solving_the_Power_Flow.htm);
приведённые условия — явный контракт этого экспериментального профиля, а не
подтверждение всего алгоритма независимой программой.
Повтор активного набора даёт `q_limit_active_set_cycle`, исчерпание числа проходов
(`max_iterations`) — `q_limit_active_set_budget`. Они не выдаются за успешный режим.
Объявленная граница slack проверяется после стабилизации остальных ограничений;
нарушение — ошибка `slack_q_limit`, а не успешный ограниченный режим.

В ответе узел и источник получают фактический тип `pq`,
`q_limit_status=clamped`, `q_limits_applied=true`; события `q_limit_events`
содержат component ID, исходный Q, фиксированный Q (p.u.) и номер прохода.
`solver.q_limit_passes`, общий счётчик итераций и предупреждения позволяют
проследить расчёт. Неактивная объявленная граница — `within_bounds`, отсутствие
границ — `not_declared`. Сходимость не доказывает соблюдение всех иных ограничений.
Возврат записывается событием `from=pq/to=pv`, с `v_before_pu`, `v_target_pu`,
исходным Q и номером прохода; итоговый статус источника — `within_bounds`.
Идентификатор политики: `internal-emf-active-set-pv-pq`.

В `q_limit_networks` четыре независимых эталона той же физической схемы на
9 узлов: верхняя граница −5 Mvar первого PV, нижняя 0 Mvar, неактивный диапазон
−100…100 Mvar и два одновременно ограниченных PV (−5 и −6 Mvar).
PYPOWER независимо решает заранее явно заданную PQ-постановку известного
активного набора; его автоматический ENFORCE_Q_LIMS здесь выключен.
Это проверяет физический результат выбранных переключений, а не все возможные
траектории выбора активного набора. V/θ/P/Q, все концы ветвей и баланс прошли
допуски из таблицы; HTTP проверен реальным сокетом. Дополнительно проверены
равные границы, неполная пара, NaN, обратный диапазон, общий бюджет и отказ slack.

В `q_release_network` начальный режим нарушает две границы: верхнюю −5 Mvar
источника 2001 и нижнюю 20 Mvar источника 2002. После ограничения 2002 первый
источник снова может регулировать ЭДС 1.02 p.u. в диапазоне −100…−5 Mvar.
Монотонный алгоритм ошибочно оставлял оба источника PQ: дефект воспроизведён
семью упавшими проверками до изменения решателя. Независимый PYPOWER решает
конечную постановку с 2001=PV, 2002=PQ; автоматические Q-переключения отключены.
Проверяются V/θ/P/Q, все мощности концов ветвей, баланс и реальный HTTP.
Отдельная аналитическая ёмкостная двухузловая сеть с обратной чувствительностью
Q/V проверяет отказ при цикле, а не пригодность AVR возле коллапса напряжения.

## Независимые питаемые острова

`calculate` разделяет собранную систему по физическим связям. Параметры и общий
базис сохраняются; локальные индексы используются только внутри solver и
возвращаются к глобальным индексам компилятора во всех узлах, концах ветвей,
источниках, шунтах и Q-событиях. Острова имеют независимые опорные углы.
Ровно один явно выбранный slack допускается в каждом острове; единственный
источник может стать slack автоматически. Ambiguous/multiple slack и остров
без источника прекращают запрос. Частичный результат не публикуется.
Distributed slack, смена slack при Q-ограничении и обесточенный профиль ещё отсутствуют.

`solver.slack_buses` / `slack_components` — массивы для всех островов.
Старые скалярные `slack_bus` / `slack_component` остаются только для одного острова.
`island_results` содержит island ID, глобальные bus IDs, slack, PV/PQ,
число уравнений/неизвестных, итерации, невязку, Q-проходы, время и отдельный
баланс P/Q. Верхний баланс суммирует балансы островов, итерации — сумму шагов,
невязка — максимум. `max_iterations` общий для всех островов и Q-проходов;
его исчерпание до следующего острова — `island_iteration_budget`.
`solver.iteration_budget_scope=all-islands-and-q-passes` явно фиксирует этот смысл.

290 проверок соединяют два существующих независимых эталона: 9-узловую схему
с возвратом PQ→PV и 14-узловую схему с тремя источниками. Опорные углы −11°
и +27°; сравниваются независимые V/θ/P/Q (угол эталона плюс заданный сдвиг),
все физические концы ветвей, балансы, принадлежность и уникальность глобальных
индексов, перестановки исходных объектов и реальный HTTP `/calculate`.
Допуски — из общей таблицы. Проверены ambiguous slack в одном острове,
разомкнутая связь между островами и отказ при двух slack после её замыкания,
общий бюджет, отказ для обесточенного участка и автоматический slack отдельно
в двух одноисточниковых островах. В UI контракт проверяет полный непересекающийся
раздел узлов, источники опоры, конечность метрик и сумму итераций до отрисовки.

## Приватный проект через настоящий API — 2026-10-10

В отдельном Docker Compose стенде сценарий `tests/integration/Test-GoJuliaReference.ps1 -ProjectMode` создаёт локальный аккаунт через stdin оператора, входит по HTTP, создаёт приватный проект/схему и пять объектов. Четыре связи создаются защищёнными командами с UUID и текущей топологической ревизией. Расчёт выполняется через `/api/projects/{projectId}/schemes/{schemeId}/calculate` с явными `three-phase/newton-raphson` и If-Match. Анонимный запрос отклоняется; успешный ответ содержит SHA256 входа и идентификаторы/ревизию снимка, запрещает кеширование.

Физическая схема — источник, шины 110/10 кВ, двухобмоточный трансформатор с потерями/магнитизацией и нагрузка 10 MW + 3 Mvar. Результат сравнивается с `compiled_transformer` из независимого набора `backend-julia/test/reference/ac-networks-v1.json`. Проверяются V/θ/P/Q трёх расчётных узлов и потоки обоих концов двух ветвей; принадлежность устанавливается по исходному оборудованию, а не порядку узлов. Магнитизация приводится к одинаковой физической границе HV трансформатора.

Локально обе версии сценария (приватная и legacy) прошли: V/P/Q — 1e-8 p.u., θ — 1e-8 rad, потоки ветвей — 1e-6 MW/Mvar. Временные данные удалены после проверки. Сценарии включены в CI; удалённый запуск приватного варианта ещё не подтверждён. Это проверка конкретного симметричного установившегося режима, без расширения области применимости на динамику или все виды оборудования. Изоляцию при отзыве доступа во время расчёта отдельно проверяет PostgreSQL/HTTP-worker регрессия Go.
