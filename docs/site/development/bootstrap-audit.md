# Аудит bootstrap-данных и история миграций

Команда `server -audit-database` проверяет ограниченную область БД и выдаёт JSON-отчёт. Она предназначена оператору Docker-установки, не опубликована через HTTP и не выдаёт имена, пароли, токены, параметры оборудования или содержимое проектов.

Она завершается до обычного `initDB`: **не применяет миграции**, не заполняет контрольные суммы и не запускает API. Все запросы БД выполняются в одной `READ ONLY REPEATABLE READ` транзакции; режим чтения подтверждается самой PostgreSQL. Для основных SQL-запросов задан лимит 5 секунд, ожидания блокировки — 1 секунда. Контекст операций БД CLI ограничен 15 секундами; это не принудительное прерывание чтения SQL-файлов с файловой системы. При ошибке полный отчёт не выдаётся.

## Запуск в Docker

Отдельная [сверка каталога с seed-эталоном](./catalog-audit.md) доступна через `-audit-catalog` / `Audit-EnersyDatabase.ps1 -Catalog`. Состояние миграций и legacy-пользователей проверяется этим общим аудитом отдельно.

Для работающего контейнера API:

```powershell
./scripts/database/Audit-EnersyDatabase.ps1 -OutputFile .cache/database-audit.json
```

Каталог вывода должен существовать. Скрипт проверяет формат отчёта и вызывает только `/app/server -audit-database` внутри `go-api`; он не перезапускает сервисы. Для другого контейнера задайте `-Container`. Параметры подключения и каталог миграций берутся из конфигурации этого контейнера, а не из отдельной установленной PostgreSQL/Go на компьютере оператора.

Можно вызвать CLI напрямую:

```powershell
docker compose exec -T go-api /app/server -audit-database
```

Для ещё не запущенного API нужен одноразовый контейнер с образом приложения и настройками подключения к проверяемой БД. Не запускайте обычный сервер ради аудита старой БД: обычный запуск выполняет миграции. Встроенный каталог SQL ищется относительно исполняемого файла. Явный `MIGRATIONS_SOURCE` предназначен для разработки/тестов; нельзя подменять им применённую историю ради зелёного отчёта.

## Смысл отчёта

| Поле | Что подтверждается |
| --- | --- |
| `formatVersion`, `scope` | Формат 1; только `legacy-bootstrap-and-migration-inventory` |
| `readOnly`, `capturedAt` | Подтверждённая сервером транзакция чтения и время её снимка |
| `latestSourceVersion` | Последняя версия зафиксированного при запуске набора SQL |
| `version`, `dirty` | Текущая отметка мигратора; строки версий передаются без округления |
| `legacyUsers` | Число строк старой таблицы `users`, не число действующих аккаунтов |
| `duplicateLegacyNameGroups` | Группы точно равных `name` с несколькими строками; это кандидаты для разбора, а не доказанные дубли людей |
| `unresolvedLegacyOwners` | Заданные (не NULL) `owner_id` схем, для которых нет соответствующего ID в legacy `users`; NULL-владелец не заменяется выдуманным ID |
| `migrationVersionRows` | В таблице отметки мигратора должна быть ровно одна строка |
| `checksumMismatches`, `missingIntegrityEntries`, `unexpectedIntegrityEntries` | Расхождения, пропуски и лишние записи относительно зафиксированного набора SQL и текущей версии |
| `legacyBaselineEntries` | Исторические записи, впервые зафиксированные как baseline; прежние байты SQL этим не доказываются |
| `referenceChecks` | Количества NULL, отсутствующих целей и межсхемных несоответствий для [фиксированных legacy-связей](#legacy-reference-checks); непроверенное — JSON null |
| `findings` | Коды наблюдений, без содержимого пользовательских строк |

Отсутствующая таблица/непроверенная величина передаётся как `null`, а не как нулевой результат. Неизвестная версия, dirty, ожидающие миграции, отсутствующий источник, повреждённая история и расхождения требуют разбирательства. При несовместимой структуре или ошибке SQL команда может завершиться с ошибкой вместо частичного JSON.

Статус `no_findings_in_audited_scope` означает отсутствие замечаний только в этой области. Он **не проверяет** весь каталог по эталону, физику, пригодность расчётов, все ограничения БД, права пользователей, backup/restore или безопасность установки. `review_required` означает наличие наблюдений, включая честно обозначенный исторический baseline; сам по себе он не равен отказу readiness. Успешное выполнение CLI возвращает код 0 и при наличии наблюдений: автоматизация должна анализировать `status`/`findings`, а не только exit code. Ошибка выполнения/вывода возвращает ненулевой код.

## Политика старых данных

1. `database/init.sql` и `database/ees_schema.sql` сохраняются для воспроизведения исторического импорта. Это не второй путь обновления работающей БД. Штатный путь — последовательные версионированные миграции, применённые файлы не редактируются.
2. Старый `INSERT users ('Alice'),('Bob') ON CONFLICT DO NOTHING` не был идемпотентным: уникального ограничения имени нет. Повтор bootstrap может создать новые ID с теми же именами. Считать их одной личностью, добавлять `UNIQUE(name)` или удалять строки по имени автоматически нельзя.
3. `users` и `circuit_schemes.owner_id` — legacy-данные; они не предоставляют доступ к приватным проектам. Совпадение ID/имени с `auth_accounts` не означает тождество и не служит основанием назначения роли. Действующие права задаются проектом и аутентифицированной сессией.
4. До переноса нужна резервная копия и закрытый операторский разбор конкретных ID, зависимостей и происхождения. Карта старых/новых ID подтверждается отдельно; отсутствие FK не означает отсутствие внешних ссылок или выгрузок. Сначала проверяются зависимые строки и восстановление копии. Аудит не выполняет объединение, удаление или назначение прав.
5. Старые SQL views заменяются штатной миграцией определения. `invalid_scheme_connections` — диагностическое представление связей, а не физический решатель и не механизм предоставления доступа. Проверка эквивалентности миграций сравнивает итоговые определения views; копирование старого view поверх новой схемы не поддерживается.

## Проверки 2026-10-25

На PostgreSQL 15 в Docker проверены чистая установка, оба legacy SQL, двукратный bootstrap, неизвестный ID старого владельца, dirty, будущая/неизвестная версия, пустая отметка мигратора, изменённая контрольная сумма, отсутствующий SQL-источник и отмена. Аудит сохранил структуру, проверяемые строки каталога и все legacy-пользовательские строки; содержимое этих строк в JSON не попало. Для отсутствующей таблицы пользователей подтверждён `null`. Исполнение настоящего CLI на пустой БД не создало таблиц мигратора и не заполнило baseline. PowerShell-обёртка проверена на рабочей установке, без исправления её данных.

`TestMigrationDeploymentPostgres` дополнительно разворачивает **реальную непосредственно предыдущую версию** из соответствующего поднабора миграций, сохраняет объект/параметр/геометрию и обновляет её полным набором. Итоговые столбцы, ограничения, индексы, функции, triggers, views и каталог по естественным ключам совпали с чистой установкой; объект сохранился. Предыдущая версия для текущего набора — `20261021002`, новая — `20261024001`; следующая миграция автоматически сдвигает этот тестовый барьер.

Вместе прошли существующие проверки future/unknown/dirty, изменённого и удалённого SQL, пропуска истории, нормализации CRLF, исторического baseline, параллельных первых запусков и повторного развёртывания. `go vet` прошёл. Это не новый прогон численных эталонов и не подтверждение удалённого CI. Политика полноценного сравнения фактического legacy-каталога с эталонным, включая пользовательские изменения, и конкретные карты переноса остаются открытыми в BASE-05.

## Карта legacy-владельцев схем {#legacy-owner-map}

Оператор может явно исправить ссылку `circuit_schemes.owner_id` у схемы без приватного проекта. Это исторические метаданные: они не определяют действующий аккаунт или доступ к проекту. Команды не объединяют и не удаляют строки `users`, не переименовывают людей, не создают аккаунты, сессии или роли. Совпадение имени не используется для выбора целевого ID. Приватные схемы с заданным `project_id` отклоняются.

### Снимок для разбора

```powershell
docker compose exec -T go-api /app/server -audit-legacy-owners
```

Отчёт формата 1, `scope: legacy-scheme-owner-inventory`, возвращает область `database`/`schema`, текущую версию и отпечаток SQL, `snapshotSha256` и списки `users`/`schemes`. У строк есть точный строковый `id` и `rowSha256`; у схем дополнительно `ownerId` и `projectId`, включая явный `null`. Имена людей, названия/описания схем и прочие исходные значения в JSON не включаются. Для разрешения неоднозначности оператор отдельно проверяет первоисточник конкретных ID.

`rowSha256` — SHA-256 UTF-8 представления PostgreSQL `to_jsonb(строка)::text` целиком. Общий отпечаток — SHA-256 Go JSON объекта с упорядоченными по числовому ID массивами `users` и `schemes`, содержащими эти ссылки/хеши. Он включает также строки с одинаковыми именами, NULL и неизвестными ID владельцев. Дата формирования в отпечаток не подмешивается. Изменение любой пользовательской строки или схемы требует нового снимка. Временная смена значения с последующим полным восстановлением прежних байтов отдельным журналом не обнаруживается.

Инвентарь читается в одной подтверждённой сервером `READ ONLY REPEATABLE READ` транзакции; максимум 100000 строк каждой таблицы, сверх лимита — ошибка. Изначально выбранная схема БД закрепляется: отсутствующая таблица не читается из следующей схемы `search_path`. Режим требует полностью обновлённую чистую БД и согласованную историю checksum. Для предварительного анализа ещё не обновлённой базы используется прежний `-audit-database`.

### Явное решение по ID

```json
{
  "formatVersion": 1,
  "scope": "legacy-scheme-owner-map",
  "database": "app_db",
  "schema": "public",
  "sourceVersion": "20261024001",
  "migrationSha256": "<из своего текущего снимка>",
  "snapshotSha256": "<из своего текущего снимка>",
  "changes": [
    {
      "schemeId": "123",
      "expectedSchemeSha256": "<rowSha256 выбранной схемы>",
      "fromOwnerId": "17",
      "toOwnerId": "23",
      "reason": "Явный выбор по проверенному источнику для конкретной схемы"
    }
  ]
}
```

Пример показывает структуру, а не готовое решение для рабочей БД. Хеши заменяются своими 64-символьными значениями. `fromOwnerId` и `toOwnerId` обязательно присутствуют: пропуск отличается от явного JSON `null`. Источник может быть неизвестным или даже отрицательным старым ID, если именно он сохранён в схеме; новый ненулевой ID должен быть положительной десятичной строкой и существовать в legacy `users`. Явный `toOwnerId: null` очищает только историческую ссылку. Для выбора владельца ранее незаполненной схемы задаётся `fromOwnerId: null`. Пустая операция, повтор схемы и числовые JSON ID отклоняются.

Одинаковое имя у исходного и целевого ID не подтверждает, что это один человек. Карта фиксирует отдельное операторское решение по схеме; обе строки пользователей остаются на месте. Неизвестные внешние ссылки на прежние ID не переназначаются. Причина обязательна, до 1000 байт UTF-8; карта и квитанция содержат этот комментарий. Общие ограничения: один UTF-8 JSON до 1 MiB, не более 1000 изменений, без неизвестных полей, дублей ключей и второго документа.

### Проверка и применение

После резервного копирования и разбора первоисточников:

```powershell
$map = Get-Content -LiteralPath .cache/reviewed-legacy-owners.json -Raw -Encoding utf8
$map | docker compose exec -T go-api /app/server -check-legacy-owner-map
# После проверки карты и результата, в окно обслуживания:
$map | docker compose exec -T go-api /app/server -apply-legacy-owner-map
```

Проверка возвращает `checked_not_applied` из read-only транзакции. Применение повторяет все условия и до чтения снимка блокирует `users`, `circuit_schemes` и историю миграций. Lock timeout — 2 секунды, statement timeout — 10, предел CLI после чтения входа — 15. Сравниваются область подключения, версия/отпечаток SQL, полный снимок, хеш каждой схемы, прежний владелец, отсутствие приватного проекта и существование выбранного target. Неоднозначный ID не выбирается автоматически.

В одной транзакции обновляется только `owner_id`. Все остальные поля схем, оборудование, параметры, топология, пользователи и действующие права сохраняются. Источник SQL проверяется повторно до commit. Ошибка любой записи откатывает весь пакет. Все операторские режимы взаимоисключающие, HTTP-маршрута нет; команда не запускает bootstrap/миграции и доступна администратору контейнера/БД.

Успех `applied` возвращается после commit вместе с SHA-256 карты и отпечатками до/после. Это контроль целостности, а не подпись или доказательство личности. Повтор исходной карты отклоняется из-за изменившегося снимка. При потере ответа сначала проверяют фактическое состояние; для обратного изменения готовят новую карту по новому снимку. Автоматический перенос legacy ID в `auth_accounts`, выдача доступа, удаление дублей и обработка внешних ссылок этим не реализованы.

### Приёмка — 2026-10-26 {#legacy-owner-verification}

Проверено на одноразовой PostgreSQL 15.19 в Docker. Рабочие legacy-владельцы не переназначались.

| Сценарий | Подтверждённое поведение |
| --- | --- |
| Две строки с одинаковым именем | Обе строки пользователей сохранены |
| Переназначение конкретной схемы | Меняется только исторический `owner_id` |
| NULL и неизвестный отрицательный ID | Явное заполнение или очистка по карте |
| Аккаунты, сессии и участники | Новые записи и права не появляются |
| Ошибка второй записи | Весь пакет откатывается |
| Два одновременных применения | Успешно ровно одно |
| Изменившийся пользователь или схема | Устаревшая карта отклоняется |
| Занятая таблица | Lock timeout без изменения владельца |
| Запасная схема в `search_path` | Инвентарь не выходит за выбранную схему |

Настоящий CLI прошёл аудит, проверку, применение, отказ повторной карты и отказ совмещения операторских режимов. Проверены также отсутствующий target, другой источник/версия/снимок/область БД, dirty и неполная история миграций. Запрет приватной схемы отдельно проверен на синтетическом снимке; новые аутентифицированные аккаунты для этой приёмки не создавались. Полный Go-набор с race и PostgreSQL: 105 успешных тестов верхнего уровня, три opt-in интеграции пропущены. `go vet` и сборка прошли. Это не новый прогон физического ядра и не подтверждение удалённого CI.

## Зависимости legacy-узлов и результатов {#legacy-reference-checks}

`-audit-database` дополнительно возвращает `referenceChecks`: 37 агрегированных проверок в той же READ ONLY REPEATABLE READ транзакции и с прежними таймаутами. Это аддитивное поле формата 1. Отдельный HTTP-маршрут и миграция БД не добавлены. Отчёт не содержит конкретных ID, названий, координат, физических параметров или численных результатов.

Для каждой из 16 ссылок проверяются отдельно отсутствие значения (`<table>.<column>.null`) и заданный ID без целевой строки (`<table>.<column>.dangling`). Проверяемый перечень фиксирован:

| Источник | Ссылка на |
| --- | --- |
| `component_params_template.component_type_id` | `component_types.id` |
| `equipment_models.component_type_id` | `component_types.id` |
| `equipment_model_params.equipment_model_id` | `equipment_models.id` |
| `scheme_components.scheme_id`, `component_type_id` | `circuit_schemes.id`, `component_types.id` |
| `scheme_component_params.scheme_component_id` | `scheme_components.id` |
| `scheme_connections.scheme_id`, `from_component_id`, `to_component_id` | `circuit_schemes.id`, `scheme_components.id` для обеих сторон |
| `circuit_nodes.scheme_id` | `circuit_schemes.id` |
| `calculation_results.scheme_id` | `circuit_schemes.id` |
| `calculation_node_results.calculation_id`, `node_id` | `calculation_results.id`, `circuit_nodes.id` |
| `calculation_branch_results.calculation_id`, `from_component_id`, `to_component_id` | `calculation_results.id`, `scheme_components.id` для обеих сторон |

Ещё пять проверок выявляют существующие строки с разными ненулевыми ID схем: `nodeResults.schemeMismatch`, `branchResults.fromSchemeMismatch`, `branchResults.toSchemeMismatch`, `scheme_connections.from_component_id.schemeMismatch` и `scheme_connections.to_component_id.schemeMismatch`. Например, узел существует, расчёт существует, но узел относится к другой схеме — одних отдельных FK на ID для этого недостаточно. Совпадение числового `node_number` не используется вместо идентичности узла.

Число в `referenceChecks` — количество строк источника, соответствующих конкретному условию. Одна строка может попасть в несколько независимых проверок; их нельзя складывать в число уникальных повреждённых объектов. Числовой 0 означает выполненный запрос без таких строк. JSON null означает отсутствие необходимой таблицы/колонки в точной текущей схеме. Если источник существует, а таблица цели отсутствует, проверка `.null` может быть выполнена, а `.dangling` остаётся неизвестной. Таблицы из fallback `search_path` не подставляются. Несовместимые типы, отсутствие прав и ошибки SQL завершают весь аудит ошибкой, без успешного частичного отчёта.

Ненулевая проверка добавляет `legacy_references_require_review`; неизвестная — `legacy_reference_checks_incomplete`. NULL исторически допускается частью SQL-колонок и сам по себе не доказывает порчу: оператор должен установить, является ли запись незавершённой, непривязанной или ошибочной. Аудит не выбирает замену и не восстанавливает связь по имени, номеру, координатам или соседству.

Область охватывает все строки перечисленных legacy-таблиц, включая возможные ссылки на уже приватные схемы; это операторский агрегат, а не проверка доступа участника проекта. Ссылки на legacy-модели экземпляров и владельцев проверяются отдельными средствами каталога и карты владельцев. Произвольные пользовательские таблицы, файлы, выгрузки, внешние системы, современная авторизация и достоверность старых численных результатов этим перечнем не подтверждаются. Физические значения в старых результатах не пересчитываются и не объявляются проверенными.

Приёмка на отдельной PostgreSQL: четыре затронутых верхнеуровневых теста с детектором гонок прошли (4.475 с), включая fresh, оба legacy-bootstrap и повторный bootstrap. Синтетический повреждённый fixture отдельно подтвердил NULL, отсутствующий node ID и пять межсхемных несоответствий; сравнение строк узлов, расчётов, узловых/ветвевых результатов и соединений до/после совпало. Для представления более старого состояния только в тестовой схеме сняты новые составные ограничения/port-trigger и один FK; рабочая БД и её ограничения не использовались. Удаление целевой таблицы дало неизвестные проверки вместо нулей; другая точная схема не читала похожие таблицы из search_path. Имена, значения и ID fixture не попали в JSON.

Это подготовка проверяемого переноса, а не сам перенос legacy-данных. Сохранение внешних ссылок, явные карты остальных ID, backup/restore и подтверждённое назначение реальных аккаунтов/проектов остаются в BASE-05.

Дополнительная проверка выпуска: полный Go vet/build и race-набор прошёл — 123 верхнеуровневых теста, 5 прежних opt-in пропущены, 124.707 с. Отдельно после добавления CLI-проверки собран реальный бинарник: `-audit-database` на пустой схеме выдал 37 неизвестных значений и не создал ни одного отношения; при несовместимых типах legacy-колонок команда отказала без JSON в stdout. Этот сценарий с race прошёл за 1.357 с. Запуск subprocess ограничен 20 секундами. Go-линтер до добавления последнего CLI-теста: 0 замечаний; новая миграция и изменение рабочего развёртывания не требуются.
