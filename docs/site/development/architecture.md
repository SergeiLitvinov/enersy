# Архитектура проекта

| Область | Реализация | Ответственность |
| --- | --- | --- |
| Интерфейс | React / TypeScript | Редактор, выбор паспорта, ввод параметров и отображение результата |
| API | Go | Хранение схем и каталога, миграции, проксирование расчёта |
| Вычисления | Julia / EnersyCompute | Проверка входа, сборка электрической топологии, модели и решение |
| Данные | PostgreSQL | Каталог, схемы, параметры, соединения |
| Геометрические функции | Rust / WASM | Вспомогательная обработка редактора; не численное ядро энергосистемы |
| Документация | VitePress / TypeDoc / Node | Руководство, канонические правила и автоматически построенный справочник |

## Границы домена

Физический объект, заводской паспорт, математическая модель, расчётное представление и графический символ должны иметь независимые идентичности. Это целевой принцип; текущая SQL-схема ещё связывает часть этих сущностей через тип и строковые параметры. Положение объекта на холсте не является электрической связью.

В Julia `dto.jl` проверяет вход, `units.jl` задаёт базисы, `topology.jl` собирает узлы по портам, `models.jl` формирует проводимости, `solver/newton_raphson.jl` решает AC-задачу, `calculate.jl` преобразует результат. `http_api.jl` отделён от пакета; запуск сервера находится в `server/main.jl`.

## Оценка текущего устройства

Разделение React / Go / Julia подходит для постепенного развития. Переписывание стека сейчас не решит главные проблемы: нужны устойчивые доменные контракты и воспроизводимые расчёты. Go стоит развивать как модульное прикладное ядро; вычислительный worker отделять по жизненному циклу задания, без дробления каждого справочника на отдельный сервис.

Приоритеты: версионированные объекты/терминалы/модели, единый источник описаний портов, неизменяемый снимок запуска и автомат состояний задания. Затем — разреженные матрицы и измерения масштаба. Оптимизация Rust/WASM оправдана после профилирования, а не как замена физического ядра.

`component_creation.go` уже сохраняет паспорт и параметры транзакцией. `connections.go` проверяет схему и порты по таблице `component_type_ports`; ограничения PostgreSQL дополнительно защищают новые записи. Этот legacy-реестр ещё не является версионированным контрактом всех терминалов: геометрия в TypeScript и топологические алиасы Julia пока требуют согласования. Исправление интерфейса само по себе не устраняет этот архитектурный долг.

## Расширение моделей

Для тяжёлых задач рассматривается [гибридное вычислительное ядро](./compute-backends): Julia плюс опциональные Rust/native или специализированные C/C++-модули. Решение о переносе принимается по одинаковым физическим тестам и измерениям, а не по названию языка. Этот путь пока является предложением.

Добавление символа или строки каталога недостаточно. Опишите терминалы, физические параметры и единицы, уравнения и границы применимости. Добавьте независимый эталон, диагностику неверного входа и запись о поддержке. Пока нет полноценного plugin ABI моделей; не представляйте ручное изменение Julia как готовую систему пользовательских плагинов.

## Будущие интеграции

Редактор развивается как [два вида одной сети](./diagram-views): принципиальная схема с УГО и расчётная схема замещения. ModelBinding, внутренние узлы и раскладки отделяются от паспорта и физического графа; полный выбор модели ещё предстоит реализовать.

IEC 61850 планируется как опциональный адаптер к `C:\project\open-libiec61850`. Его сетевой обмен не входит в residual численного решателя. Будущая opencim не является основанием внутреннего домена или обязательной зависимостью.

Детальный [анализ проекта](/generated/review) фиксирует исходные проблемы; [правила](/generated/rules) задают требования. Выполненные изменения и остающиеся критерии отражаются в [TODO](/generated/todo).
