# Агентный интерфейс, MCP и harness

Решение от 2026-11-01: развивать агентный способ работы **дополнительно к стандартному редактору**. Уже есть общий слой чтения/создания оборудования, каталог и ограниченный Docker stdio MCP-мост. Встроенный harness и чат пока не реализованы. План — AGENT-01–04 в [TODO](/generated/todo). Обычная Docker-поставка и расчёты работают без LLM, внешнего провайдера и MCP-клиента.

## Основание: что взято из Voco

Просмотрена текущая рабочая копия `C:/project/voco`: `server/api/automation.py`, `server/api/agent_harness.py`, `server/mcp.py` и `docs/architecture/agent-harness.md`. Базовый HEAD — `eef3f64`, эти четыре файла ещё не закоммичены. Это статический разбор параллельной разработки, не запуск тестов Voco и не подтверждение его готовности.

Полезное разделение: AutomationService предоставляет общий каталог команд, MCP адаптирует транспорт для внешнего клиента, а harness исполняет цикл запросов модели и инструментов. Встроенный чат не получает собственную копию инженерного документа. Перед изменением проверяются scope и revision, после команды — фактическое состояние и инженерные артефакты.

Переносится этот принцип, а не Python/CAD-реализация. У Enersy другая модель многопользовательского доступа и PostgreSQL: квитанции команд должны переживать restart и повтор сетевого запроса. Описанная в Voco ограниченная память receipts не подходит для такой гарантии. Loopback-only URL его stdio-моста также нельзя слепо перенести в Docker: сервисы Enersy соединяются через явно заданное внутреннее имя API.

## Один владелец состояния

| Слой | Ответственность |
| --- | --- |
| React, MCP-клиент, встроенный чат | Разные способы формировать намерение пользователя и отображать результат |
| Прикладные команды Go | Права, типизированные входы, ожидаемые ревизии, транзакции, квитанции и события |
| PostgreSQL | Общая схема проекта, версии паспортов/Study, журнал выполнения и неизменяемые снимки |
| Julia / Rust | Проверка физической постановки, компиляция и поддержанные численные методы |

MCP и harness используют те же прикладные операции, что HTTP/UI. В адаптере нет отдельного графа, собственных SQL-обновлений или копии уравнений. Стандартный редактор продолжает работать и показывает изменения агента через обычное обновление ревизий.

LLM выбирает действия из опубликованного каталога; доменные и численные валидаторы определяют допустимость. Наличие инструмента не расширяет область численной приёмки. Поддержка УГО трёхобмоточного трансформатора, например, сама по себе не разрешает агенту объявить расчёт его режима реализованным.

## Реализованная основа: чтение схемы {#shared-scheme-read}

Первая операция общего слоя — `applicationService.ReadScheme` в `backend-go/application_scheme.go`. Она принимает серверную сессию отдельно от типизированного `readSchemeCommand` с project/scheme ID. HTTP-обработчик редактора вызывает эту операцию; прикладной код не создаёт HTTP-запросов и не хранит глобально выбранный проект.

Доступ к точной паре проект/схема и весь граф читаются в одной read-only repeatable-read транзакции. DTO типизирован: компоненты, строковые частные IDs/ревизии, исходный текст параметров, объявленные единицы, паспортная привязка, терминальные соединения и диагностика. Объекты и связи упорядочены по ID. Существующий анонимный редактор сохраняет числовой формат IDs через тот же reader; прикладная операция не переключается в анонимный режим при нулевом project ID. Полученный снимок не даёт разрешения на последующую запись; следующий вызов снова проверяет права.

Это ограниченная основа AGENT-01. Каталог и MCP уже используют чтение и защищённое создание оборудования, описанные ниже. Перенос остальных записей на постоянные квитанции и встроенный harness ещё предстоят. Дополнительных учётных данных или обязательных сервисов этот слой не добавляет.

## Контракт команды и контекста

Каждый вызов имеет версию схемы, типизированные аргументы и ограниченный размер. Контекст содержит проект, схему/Study, рабочий контекст и ожидаемые ревизии. Автор определяется серверной аутентификацией; переданный в аргументах accountId не даёт прав. Доступ к контексту, списку инструментов, вызову и квитанции повторно проверяется при каждой операции, включая replay после отзыва сессии.

Запись получает уникальный commandId и hash намерения. Та же команда с тем же содержимым возвращает сохранённую квитанцию; повтор commandId с другими аргументами отклоняется. Изменение и успешная квитанция фиксируются одной транзакцией. Потеря ответа после commit не означает разрешение повторно создать оборудование. Неизвестный исход сначала сверяется по квитанции и текущей ревизии. Автоматический retry записи без такого контракта не включается.

Уже есть полезная основа: If-Match/ревизии объектов и топологии, durable-команды соединений, commandId сохранения Study и постановки Run, неизменяемые входы/происхождение, права проектов и отдельные сессии. Общее прикладное чтение схемы уже выделено; полного command service для изменений графа ещё нет — это оставшаяся часть первого этапа. Существующие CRUD-методы не объявляются автоматически идемпотентными.

Сначала публикуются чтение контекста, каталога, схемы, поддержанных моделей/движков, состояния Study/Run и диагностики. Запись добавляется по мере готовности общего контракта: оборудование и параметры с единицами, терминальные соединения, состояние аппаратов, паспортная привязка, снимок Study и запуск. Неподдержанные cancel/pause/step не обещаются и не эмулируются остановкой контейнера.

## Первая защищённая запись: создание оборудования {#equipment-command}

`applicationService.CreateEquipment` принимает сессию отдельно от команды: project ID, UUID, ожидаемая ревизия топологии и типизированное оборудование. ID схемы входит в намерение. Автор определяется по заблокированной серверной сессии; повтор другим аккаунтом отклоняется. Новый вызов сравнивает топологию, использует общую валидацию/копирование каталога и проектного паспорта и фиксирует оборудование, параметры и квитанцию одной транзакцией. Текст параметров и объявленные паспортом единицы сохраняются.

Квитанции находятся в `project_application_commands` (аддитивная миграция v2). Ключ уникален в проекте; изменения и удаление отдельной квитанции запрещены. История удаляется только вместе с её схемой/проектом. Повтор с тем же автором и точным намерением возвращает исходные ID/ревизию/параметры, даже если каталог изменился или ответ первого вызова потерян. Тот же UUID с другими данными/ожидаемой ревизией — 409. Для новой команды устаревшая топология — 412. Конкурирующие вызовы сериализованы по ключу и схеме. При replay заново проверяются права и сессия; удалённое после создания оборудование отмечается `deleted=true` и не создаётся повторно.

Существующий POST `/api/projects/{project}/schemes/{scheme}/components` включает этот режим при передаче `Idempotency-Key: UUID` и `If-Match: "topologyRevision"`. Ответ дополнен commandId/deleted/topologyRevision, повтор отмечен заголовком `Idempotency-Replayed: true`. ID/ревизия оборудования и параметры относятся к исходному созданию; topologyRevision и deleted отражают состояние на момент текущего подтверждения. Это квитанция, а не разрешение считать оборудование неизменённым: актуальный граф нужно перечитать. Обычный POST без обоих заголовков пока остаётся однократным и не получает гарантии replay. Отдельный read-receipt endpoint ещё не опубликован.

Приватный редактор теперь использует UUID и CAS для каждого нового создания. Перед POST точное намерение записывается в sessionStorage вкладки; ошибка сохранения останавливает отправку. Ключ изолирован по account/session/project/scheme. При открытии редактора записи восстанавливаются в заблокированную очередь для явной сверки; «Повторить создание» отправляет исходные UUID/CAS/данные. После квитанции требуется новое полное чтение схемы. Только затем удаляются локальная запись и барьер. Явное принятие серверного состава также снимает только выбранные намерения. Созданное, а затем удалённое оборудование не появляется заново.

ProjectEditor передаёт ожидаемые account/session заголовками; Go сравнивает их с аутентифицированной cookie внутри транзакции, удерживая блокировки сессии/аккаунта/проекта. Смена cookie другой вкладкой приводит к command_session_changed (409), не к новой записи от другого автора. Ожидаемые IDs не являются разрешением и не входят в hash инженерного намерения. Прямой прикладной клиент может задать ExpectedIdentity; без неё всё равно действуют обычные права и привязка квитанции к автору. Выход и обнаруженная смена сессии очищают прежние локальные команды. Это сохранение создания в той же вкладке, не UI полного серверного автосохранения всех правок CORE-06. Запись, удаление и обновление прочих объектов также ещё не переведены на этот общий контракт; MCP использует только защищённое создание; встроенный harness ещё не реализован.

## Каталог доступных прикладных операций {#operation-catalog}

GET `/api/projects/{project}/schemes/{scheme}/operations` возвращает formatVersion=1, точные строковые projectId/schemeId, названия ожидаемых identity headers и список доступных операций. Каталог читает текущий доступ к точной паре проект/схема одним SQL-запросом, не загружая физический граф. Читатель получает только scheme.read.v1; владелец, администратор и редактор — также component.create.v1. Чужой проект, несовпадающая пара IDs и отозванная сессия не получают каталог. Ответы не кешируются; получение каталога не является разрешением на последующее выполнение.

| ID | Вызов | Повтор |
| --- | --- | --- |
| scheme.read.v1 | GET существующего URL схемы; аргументы — пустой объект | Новое наблюдение текущего согласованного графа |
| component.create.v1 | POST существующего URL components | Постоянная квитанция исходного намерения и автора |

Каждая запись содержит description, readOnly, replaySemantics, returnsEngineeringResult=false, inputSchema и http. Схемы описаны в закреплённом диалекте [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core). Это описание транспортной формы, не замена доменной валидации и не подтверждение физической применимости. На сервере дополнительно проверяются точные числовые границы десятичных IDs/ревизий, байтовые ограничения строк, модели и права. POST оборудования ограничен 1 МиБ. Язык численного ядра, поддержка решателей и расчётные статусы этим каталогом не расширяются.

Для создания inputSchema требует commandId, expectedTopologyRevision и equipment с явной геометрией, типом, именем и исходными параметрами. Выбирается один паспортный источник; единицы/параметры не придумываются. В http указаны относительный путь в текущем scope, метод, bodyArgument=equipment и header mappings: commandId → Idempotency-Key (raw-string), expectedTopologyRevision → If-Match (strong-etag, десятичная строка в двойных кавычках). Нельзя заменять исходные UUID/CAS при повторе. Квитанция не доказывает сохранность объекта сейчас — после неё требуется новое чтение графа.

Актор задаётся доверенной сессией отдельно от аргументов инструментов. При использовании ожидаемого контекста клиент передаёт оба X-Enersy-Account-Id/X-Enersy-Session-Id, сохраняя их точными строками. Каталог и приватное чтение схемы теперь также проверяют эти заголовки; несоответствие — 409 command_session_changed, неполная/неверная пара — 400. Проверка чтения входит в тот же repeatable-read снимок, что права и граф. Приватный редактор уже передаёт ожидания для защищённого создания; перенос остальных его чтений/записей на такую привязку ещё не завершён.

Новые операции не исполняются через `/operations`: это только discovery; POST и выдуманные подмаршруты отклоняются. Описания указывают на существующие обработчики общих ReadScheme/CreateEquipment. Идентификатор создания общий для каталога, digest и записи журнала; отдельного графа или копии записи нет. Карты/схемы создаются заново на каждый вызов: изменение выданного DTO не меняет следующий каталог. SQL/shell/управление физическими устройствами и неподдержанные расчётные методы не публикуются.

Ограниченный MCP-adapter реализован отдельным Go-модулем `mcp-go` и опциональным Compose-профилем `mcp`. Он использует этот каталог и обычный приватный API; доступа к БД у него нет. Сам HTTP discovery не является MCP transport. Встроенный harness ещё не реализован.

## Два агентных режима

**Внешний клиент через MCP.** Пользователь подключает свой клиент; его harness и LLM остаются снаружи Enersy. Начальный вариант — opt-in Docker stdio-адаптер к работающему API. stdout содержит только JSON-RPC, журнал — stderr. У адаптера явно задан API origin; произвольные URL, SQL и shell не являются инструментами модели. Сессионные credentials задаются вне аргументов и контекста LLM, а модель видит только разрешённый проект.

Закреплён и проверяется [stdio initialize-профиль MCP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), официальный [Go SDK](https://github.com/modelcontextprotocol/go-sdk) находится только в отдельном модуле/образе. При запросе другой версии сервер предлагает 2025-11-25; клиент обязан поддержать её либо отключиться. Профиль 2026-07-28, Streamable HTTP, Tasks, resources, prompts и Apps не объявляются. Внешнему клиенту остаётся собственный harness. [Запуск и ограничения моста](../guide/mcp.md).

**Встроенный harness.** Отдельный исполнитель получает цель, разрешённый scope, бюджет и сообщения. Цикл: получить актуальный контекст → запросить модель → проверить tool call → исполнить команду → прочитать наблюдение → продолжить или проверить завершение. Адаптер провайдера отделён от доменных инструментов; конкретный облачный или локальный LLM не становится обязательной зависимостью ядра.

Harness ограничивает шаги, время, токены и параллелизм по пользователю/проекту. Его состояние и события сохраняются; после restart незавершённый ход имеет явный статус interrupted. Продолжение сверяет квитанции и свежие ревизии. Provider context и приватный reasoning не выдаются через публичные DTO или чужую сессию. «Остановить» запрещает следующие действия; отмена уже принятого расчёта — отдельная команда с собственным подтверждённым исходом. Принятые правки не откатываются вместе с чужими изменениями.

## Пользовательский интерфейс и инженерный контроль

Чат — дополнительная панель, не замена схемному редактору. Режим «План» даёт только чтение. Режим изменения ограничен явно выбранным проектом, разрешёнными действиями и бюджетом. В пределах выданного режима не требуется отдельная карточка подтверждения каждой обычной правки. Удаление значимых данных, расширение доступа и выход за заданный scope имеют отдельную политику. Журнал показывает, что принято сервером, что отклонено и какие результаты действительно получены.

Текст паспорта, названия элементов, импортированные материалы и ответы инструментов — данные, а не новые разрешения. Агент не подставляет физические параметры для видимости сходимости, не меняет единицы/допуски/границы без инженерного основания и не исполняет произвольный код для обхода штатных методов. Недостающий ток КЗ, схема нейтрали или номинал требуют уточнения либо явной диагностики.

Перед передачей данных провайдеру пользователь видит выбранное подключение и область контекста. Секреты остаются на сервере. Данные одного проекта/аккаунта не попадают в другой через кеш, историю или сообщения позднего хода. IEC 61850 и команды физическим устройствам не входят в начальный агентный интерфейс.

Завершение инженерной задачи подтверждается текущим снимком и квитанциями, поддержанным статусом решателя, единицами, сходимостью, балансами и неизменяемым результатом. Фраза модели «готово» не является критерием. Независимые эталоны и допуски остаются общими для ручного, MCP и встроенного сценария.

## Порядок приёмки

### Проверенный stdio-срез, 2026-11-01

Отдельный модуль закрепляет официальный Go MCP SDK 1.4.1, JSON Schema 2020-12 и профиль 2025-11-25. В API эти зависимости не добавлены. HTTP-клиент не использует переменную proxy и не следует перенаправлениям; принимает только выбранный origin, фиксированные пути и ограниченные JSON-ответы. API origin на обычном HTTP допускается только для loopback/localhost или Docker-имени `go-api`; внешний origin требует HTTPS.

На Docker Linux amd64 прошли Go vet и race-тесты моста: конфигурация и точные IDs, официальный SDK-клиент, актуальный discovery/отзыв доступа, проверка аргументов до HTTP, отмена с прерыванием HTTP, отсутствие отражения ошибок/секретов, redirects и размер ответа. Независимые сырые stdio fixtures проверяют negotiation/fallback, точную корреляцию ID, EOF, дубли ключей, UTF-8/UTF-16, глубину и размер кадра. В отдельном процессе настоящий SDK-клиент прошёл через API и PostgreSQL: владелец/read-only default, viewer при write opt-in, создание/replay, stale CAS, изменённое намерение, чужой и отозванный акторы. Итог — три компонента (два исходных fixture + один созданный) и одна постоянная квитанция. Это пять групп тестов моста плюс интеграционная группа API; opt-in клиент в обычном unit-прогоне пропускается и затем реально выполняется backend fixture.

Запуск из корня после подготовки обычных Go-зависимостей:

```sh
docker compose -f tests/integration/go-compose.yml run --rm --no-deps dependencies
docker compose -f tests/integration/mcp-compose.yml run --rm --no-deps dependencies
docker compose -f tests/integration/mcp-compose.yml run --rm mcp-check
docker compose -f tests/integration/mcp-compose.yml run --rm --no-deps lint
docker compose -f tests/integration/mcp-compose.yml run --rm --no-deps audit
docker compose -f tests/integration/mcp-compose.yml down
```

### Следующие уровни

1. Общий command service: два пользователя, несколько сессий, конфликт ревизий, потеря acknowledgement, restart и replay без второй записи; отозванная сессия не получает квитанцию.
2. MCP: negotiation, discovery, schemas, framing/лимиты, неизвестные инструменты, приватность и настоящая работа через API; неподдержанные расширения не объявляются.
3. Harness: детерминированный fake-provider в CI управляет реальными командами и worker; подменён только LLM. Результат AC-схемы сопоставляется с независимым эталоном. Проверяются ошибки инструментов, Stop, interruption и неизвестный исход записи.
4. Панель чата: стандартный редактор и агент показывают один граф; конфликт сохраняет намерение; позднее событие чужого scope отвергается; браузерная приёмка включает узкий экран и клавиатуру. Живая модель — дополнительный smoke, не замена воспроизводимых тестов.
