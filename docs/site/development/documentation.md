При обновлении Node сначала выбрать поддерживаемую ветку, проверить содержимое образа и новую точную версию, затем согласованно изменить `.node-version` и digest во всех Node Dockerfile/Compose. После установки по lock-файлам выполнить сборку, типизацию, линтер, тесты и аудиты frontend/сайта. При обновлении nginx проверить оба proxy через `tests/integration/Test-ProxyDns.ps1`: смена IP контейнеров, сохранение путей и query-параметров, восстановление DNS без перезагрузки proxy. Не заменять digest автоматически при каждом запуске. Изменение этих образов не обновляет PostgreSQL и не требует изменения пользовательской БД.

Сборочный SDK API — Go 1.26.10; модуль требует Go 1.26.0. Dockerfile, интеграционные клиенты Go и генератор эталона каталога используют закреплённый Alpine-образ SDK. `GOTOOLCHAIN=local` запрещает незаметную загрузку другого компилятора. Production-бинарный файл собирается с `CGO_ENABLED=0`, `-mod=readonly` и `-trimpath`. Runtime — Alpine 3.24.3 по digest; корневые сертификаты уже входят в этот образ, поэтому установка пакетов через плавающий APK-репозиторий больше не нужна.

`tests/integration/go-compose.yml` задаёт отдельную проверочную среду для разработчика и CI. Для детектора гонок используется Go 1.26.10 на Debian Bookworm с C-компилятором; версия Go совпадает со сборкой API. PostgreSQL 15.19 хранит тестовые данные в tmpfs. Портов host и томов рабочего приложения нет. Исходники подключены только для чтения; writable-кэши располагаются в `.cache`. Проверки не могут перезаписать `go.mod`, `go.sum` или эталон каталога.

Из корня проекта:

```sh
docker compose -f tests/integration/go-compose.yml run --rm --no-deps dependencies
docker compose -f tests/integration/go-compose.yml up -d --wait postgres
docker compose -f tests/integration/go-compose.yml run --rm --no-deps go-check
docker compose -f tests/integration/go-compose.yml run --rm --no-deps lint
docker compose -f tests/integration/go-compose.yml run --rm --no-deps audit
docker compose -f tests/integration/go-compose.yml down
```

В CI очистка выполняется и после ошибки. При ручном запуске также завершайте стенд командой `down`. Подготовка модулей и аудит имеют отдельную сеть для доступа к реестрам; `go-check` и линтер работают во внутренней сети с `GOPROXY=off` и `-mod=readonly`. Отсутствующая зависимость останавливает проверку. Для запуска достаточно Docker/Compose; SDK Go на host не требуется.

Проверено 2026-10-25 на `linux/amd64`: production-сборка API, `go vet`, обычные PostgreSQL-тесты на Alpine и финальный набор с `go test -race -v -count=1` на Bookworm. В финальном race-прогоне прошли 89 верхнеуровневых тестов, три отдельных сценария worker/профилирования пропущены (`TestCalculationArchiveWorkerPostgres`, `TestCalculationSnapshotProfilePostgres`, `TestStudyFrozenInputWorkerPostgres`). Проверки охватывают миграции, контроль их содержимого, аудит каталога, проекты, права, сессии, версии исследования, ошибки доставки и запрет перенаправлений worker; повторную численную приёмку Julia/Rust этот прогон не заменяет. Линтер и форматирование прошли без замечаний; отдельный неформатированный fixture подтвердил ошибку `fmt --diff` с кодом 1. Удалённый запуск GitHub Actions этим локальным отчётом не подтверждён.

Полные digest SDK и тестовой БД записаны в Compose, digest runtime — в `backend-go/Dockerfile`. PostgreSQL закреплён на 15.19: основной Compose и проверка backup/restore — Debian-образ, одноразовые интеграционные стенды — Alpine. Переход с 15.18 и проверка реальной резервной копии описаны в [приёмке PostgreSQL](./postgres-upgrades.md). Обновление остальных инструментов/зависимостей остаётся частью BASE-07.

Линтер закреплён как `golangci-lint 2.15.0` по digest. В его образе установлен SDK Go 1.27.2, сам инструмент собран Go 1.27.0; production и race-тесты используют Go 1.26.10. Конфигурация версии 2 сохраняет анализаторы `errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`, `gosec`, `misspell`, `revive`; прежний `gosimple` входит в `staticcheck`. Для него явно выбраны прежние семейства `SA*` и `S1*`, без ранее отдельно включавшихся stylecheck и quick-fix. `gofmt` и `goimports` проверяются отдельным `fmt --diff`, поскольку в версии 2 это форматтеры. Сохранены прежние исключения и таймаут 3 минуты; анализаторы перечислены явно, чтобы изменение стандартного набора инструмента не меняло проверку молча. Основание переноса — [официальное руководство миграции](https://golangci-lint.run/docs/product/migration-guide/).

После переноса исправлена обработка ошибок записи HTTP и отката транзакций, удалены две неиспользуемые функции. Ожидаемый `sql.ErrTxDone` после commit не считается сбоем отката; другие ошибки регистрируются. Ошибка доставки ответа не вызывает повторную запись тела или изменение уже отправленного статуса. Общая выдача точных JSON-байтов проверяет синтаксис и MIME-защиту, сохраняя содержимое архива и его SHA-256. Worker не может перенаправить расчётные входы на другой URL. [HTTP-контракт](../reference/http.md). Точечные исключения gosec сопровождаются основаниями у кода: фиксированные SQL-фрагменты и quoted identifiers, публичные PHC-параметры и имена колонок, операторские cookie/worker-настройки, проверенный JSON вместо HTML.

Аудит Go выполняет закреплённый `govulncheck v1.9.0` с `-test` и `CGO_ENABLED=0`, как при production-сборке. До обновления модулей 2026-10-25 он не нашёл достижимых уязвимостей и замечаний в импортируемых пакетах, но сообщил о 18 уязвимостях в других пакетах требуемых модулей `golang.org/x/crypto v0.46.0` и `golang.org/x/sys v0.39.0`. Формат результата, анализ достижимости и ограничения описаны в [официальной документации govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck). CI использует текстовый режим, в котором найденная достижимая уязвимость завершает команду ошибкой; JSON-режим сам по себе таким барьером не является. Сбой установки инструмента или доступа к базе advisory также не считается успешной проверкой.

### Совместимое обновление модулей Go {#go-dependencies}

2026-10-25 штатным Go-инструментом обновлены только `x/crypto` до 0.58.0 и `x/sys` до 0.49.0. Обе версии требуют Go 1.26.0, выбранный SDK 1.26.10 сохранён. `go mod tidy` заменил четыре записи контрольных сумм прежних версий; остальные runtime-зависимости не менялись. Формат и параметры Argon2id, соль, длина ключа, PHC-префикс, формат cookie и хеширование сессий сохранены; миграция или сброс паролей не требуются.

Проверены синтетические PHC-хеши, заранее полученные на `x/crypto 0.46.0`: ASCII и кириллица с emoji, правильный и неправильный пароль. Это проверка совместимости со старой реализацией, не независимая сертификация криптографии. PostgreSQL-регрессия читает старую запись пароля без её перезаписи и сессию с заранее вычисленным SHA-256. Отзыв старой сессии не отзывает новую сессию того же пользователя. Производственные аккаунты в тестах не используются.

После обновления прошёл полный Go-прогон с PostgreSQL и детектором гонок: 91 верхнеуровневый тест; прежние три отдельных сценария worker/профилирования пропущены в этом стенде. Осталась [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932) для неиспользуемого OpenPGP: в advisory нет исправленной версии. Приложение не импортирует этот пакет; правило `depguard` запрещает случайно подключить его и подпакеты, включая тестовый код. Проверка на отдельном fixture подтвердила отказ для корневого пакета, `armor` и `packet`. Замечание не скрыто из аудита, и результат не объявляется нулевым аудитом всего модуля.

### Минимальный компилятор Rust {#rust-msrv}

Заявленный в обоих Cargo-манифестах `rust-version = "1.85"` означает нижнюю границу 1.85.0, а не последний patch ветки 1.85. Для её проверки добавлен отдельный Docker-профиль:

```sh
docker compose --profile rust-msrv-check run --rm --no-deps --build rust-msrv-check
```

`scripts/build/rust-msrv.Dockerfile` закрепляет `rust:1.85.0-bookworm@sha256:0ff31c9ffa641a62e48d543fb00b4960955ea375f40776f40f585b89e654cc5e`. Официальное зеркало ECR и Docker Hub дали одинаковый digest. Сборка подготавливает зависимость `wasm-bindgen` из lock-файла и target `wasm32-unknown-unknown`. Сам сценарий выполняется без сети с лимитами 2 CPU/2 GiB. Он проверяет точную версию Rust/Cargo и заявленный минимум в обоих манифестах; затем запускает native-тесты с default/all features, release-сборку C ABI, host-тесты WASM-прототипа и release-сборку настоящего `.wasm`. Манифесты и lock-файлы сверяются по SHA-256 до и после. Подмена SDK более новым отклоняется до тестов: контрольный запуск на 1.99.1 завершился кодом 1.

На Docker `linux/amd64` 2026-10-25 конечный профиль завершился с кодом 0: фактически использовались rustc 1.85.0 и Cargo 1.85.0. Прошли 8 native-тестов с default features, 11 со всеми features, включая C ABI, и 31 host-тест WASM-прототипа. Собраны непустые release-файлы `libenersy_numerics.so` и `rust_wasm.wasm`; все четыре SHA-256 Cargo-манифестов/lock-файлов сохранились. Формулы, исходники решателей и допуски ради поддержки старого SDK не менялись. Результат относится к проверенным пакетам/targets и зафиксированному набору зависимостей, а не к любому будущему обновлению. Полная Julia↔Rust-приёмка на минимальном SDK отдельно не запускалась; ранее опубликованные 235 FFI-проверок относятся к основному SDK.

Проверка включена в Rust job CI дополнительно к тестам/Clippy/rustfmt на основном SDK 1.99.1. ### Аудит зависимостей Rust и Julia {#numerical-dependency-audit}

2026-10-25 добавлен Docker-профиль RustSec с `cargo-audit 0.22.2`, установленным через `cargo install --locked`. Образ SDK закреплён тем же digest Rust 1.99.1. Проверка читает оба `Cargo.lock` только для чтения, загружает актуальную базу и запрещает также предупреждения (`--deny warnings`). В выполненном прогоне загружены 1352 advisories; оба lock-файла просканированы, команда завершилась с кодом 0 без замечаний. Этот профиль включён в CI. Результат относится к известным замечаниям в Rust-пакетах на дату проверки, а не к контейнерной ОС, достижимости функций или всей безопасности приложения. [Назначение cargo-audit](https://github.com/rustsec/rustsec/tree/main/cargo-audit).

```sh
docker compose --profile rust-audit run --rm --no-deps --build rust-audit
docker compose --profile julia-audit run --rm --no-deps --build julia-audit
```

Julia-профиль запускает `scripts/security/audit_julia.jl` на runtime из основного Dockerfile. Скрипт читает Manifest 2.0/2.1 без изменения, запрашивает публичные имена и точные версии пакетов в [OSV API](https://google.github.io/osv.dev/post-v1-querybatch/) и печатает JSON с SHA-256 Manifest, временем, инвентарём, находками и ограничениями проверки. Локальные/repository-зависимости перечисляются отдельно и не выдаются за пакеты General. Проверяются версия фактической Julia, версия загруженного Zlib_jll и версия его бинарной zlib; SHA-256 библиотеки включается в отчёт. Несовпадение runtime/Manifest, неполный ответ, ошибка сети, повторяющийся токен или провал положительного контроля завершают команду ошибкой. Наличие замечаний также даёт код 1. Контрольная уязвимая HTTP 1.10.16 должна обнаруживаться как `JLSEC-2025-1`.

Первый запрос на Julia 1.10.12 проверил 22 версионированных пакета и отдельно перечислил 13 записей без версии. Были обнаружены [JLSEC-2026-479](https://security.julialang.org/advisories/JLSEC-2026-479/) и [JLSEC-2026-480](https://security.julialang.org/advisories/JLSEC-2026-480/) для встроенной zlib 1.2.13. Символ MiniZip отсутствовал, CRC combine присутствовал; Pkg.update/Pkg.add в копии окружения не заменили встроенную библиотеку. Эти находки привели к обновлению runtime ниже. В конечной сборке Julia 1.13.2 аудит проверил 34 версионированных пакета, отдельно исключил локальную запись самого проекта и вернул 0 находок с кодом 0. Версии и SHA-256 оставшихся внешних исходных пакетов не изменены.

На конечной сборке прошли 28 проверок Julia-аудитора, включая постраничный ответ, отказ при более старом runtime/несовпавшем Zlib_jll и положительный OSV-контроль. В CI включены и эти проверки, и отдельный обязательный аудит фактических зависимостей. Найденная уязвимость или недоступная база не превращаются в успешный результат. Сам удалённый запуск GitHub Actions локально не подтверждён.

Источником Julia advisories служит [база JuliaLang](https://github.com/JuliaLang/SecurityAdvisories.jl), распространяемая через OSV. Сами сопровождающие предупреждают о неполноте данных для JLL. Поиск по версии не доказывает отсутствие уязвимостей: advisories к самому runtime Julia, исключённым/неверсионированным записям и пакетам контейнерной ОС этим запросом не проверяются. Сверка runtime и бинарной zlib проверяет идентичность окружения и не заменяет эти аудиты.

### Обновление Julia и устранение замечаний zlib {#julia-runtime-upgrade}

Основной образ — `julia:1.13.2@sha256:3974efa4758e60a1a30d0bed2c9bb64c002eb5e231a7f6ea6de73f78433073b3`. Это официальный поддерживаемый stable-релиз; [страница Julia](https://julialang.org/downloads/) различает его и LTS 1.10.12. В образе действительно загружена zlib 1.3.2 (`Zlib_jll 1.3.2+0`), SHA-256 ELF-библиотеки `d3e3523af664be8ae1c883f3d353fcad2077e16b29a58c9282c57d9262cf680a`. Нужные исправленные границы обоих advisories пройдены; ignore не добавлен.

Manifest согласован штатным Pkg в копии окружения, затем проверен в конечном образе. Формат стал 2.1, версия Julia — 1.13.2; Project.toml не менялся. Обновились стандартные библиотеки и поставляемые с Julia BLAS/SuiteSparse/zlib. OpenSSL_jll 3.5.8 теперь предоставляется runtime, JLLWrappers больше не требуется. Версии и git-tree-sha1 оставшихся внешних пакетов, включая HTTP 2.8.0 и JSON3 1.14.3, сохранены. Совместимость старого Pkg с новым Manifest не заявляется; штатный запуск использует закреплённый Docker runtime.

На `linux/amd64` прошли полный численный/HTTP-набор Julia с прежними допусками, 235 проверок Julia–Rust и два интеграционных сценария Go/PostgreSQL с реальным native-worker: точный архив результата и неизменяемый снимок Study. В последнем архивном сценарии остаток баланса составил P = −1.08·10⁻¹⁴ МВт, Q = −3.55·10⁻¹⁴ Мвар. Новые результаты фиксируют Julia 1.13.2; побитовое совпадение новых расчётов со старым runtime не утверждается. Известный NUM-NR-START-01 остаётся открытым, а старые измерения производительности не пересчитываются задним числом.

На локальном стенде сохранён тег `enersy-julia-lts-before-113:20261025` с прежним проверенным образом для отката. Он не является внешним публикуемым артефактом. Смена runtime не требует миграции БД; пользовательские тома и параметры моделей не менялись.

После смены runtime отдельно выполнена миграция deprecated [JSON3](https://github.com/quinnj/JSON3.jl) на JSON.jl, описанная ниже. Сверка версий внешних пакетов в предыдущем абзаце относится к этапу смены runtime, до этой миграции.

### Миграция JSON-кодека и совместимость архивов {#json-codec-migration}

В текущем worker используется JSON.jl 1.12.2 и StructUtils 2.11.1. JSON3 1.14.3 и StructTypes удалены из Project/Manifest; остальные внешние версии сохранены при согласовании через Pkg с PRESERVE_ALL. Изменены HTTP-кодек, универсальная нормализация DTO и вызовы в тестах/benchmark/audit; формулы электрических моделей и допуски независимых эталонов не менялись. DTO теперь опирается на AbstractDict/AbstractVector вместо специальных контейнеров JSON3. [JSON.jl](https://github.com/JuliaIO/JSON.jl) поддерживает используемую ветку Julia.

Перед изменением сохранён реальный JSON3-ответ на проектную 12-узловую сеть: `test/reference/json-wire-v1/` содержит исходные вход/выход и происхождение с SHA-256, а также восемь HTTP-сценариев. SHA-256 старого результата — `c66811fd8ba49998dfc3800f12822781805695cf815ae7f186f90a8f460c9773`. Этот ответ — эталон совместимости транспорта, не замена независимой численной проверке. Сравнение новым и независимым JS-парсерами выявило только переменные `computation_time_ms` корня и острова. В тесте проверяется их конечность/неотрицательность, после чего все остальные значения и структуры сравниваются точно, без нового допуска.

JSON.jl требует полного тела, запрещает дубликаты ключей и NaN/Infinity, сохраняет null/пустые массивы и Unicode. Раньше JSON3 принимал корректный префикс с хвостом; теперь это 400 `invalid_json`. Ошибки остаются структурированными; детали сообщения парсера могут изменяться, стабильны код/категория/HTTP-статус. Нечисловой Float64 в выходе даёт 500 `serialization_failure`.

Попутно исправлен DTO-ID-01: Int64 больше 2⁵³ больше не проходит через Float64 перед проверкой диапазона. Проверены `9007199254740993`, typemax(Int64), отклонение следующего целого и boolean. Это правило Julia DTO; формат строковых ID приватного проектного API не изменён. [Зафиксированные дефекты](./defects.md#json-boundary-fixes).

Выполнены 40 проверок замороженного транспорта и 26 проверок строгого JSON/ID, полный Julia-набор и 235 проверок Julia–Rust. Go vet/build/race с PostgreSQL: 92 верхнеуровневых теста прошли, три opt-in сценария пропущены; линтер — 0 замечаний. Новый `TestJSON3CalculationArchiveCompatibilityPostgres` проверяет точное воспроизведение прежних JSON3-байтов с исходным SHA-256/ETag и доступом разных разрешённых сессий. Два opt-in сценария реального native-worker и Study дополнительно запущены отдельно и прошли. Новые ответы сохраняются точно как получены; старые архивы не пересериализуются ради нового кодека.

Аудит конечного образа проверил 33 пакета и вернул 0 advisories. Проверки аудитора, включая положительный OSV-контроль, также прошли. Нулевой аудит не подтверждает отсутствие всех возможных ошибок, лицензионную совместимость или устранение NUM-NR-START-01. Старый проверенный образ сохранён локально как `enersy-julia-before-json:20261025`; он не является внешним артефактом. [HTTP-контракт](../reference/http.md#worker-json-contract).

## Единый процесс

Руководство находится в `docs/site/guide`, пояснения разработчикам — в `docs/site/development`. Основные правила, анализ и план сохраняются в `docs/CODING_RULES.md`, `docs/PROJECT_REVIEW.md` и `TODO.md`: сайт копирует их автоматически, вручную дублировать не нужно.

Для разработки без контейнера используйте версию Node.js из `.node-version` и pnpm 11.19.0, затем из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm docs:dev
```

Перед отправкой изменений:

```sh
pnpm docs:build
pnpm docs:preview
```

Сборка выполняет тесты генератора, создаёт справочник, запускает TypeDoc и проверяет внутренние ссылки VitePress. Итог — автономный статический сайт `docs/site/.vitepress/dist`, без сервера БД и вычислительного worker. Поиск работает локально в браузере.

## Автогенерация кода

TypeDoc строит семантический справочник экспортированных функций и типов `frontend/src/api/ees-api.ts`. Он не описывает всё приложение.

`scripts/docs/generate.mjs` индексирует объявления TypeScript, Go, Julia, Rust и SQL, сохраняет исходники с комментариями/docstrings и номера строк. Индекс текстовый: не обещает разрешение типов или перегрузок. Пути и содержимое берутся из текущего дерева; выдуманных ссылок на ещё не опубликованный commit нет.

Генератор читает только перечисленные каталоги кода и четыре канонических документа, включая отчёт проверки реализации. `.env`, БД, `node_modules`, `target` и сторонние символы в сайт не включаются. Сгенерированные каталоги не коммитятся; при следующем запуске они полностью обновляются, поэтому удалённые объявления не остаются в справочнике.
